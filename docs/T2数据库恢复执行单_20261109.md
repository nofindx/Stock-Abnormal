## 3. 隔离库就绪后的执行顺序（开发侧）

### A. 真实备份恢复及对账

- 记录恢复发起、开始和完成时间、备份恢复点、任务号及目标实例。测试开始时记录假定事故发生时刻；RTO 从该时刻起计，包括等待和验收，不只算导入 SQL 用时。
- 确认恢复库包含实际使用的 `stock_basic / stock_calc_base / index_calc_base / prediction_dataset / publication_* / schema_migration`，以及备份中存在的其他表。不能只恢复 `001/002/003` 的空表，就声称恢复了当前业务库。
- 在无任务写入、无 DDL 的恢复副本上采集只读清单：

```bash
python3 -m server.tools.recovery_check snapshot --expect-database TEST_DATABASE --output /tmp/t2-before.json
```

`TEST_DATABASE` 必须替换为实际隔离库名。工具只使用 `T2_MYSQL_*`，事务为只读一致性快照，摘要不包含原始行、PDF、密钥或 token；拒绝非 InnoDB 表和空库。

- 与**同一恢复点**的备份清单对比。不断变化的生产当前库不能直接与旧备份做全表等值比较。如果云备份没有可用行级清单，明确记为缺证据：可在已恢复且无写入的隔离副本制作一致性逻辑备份，再恢复到第二测试 schema，对两者对账，以证明该逻辑备份恢复链路；这不能冒充最初云备份与生产源的逐行一致性证据。
- 恢复后再采一份清单，用下面命令做严格对账；表缺失、结构不同、行数不同、内容不同任一项均失败，不能仅凭行数一样判通过：

```bash
python3 -m server.tools.recovery_check compare /tmp/t2-before.json /tmp/t2-after.json
```

- 将事实、重置生效日期、规则版本/引用、收益向量、预测数据集和活动发布指针逐项检查；对恢复输入运行实际派生计算，与恢复前同一输入结果比较。再通过测试服务的只读 API 检查单股、预测和重点监控，不能以 SQL 对账代替 API/重放。
- 记录已备份输入之后的增量追平范围，真实恢复到当前日期时，完成行情/公告补采及派生重放后才能解除对应结果的不可用；演练只在隔离库回放，不向生产发布。

### B. 空库、迁移中断与重试

准备一个额外的**空测试 schema**，名称必须以 `t2_` 开头；不要使用上一步已有数据的恢复库。工具不会删表清库，非空会拒绝运行。只把测试账号配置给 `T2_MYSQL_*`，再执行：

```bash
T2_RUN_MYSQL_DRILL=1 python3 -m unittest server.migrations.test_mysql_recovery -v
```

- 对 `001/002/003` 分别在中间 DDL 后、最终 DDL 后且 ledger 提交前断开连接，重新连接重试，检查旧输入不丢失、未完成迁移不记成功、最终重复执行无变化。
- 在真实 MySQL 上验证公告事实/指针/outbox 发布失败一起回滚，不留下半发布结果。
- 该脚本验证的是编号迁移和共享发布事务，**不代表完整旧库升级兼容性**。当前容器实际发布路径仅应用 `003`；恢复出的旧库应沿该路径测试一次，并核对现有表/ledger/API/worker 兼容性。不在恢复库盲目回放全部历史 SQL。
- “连接中断后重试”不等于 MySQL 服务崩溃或磁盘损坏演练；本轮不执行生产故障注入。

### C. 时间目标与门禁

目标仍为 `RPO≤24h`、`RTO≤2h`。工具 `recovery_timing()` 接受带时区的恢复点、事故时刻、操作开始、恢复验收完成时间；包括等待在内的 RTO 超限、时间缺失或顺序不合法，都不能判通过。完成以上 A/B 和时间实测后再关闭 `MIGRATE-01 / RECOVERY-01`；当前只读摘要相等不能自动关闭 T2。
