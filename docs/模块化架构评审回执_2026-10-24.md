## 1. 一条根因，解释全部问题

> **评审稿按「绿地新项目」书写，而 `Stock-Abnormal` 是一个已上线的存量系统；更严重的是，目标架构与现状在存储层和计算层是「反向」的——文档把「目标态应具备的能力」当成了「当前已具备的能力」来排验收计划。**

实证对照：

| 评审稿声称 / 隐含前提 | 磁盘现实 | 证据 |
|---|---|---|
| §1「不以现有代码目录、数据库或部署方式为前提」 | 后端已上线生产（云托管 `flask-9a5y`，规则 v64/v26），代码 14,167 行 | `版本发布记录.md`、`git log` |
| §5.1「追加和更正记录，不以覆盖当前值代替历史」 | 事实账本是 `ON CONFLICT(source_id) DO UPDATE` **覆盖式** | `data/fact_ledger.py:132-134` |
| §5.2「CloudBase MySQL 是权威存储」 | 公告事实落在**容器 `/tmp`** 的 SQLite | `monitor_service.py:62` 默认 `/tmp/stock-abnormal/monitor.db` |
| §5.1「规范事实层：标准行情序列」 | 日线行情**根本不落库**，只存 30 日收益率向量 JSON | `market_calc_repository.py:97-112`；`market_service.py:2465` |
| §5.3「build_id 隔离 + 单事务切指针 + 原子发布」 | `dataset_version`/`build_id` 在 `server/` 与 `miniprogram/` **零命中** | 全仓 grep，仅评审稿自身出现 |
| §2.2「规则只定义一次，计算只实现一次」 | 阈值 **4 组字面量 + 12 处板块前缀推断**；计算实现 **两套**（线上跑 `_vector_metrics`，`engine.py` 零生产调用） | 见 §3 P1-2 / P1-3 |

**后果**：§9 的 8 步迁移计划中，没有一步的完成判定是「可验证且验证通过即代表目标达成」的（详见 §5）。

### 决策 6｜规则说明页的兼容期展示

前端第一批只做「删硬编码分支」，此时 RuleCatalog DTO 尚未落地 → 规则说明页会出现**一段无阈值表的窗口期**。
- 方案一（推荐）：整块显示「规则说明暂不可用 · 规则版本 RULE-2026-10-24.1」，并在 DTO 落地前不承诺该页可用
- 方案二：保留硬编码静态表作过渡 → **与本次治理目标冲突，不推荐**，若采用须明确标注"临时"并设到期日，否则会变成永久硬编码

### 决策 7｜版本信封缺失时的提示强度

前端第二批引入 `datasetVersion` 信封后，旧后端返回**没有**该信封。三种处置：静默通过 / 顶部黄条提示 / 阻断页面。
- 前端建议：**顶部黄条「规则/数据版本未知」**（fail-closed 但不阻断，属 §2.4 的降级表达）
- 需你确认：这个提示强度在**正式发布后**是否可接受（若届时仍是降级态，等于长期带黄条上线）。若不可接受，则必须保证后端先于前端完成信封改造。

### 决策 8｜事实账本迁移后的保留策略（影响 P1-16 工作量）

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **A（推荐）** | 事实**永久保留**，`fact_set_fingerprint` 在**查询侧**按 `recorded_at <= :T` 计算 | 模型简单，只增不改，天然可审计，符合 §5.1 追加式语义 | 每次重放要先算一遍 fingerprint（I/O 换实现简单） |

建议 **A**。若选 B，需额外明确 snapshot 的保留份数与清理策略。

## 6. 运维段要点（韩渡川）

**表决：需返工。** 理由：§8 是一份写得很好的运维目标态，但它是**绿地项目**的目标态；放到一个已上线的存量系统上，且与事实不符。**§8 不能作为当前上线验收依据**（第 8 步「上线验收」要求 RPO/RTO，而当前无任何备份能力，连一次真实恢复演练都未完成）。

**§8 的 10 条要求逐条核对结果**：仅 **2 条达标**、**4 条部分达标**、**4 条未达标**。

| §8 条款 | 状态 | 与现状差距 |
|---|---|---|
| API 服务与 Worker 在云托管运行，可分开扩缩容 | **未达标** | 单服务，定时任务在 API 进程内线程 |
| Worker 采用 MySQL 租约/幂等键防重复执行和有界并发 | **未达标** | `market_calc_job` 无租约字段，仅进程内 `threading.Lock`；`prediction_job` 租约无 fencing token |
| 慢公告/PDF 处理不得阻塞 API | **未达标** | 与 API 同进程同线程；PDF 解析无超时、无 size 上限，最坏情况 OOM |
| 多 Worker 使用 MySQL 共享租约和唯一 build 锁；重启后可恢复或安全重试 | **未达标** | 无 build 锁；重启后 `for update` 与事实账本不同实例，租约无 fencing token |
| Schema 变更按 expand-migrate-contract 部署，兼容旧 DTO/客户端版本 | **未达标** | 运行时 `ensure_schema()` 执行 DDL，且 `try/except: pass` 吞错，变更内容不进代码库 |
| 健康检查分别报告 MySQL/Tushare/公告源/**对象存储** | **部分达标** | MySQL 与 Tushare 有；对象存储**无**；健康检查无 `/health/live` 与 `/health/ready` 分离 |
| 外部源设超时、限流、熔断和按来源重试；单源失败只降低该源覆盖状态 | **部分达标** | Tushare 有超时和重试；三个公告源无统一限流/熔断/重试；无源级 `degraded` 状态区分 |
| 数据库和公告对象归档需要跨可用区备份及恢复演练；上线前定义并验证 RPO/RTO | **未达标** | 无备份自动化、无恢复演练记录、RPO/RTO 未定义 |
| 对外 API 做请求频率限制、输入白名单、响应字段最小化 | **部分达标** | 参数校验有白名单；**无限流和防刷**；响应字段未最小化 |
| 所有任务记录请求/任务 ID、输入水位、规则/代码版本、耗时、重试、输出 build 和差异摘要；敏感凭据仅放密钥管理 | **部分达标** | 任务表有重试与时间戳；无 request_id、无 P95 耗时指标 |

**阻断项（决定「当前不能拆分 Worker」）**

1. **事实账本在容器 `/tmp`，且比"容器本地盘"更差**：`MonitorRepository` 本体就是 SQLite（`monitor_service.py:70-73`），`monitor.db` + `monitor.facts.db` 两个库都可能在 `/tmp`；PDF 落 `MONITOR_PDF_DIR`（`:195`）。容器重启/扩缩容/重新发布后**近期公告快照、事实账本、PDF 全部丢失**。§8 的「分开扩缩容」在拆分后会把一个库变成 N 个互不同步的库——**拆分前必须先移库**。
2. **迁移前必须先做生产探测**（紧前任务）：确认 `MONITOR_DB_PATH` / `MONITOR_PDF_DIR` 生产实际配置，以及 `/tmp` 下文件大小与 `announcement_raw` / `announcement_fact` 当前行数。若**已配持久化路径** → 先全量导出备份再迁；若**未配（`/tmp`）** → 容器重建即从零，**不存在存量**，迁移简化为「MySQL 从零初始化 → 双写 → 影子读比对 → 切读 → 停写」。
   ⚠️ 探活禁用 `/health`（`service` 硬编码 `"ok"`，永远返回 ok）。改用 `POST /api/official-monitor/refresh`（`:306`）观察是否 200，或**直接在云托管控制台查看容器环境变量**——同一份 `container.config.json` 无法区分环境，控制台是唯一可信来源。
3. **`ensure_schema()` 无任何并发保护**：多实例或 API+Worker 并存时，`CREATE TABLE IF NOT EXISTS` + `ALTER TABLE` 并发执行会抢 MDL 导致启动即挂；且 Cold Start 每次重新执行。

**安全拆分 Worker 的顺序（不可颠倒）**
1. 补 fencing token + 心跳（不拆进程也要做——`prediction_job` 租约在单进程下同样不可靠）
2. 把事实账本与 PDF 移出 `/tmp`（迁 MySQL / 对象存储）
3. 停掉运行时 DDL，改流水线执行
4. 引入进程开关，API 与 Worker 双轨运行（Worker 空转）
5. 确认外部调度稳定后下线 `start_scheduler`；保留云托管上一版本 ≥ 7 个自然日

**RPO/RTO 建议值**（依据：日频批处理、每日一次全市场 build、源数据可重拉、无实时交易、非金融核心系统）

| 分类 | 数据 | 最大容忍丢失 | 恢复时限 | 备份方式 |
|---|---|---|---|---|
| **A. 可重建数据** | `stock_calc_base`（收益向量）、`announcement_raw`、`prediction_cache`、`prediction_dataset` | **24h**（一个交易周期），可从 Tushare / 公告源重建 | **4h**（重跑一次 build） | MySQL 实例每日自动全备（保留 7 天），无需额外设计 |
| **B. 不可重建数据** | 股票状态、公告实体、公告原文 PDF、`AnnouncementFact`（含人工核验事实） | **`15min`（最近一次增量备份）** | **1h**（回滚备份 + 重放 binlog） | **每日全备 + binlog 增量**。这是唯一不能只靠"重跑"的数据 |

**底线建议：RPO = 15 分钟，RTO = 1 小时**（按 B 类最严格要求），且**每季度一次恢复演练**。

**最小告警清单**

### 8.1 闸门增量修订（关千锤第四轮）

**新增 G9b（事实账本迁移关闭条件，须同时满足）**：新路径新增 fact **≥ 100 条** 且 覆盖 **≥ 20 个不同 `source_id`** 且 旧读连续 **14 个自然日**为 0。

> 为什么不用「连续 7 个交易日」：那是给 prediction 高频路径的（**G9 不变**）。公告是低频事件驱动，一只股票可能几周才有一条异动公告——7 天内旧读为 0 很可能只是"这几天恰好没公告"，属**假阳性**。

**G8 补充判定（实测拦截）**：`uk_fact_cur` 必须有「并发插入两行 current 被拒绝」的**实测用例**，**不允许仅凭 DDL 存在就宣称约束生效**，且须在目标 CloudBase MySQL 实例上复现。

> 背景：原方案用 `UNIQUE KEY (source_id, superseded_marker)` + **NULL 哨兵**保证"同一 source_id 最多一行 current"。关千锤照 schema 实测——**约束不生效**，并发下插进了两行 current。
> **根因**：MySQL / SQLite 的 UNIQUE 索引把 NULL 视为互不相同，两行 `(source_id, NULL)` 不构成重复。
> **修正**：哨兵改用非 NULL 常量 `0`（`fact_id` 自增从 1 起，0 不会被占用）：`superseded_marker BIGINT NOT NULL DEFAULT 0`，历史行取自身 `fact_id`。
> 这条是「公告不得重复计次」的最后一道防线，DDL 写好了、执行成功了、review 也过了，但并发下照样破——**是本次评审主题问题在数据库层的复现**。

**G8 补充判定（二）｜`is_current` 无 DB 层唯一约束（数据库专家自陈遗漏）**

初版 schema 写的是 `UNIQUE(source_id, revision_no)` + `is_current TINYINT`——`is_current` 是**普通列，没有任何唯一约束挂在它上面**，并发下可以出现两行 `is_current=1`。
- **不能靠应用层守**：两个并发更正事务各自 `SELECT` 都看到「没有 current」，各自 `INSERT`，两次都成功。这是经典 check-then-insert 竞态，`REPEATABLE READ` 挡不住（MVCC 快照读不阻塞对方插入）。
- **MySQL 不支持部分索引**，PostgreSQL 的 `UNIQUE INDEX ... WHERE is_current` 无对应物 → **哨兵是 MySQL 上唯一的 DB 层写法**，与上面的 `superseded_marker` 同源：`current_marker BIGINT NOT NULL DEFAULT 0`（0 = current，历史行取自身 `fact_id`）+ `UNIQUE(source_id, current_marker)`。
- 建议 `is_current` 改为生成列 `AS (current_marker = 0) STORED`，避免冗余双写。

> 这与「NULL 哨兵」是**不同性质的两处疏漏**：那处是约束写错（NULL 互不相同），这处是**根本没写约束**。两处都在同一条防线上——「同一公告最多一行 current」，而这条防线是「不得重复计次」的最后一道闸。

**G8 前置修订（环境前提）｜必须先确认目标 MySQL 版本**

> **`CHECK` 约束在 MySQL 8.0.16 才真正强制；5.7 及更早版本会解析 CHECK 子句后静默丢弃。** CloudBase MySQL 两种版本都可能存在。
> 任何依赖 `CHECK` 的防呆（如 `CHECK (fact_id > 0)` 保护哨兵）在 5.7 上**写了也白写**——第三次出现「约束存在 ≠ 约束生效」。若实测为 5.7，改用**导入脚本校验 + 触发器**，不依赖 `CHECK`。

**P1 清单计数说明**：数据库专家提出的「P2-6 升 P1」与运维的 P1-03 是**同一条**（运行时 DDL 正反馈），已在回执中合并为 **P1-18**，不重复计数；数据库专家补充的加重部分（`CREATE TABLE` 无 try/except 包裹、触发条件是扩缩容常态、正反馈自扩散）已并入 P1-18 正文。

**G18 前置修订**：增加「`MONITOR_DB_PATH` 生产实测结论已出，且事实账本已有明确的持久化归属与 RPO 定义」。当前状态下 G18 无论如何都过不了——一个容器 `/tmp` 文件的 RPO 要么无意义、要么无法定义。

**迁移处置前必须先做生产探测**（结论比"没配"更明确）：`container.config.json` **整个文件无任何 env 声明**；`Dockerfile` 无 VOLUME 无挂载；`MONITOR_DB_PATH` 全仓库只在 `monitor_service.py:62` 被读、测试中被临时改写，**仓库内无任何生产配置给它赋值** → 生产几乎必然走默认值 `/tmp/stock-abnormal/monitor.db`。
**注意要探测的目标文件是 `monitor.facts.db` 而非 `monitor.db`**——`monitor_service.py:65` 事实账本是派生的另一个文件。
- **已配持久化路径** → 先全量导出备份，再迁
- **未配（/tmp）** → 迁 MySQL 提为最高优先级；同时对当前存活容器做一次即时导出（成本极低），但**不为它专门设计备份方案**
