# 下一大版本广告方案（待产品确认）

> 方案版本：ADS-PLAN-20261112.1；日期：2026-11-12，Asia/Shanghai。
> 建议小程序候选版本：2.0.0，尚未正式占用版本号。当前1.0.21已提审，备案进行中；本方案不修改当前业务代码或审核包，不表示已开通流量主。

## 1. 产品目标与边界

目标是通过少量微信官方广告补贴运行成本，保持查询、行情刷新、四项预警、模拟计算、预测筛选、重点监控及公告阅读的现有能力。

首版使用微信流量主原生模板广告 `ad-custom`，以平台实际开放能力为准；如仅适合Banner，则调整为 `ad`，同一位置只使用一种形态。暂不接第三方广告SDK、自营金融推广、插屏、激励视频或付费会员。

核心计算结果、已触发提示、监管事实、数据失败原因和公告PDF不设广告解锁条件，不因广告加载失败减少或延后业务内容。不引导点击广告，不把广告包装成股票、监管公告、投资推荐或系统按钮。

## 2. 首版广告位置

| 页面 | 推荐位置 | 展示条件 |
| --- | --- | --- |
| 异动预测 | 当前筛选列表至少5张时，置于第4张业务卡之后；1–4张时置于列表末尾 | 当前列表读取成功且至少1张业务卡；每个页面实例至多1个广告组件，当前/次日标签不同时保留两份广告 |
| 单股计算 | 模拟计算卡之后、页脚之前 | 已选股票且详情读取成功；IPO暂不适用但详情读取成功仍可展示，广告不改变适用性与行情状态 |
| 重点监控 | 首版不投放 | 优先保证监管事实及公告阅读 |
| 搜索初态、规则、隐私、错误或无结果页、PDF阅读 | 不投放 | 保持操作和说明清楚 |

预测广告为列表同级的独立展示项，不能写入业务 `items`、卡片数量、排序、预测Key、筛选或股票跳转数据。切标签、筛选变化及行情刷新不能触发广告轮播或重复请求；页面可保留同一组件，不为固定“第4张”位置反复卸载重建。新的页面实例可按平台规范重新加载。

广告与股票卡有清楚的空间和样式区分，保留平台原有广告标识、关闭入口与完整点击区域；不覆盖股价、刷新、清空、标签或底部导航。具体边距与尺寸按选定模板规范及真机结果确定，不用业务卡的红黄状态样式。

## 3. 加载、失败与频率

业务S1读取成功后，广告独立加载；不等待广告再展示结果，不串入S2行情刷新、PDF下载或页面就绪判定。S2成功与失败均不自动重载广告。

首版不配置 `ad-intervals`，不做应用层自动轮播。一个页面实例最多主动挂载一次广告；返回页面、切标签、选择另一股票、清空模拟、手动刷新、跨时段业务读取都不新增广告加载循环。返回或重建的具体展示仍受微信组件生命周期及平台频控约束，不承诺能控制平台所有请求。

无填充、审核中、封禁、关闭、无效ID、网络失败、不支持的基础库均不阻断业务，也不弹窗催促重试。未加载时不展示空广告卡。遵循官方组件约定：错误时处理外层容器，不因error回调立即移除广告组件导致后续load回调失效；不自建无限重试。页面隐藏、退出后清理应用层监听和任务，不后台刷新广告。

展示广告不新增用户登录、不申请手机号等无关权限、不上传本地搜索历史及模拟输入，也不向广告位参数传股票代码、监管状态或搜索词用于应用自建定向。

## 4. 实现范围与架构

保持当前业务架构，不为广告重构规则、计算、公告、数据集或重置机制。

- 前端：增加共用广告位组件和薄的配置读取层；预测、单股各接一个位置。广告事件只处理自己的布局和状态，不修改业务风险状态、缓存日期或刷新标记。
- 后端：增加公开、只读、轻量的 `/api/client-config`，返回配置版本、广告总开关、允许的小程序版本和两个广告位配置；不返回用户标识或密钥，不接受客户端写入。版本筛选只用于展示控制，不作为权限或安全判断。
- 配置存储：首版随服务配置管理，不新增业务表；广告位ID属于客户端展示标识，不是签名密钥。无需为广告新增Redis键、MySQL表、用户体系、锁或队列。
- 配置读取：本地默认关闭；启动异步获取，不阻塞业务。成功配置最多缓存10分钟；过期后更新，失败则新的广告挂载保持关闭，不无限沿用旧的开启状态。缓存或配置版本变化不立即强制重建当前广告。
- 运营关闭：优先使用微信流量主后台关闭广告单元；应用开关作为补充，客户端收到新配置后停止新的展示。已有组件及离线缓存不会保证即时消失，不能把10分钟缓存写成严格的全用户下线时限。
- 发布隔离：配置初始关闭，仅对新广告版本启用；老包无组件不受新增接口影响。整个广告配置接口不可用时，业务API及页面仍正常。

首版收入、广告请求与展示等效果指标优先使用微信流量主后台，不引入自建用户级追踪。`bind:load`仅记为加载成功，不能冒充有效曝光、点击或收入，不从组件触摸事件自建点击统计。

## 5. 开通、隐私与收益判断

开发前在小程序公众平台检查流量主入口和实际开通资格，确认当前个人主体、类目、访问量及账号状态能否开通；取得广告单元ID后才能进行真实投放验证。本方案未读取账号资格，不将网上历史的固定用户数门槛当作当前结论。备案仍在进行，按平台实际要求推进，不承诺备案中即可开通。

广告版本需要重新核对并更新小程序内隐私说明、公众平台用户隐私保护指引、审核备注和结算/税务资料。清楚说明接入微信官方广告以及平台侧的数据处理，以实际组件和后台要求填写；不能沿用“完全没有第三方数据处理”的概括，也不能虚填定位、手机号等未使用的权限。不因为增加广告而更改实际股票工具的服务内容描述或规避类目审核。

收入不作保证。粗估公式：日收入≈实际有效曝光量×实际eCPM÷1000；再与云托管、数据库等实际日成本比较。这里只能用投放后的平台有效曝光与结算口径估算，不能将页面打开次数或load事件等同收入。

建议上线后观察7–14天的收入、填充、错误、页面响应和用户反馈，再决定保留两个位置还是只保留一个。若收入很低，不增加打断用户的广告来补足预设收益。

## 6. 开发与验收安排

1. 产品确认本方案的形态、位置、免费功能边界和候选版本号；平台侧确认开通条件与广告单元可用。当前1.0.21继续审核，不混入广告改动。
2. 先完成广告版PRD补充、接口/配置契约、页面示意和测试用例；以现有正式代码为基线开发，开关默认关闭。
3. 联调：无ID、不支持、无填充、网络失败、广告位审核/关闭时，三个业务页面的查询、S1/S2、日期切换和PDF均正常。
4. 真机：iOS/Android分别检查广告加载与返回、快速切标签、反复进入单股、键盘/模拟输入、长列表/短列表/空列表、广告不遮挡按钮及无额外自动行情请求。广告点击/收入以平台规则验证，不自行反复点击制造数据。
5. 回归：股票卡数量/顺序/颜色、IPO边界、四项预警、模拟初态/清空、监管期限、公告阅读均保持原结果；广告关闭时页面正常。完整投放样本和手机结果分别记录，不用自动化通过代替。
6. 新版上传提审，备注真实说明新增微信官方广告；通过后发布，先开预测单个位置，观察稳定后再启用单股位置。开关及配置传播按上节实际边界验收。

当前只交付方案，不开启广告、不新建广告单元、不改生产环境参数、不部署或上传新包。
