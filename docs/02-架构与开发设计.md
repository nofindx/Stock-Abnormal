# 异动查查 · 架构与开发设计

> 文档版本 `2.0.5` · 文档修订 `20261125.1` · 发布标识 `20261125.1` · 计算版本 `v76`。

> 本套对应 2.0.5 本地候选，包含 2.0.4 全部修正；最近核验云端为 2.0.4，微信公众版为 2.0.3。部署、上传及真机进度见[正式上线清单](05-正式上线清单.md)。

## 1. 设计目标与分层

### 1.1 产品范围

系统提供单股计算、重点监控、异动预测三项能力。单股计算和异动预测共用同一套行情规则；重点监控只处理公告事实。系统范围以 PRD §1 为准。

| 职责 | 当前代码 | 上下游 |
| --- | --- | --- |
| 规则与纯计算 | `server/rules/`、`server/calculations/` | 接收规则/有效收益/事实边界，输出四项结果，不抓公告或写页面状态 |
| 公告及重置 | `monitor_service.py`、`server/resets/` | 采集、解析、确认事实与生效日；仓储保存修订，计算消费重置上下文 |
| 数据与发布 | `server/data/`、`market_calc_repository.py` | 保存基础向量、事实、发布指针、授权视图及任务，供业务服务读取 |
| 业务服务 | `MarketService`、`read_publications.py`、`context_service.py` | 编排数据、统一计算、筛选、授权及 S1/S2；接口供小程序消费 |
| 前端 | `miniprogram/` | 展示统一结果，处理缓存、模拟、广告、分享及保存 |

表为职责/依赖关系，不代表执行时序；运行顺序见 §2。未实现的历史架构方案不作为当前生产能力。

### 1.2 当前实现边界

`MarketService`仅对股票已存首末日期之间的缺日核验`suspend_d`，不把指数较早起点当停牌；最近缺口的前日取紧邻的股票交易日。真实内部缺口核验失败仍不可用，不隐藏源数据缺失。初始化及新增股票按每条日线自身`pct_chg/pre_close`生成收益，首条有效行也保留，末30条落库。停牌日不补零，公告事实和普通/严重重置范围不变。行情不足原因与公告覆盖原因分别表达；全市场覆盖审计与单股当前计算可用性不等同。

本节记录实际代码边界。架构研究和专家评审可从 [历史资料索引](../archive/README.md) 查阅。

四项规则固定为 3 日偏离（普通/黄色）、10 日同向、10 日偏离、30 日偏离（严重/红色）。当前规则定义位于 `server/rules/catalog.py`，通用价格序列算法及公告事件账本位于 `server/calculations/engine.py`；生产收益向量的 `_vector_metrics`、边界反解及预测编排仍在 `MarketService`，公告采集/解析仍由 `OfficialMonitorService` 承担，事实账本、重置判定和状态组装分布在相应数据/重置模块。单股、预测、监控的摘要优先级只能影响文案，不能短路任何一项规则。

10 日同向计次及普通、严重公告的重置范围按 PRD §2.2 执行。

### 1.3 运行与版本边界

规则或公告事实版本变化时，服务使用已保存的确认行情重算受影响的派生数据。发布核对同时检查后端版本、目标交易日、数据阶段、质量及任务错误。证据见[正式上线清单](05-正式上线清单.md)。

前端使用 `miniprogram/utils/business-boundary.js` 统一上海日期和阶段键。可见页面只为下一个边界设置一次定时器，触发后重新安排；隐藏/卸载清理。单股/预测边界为00:00、09:00、09:15、15:00，监控仅午夜。每页保存最近已读阶段，`onShow`与定时器共用一次失效检查，防止重复S1。失效时清除旧结果、递增请求序号并重读S1，旧S1/S2响应按序号丢弃；单股同时清除旧模拟结果。初次S1跨阶段晚返回不能再自动S2。后端`nextDayAvailable=false`且当前为next_day时，先切today再读取一次；today不会递归切换。其余阶段/休市日开放由后端控制，不在前端复制日历判断。该机制不周期请求S2；后台新数据发布后的即时推送不在本次范围。详见PRD §1.4。

单股监管展示按上海当前日期筛选有效事实：开始日不晚于当前日且结束日不早于当前日，过期事实退出；已确认但尚未开始的严重异动单独显示“将进入重点监控”，不作为当前有效监管；详情 `tradeDate` 仅表示行情/计算基线日期，不用于监管有效性或倒计时。详情、缓存和导出共用同一渲染结果。质量影响按 PRD §2.2：当前渲染使用 `stockState.marketDataState` 与 `dataQuality.isComplete` 判断行情是否整体可用；不能把仅由公告覆盖不足造成的聚合 `dataAvailable=false` 写成四项卡全部失效。

## 2. 业务流程

### 2.1 服务启动与基础资料同步

1. 加载规则版本、数据库和数据源配置。
2. 同步交易日历、股票基础资料和股票到所属指数的映射。
3. 同步 `stock_basic(list_status=L)`，更新板块、ST、上市日期、退市整理和价格限制字段。
4. 同步失败不阻塞服务启动，但必须进入 `/health`；基础资料不完整时不得发布 ready 预测集。
5. 启动预测、行情基础数据和公告采集任务。重任务互斥使用 §6.1 的进程单槽与 MySQL 命名锁；S2 共享任务另使用数据库 owner/lease，不能混为一种锁。

### 2.2 统一行情计算

输入为股票日线、所属指数日线、板块规则、行情时间和质量元数据。

1. 按 `trade_date` 取股票和指数交集并升序排列。
2. 不补自然日、不补 0。日线按共同日期配对。实时统一使用 `server/services/realtime/validation.py`：完整可解析的年月日时分秒归一到上海时区，两方来源名必须存在且相同，同报价交易日、绝对时间差 ≤60 秒；日期文本和解析失败没有宽松分支。报价正数且有限，不得来自未来或早于本次读取基准；午休、盘后和休市不因自然时间变老而丢弃最新真实报价。单股、固定池刷新、盘后初态及兼容路径均复用。配对失败保留稳定计算，股票单边成功仍更新价格。
3. 基准指数固定映射：沪市主板 `000002.SH`（上证 A 股指数）、深市主板 `399107.SZ`（深证 A 股指数）、创业板 `399102.SZ`、科创板 `000688.SH`、北交所 `899050.BJ`。API 展示名称按指数代码规范化，避免深市主板分类指数被误称为深证成指。
4. 对 3、10、30 日窗口分别取最近最多 3、10、30 个共同收益区间；仅枚举以最新共同交易日为终点的连续有效子区间，单股同时保留最大上涨偏离和最小下跌偏离。预测只筛选上涨方向。无论当日还是次日，N 日预测边界的股票侧均只纳入目标日前最多 N-1 个已知收益，指数侧与股票侧对应同一目标日结束窗口（当日保留目标日已知指数收益，次日未知指数收益假设为 0）；不可把完整 N 日已知窗口再追加目标日变成 N+1 日。触发条件是在目标窗口反推的最小目标日涨跌幅（相对该日前收盘，允许负值，不截为 0%；不是从当前报价起的额外上涨距离）。生成和刷新通过 `_prediction_trigger_fields` 统一输出带符号的 `triggerValue` 及一致的 `triggerCondition/trigger`；仅格式化时归一化负零，真实判定继续使用未舍入数值。下跌方向反解取最大边界，也不截断符号。反解公式：

```text
S = Π(1 + stockDailyReturn[i] / 100)
I = Π(1 + indexDailyReturn[i] / 100)
deviation = (S - I) × 100  # 百分数值
requiredTargetReturn = ((I + threshold / 100) / S_prior - 1) × 100
# S_prior 不含待求目标日股票收益；I 按当日已知/次日0%取目标日指数收益
```

5. 计算依据 PRD §2.2 读取普通与严重公告事实、同向计次以及 `effective_date`。按证据 ID 去重，区分已确认事件、行情候选与待核验事实。事实覆盖不足时保留原因，未知的准确次数用空值表达。
6. 单股返回双向阈值、实际窗口、收益、偏离、方向、触发和质量。四项独立返回，缺失项表达“不可判定”。预测按 PRD §2.3 筛选上涨候选。

统一规则实现必须被单股详情、全市场预测和盘中刷新共同调用，不得在页面或任务中复制阈值和窗口逻辑。

### 2.3 单股计算与前端模拟

1. 前端搜索股票并请求详情。
2. S1 读取已保存的计算基线及固定事实；S2 在所有时段获取最新报价，配对规则按 §2.2，不以交易时段限制取价。
3. 后端返回交易状态、当前有效 `monitoring`、四项 `warnings`、`nextDayForecast`、`dataQuality` 和模拟输入。当前数值选择、公告质量及行情质量对页面的影响统一按 PRD §2.2；顶部摘要/监管背景按 PRD §3.1。`buildNextDayForecast`、`presentWarnings`、`resolveStatusBanner` 分别负责这三种展示，不能用其中一类结论覆盖其他数据。
4. 前端直接展示正式结果，不用 `calculationInput` 重算状态。
5. 前端以 `simulationBase`、`futureTradeDates`、`simulationThresholds` 计算 T+N；修改某日后只重算该日及后续行，不发网络请求。

### 2.4 重点监控

1. 后台分别抓取 18.cn、中泰证券业务公告，以及巨潮资讯按交易所栏目和异动关键词检索的公告；中泰栏目 ID 为 `3465`。巨潮在日切任务中按已完成交易日回查并重试延迟披露。查询范围依公告扫描策略配置。
2. 各公告源独立采集；公告元数据保存来源 ID/链接、披露时间、标题、股票、正文哈希及确认状态，正文在采集时下载解析，不承诺永久保存完整原始正文/PDF。生产 `publication_fact` 按来源 ID + 内容哈希保存事实修订，重算从最新确认修订恢复事实；`publication_record/state/outbox` 原子保存快照、活动指针及待重算消息。相同公告重复采集不重复计次，所有源失败保留上一份成功快照。历史事实保存与用户只查询当前监控是两种边界。
3. 分类基于正文：风险提示需要“从严认定”；严重异动通过 `_recognize_monitor_text` 同时生成兼容分类、`recognitionBasis[]` 和 `ruleText`，分类函数仅从此结果取标签，避免“识别”和“原因”各实现一次。依据记录 `kind/ruleKey/windowDays/direction`，价格类另有 `deviation/threshold`，计次类另有 `count/threshold`，以及归一化正文片段 `evidenceText` 和可展示 `text`。缺依据不由当前四项结果倒推。
   - 价格类保留实际数值，按实际≤10日或≤30日窗口和相应板块阈值分类，短实际窗口需有严重认定语义；独立的多项依据不互相覆盖。
   - 同向类需公告明确严重认定及板块同向次数条件，显示名称为“同向严重异动”。`riskTone=severe-10d` 继续作为旧系统的监管族编码以兼容现有筛选/周期/重置，不再被解释成价格100%。≤10日对应 `same_direction_10d`；正式严重公告中更长的实际窗口用 `announcement_same_direction` 留存，不改产品计算器的10日窗口，不增加第五项预警。
   - 发行人、18.cn解析时携带依据；同日主备合并优先保留发行人/交易所依据。依据通过现有事实JSON、`resetEvidence` 和监控快照保存，无新表。公告解析版本升为 `20261124-product-policy-v35`，后续部署按现有后台调度重采当前窗口并重建派生；页面请求不启动采集。旧记录来不及补齐时详情使用中性兜底。

4. 普通 3 日偏离公告只作为规则事件及重置证据，不单独生成严重监管记录；严重异动公告（包括 10 日同向达阈值、10 日偏离、30 日偏离）进入重点监控。监管风险提示和退市整理另按公告类型记录。严重公告正文写“自某日以来连续 N 个交易日”但无显式截止日时，以公告日收盘作为事实截止点，监管期按已定产品周期计算；退市整理单独显示“退市倒计时”，周期取正文确认的进入日与预计最后交易日。
5. 同股同类型重叠记录由最新公告覆盖，同日同类型多来源合并，随后原子发布快照。

### 2.5 盘后预测与阶段切换

1. 15:00 后先获取可用收盘初态，完整时写入 `initial/provisional`；Tushare 正式收盘就绪后更新为 `formal/confirmed`，不能假定 15:00 已有正式数据。初态和正式分别按以下流程发布。
2. 按目标日校验 ST、IPO 适用性、退市整理、价格限制、停牌尾部和数据完整性。
3. 统一计算后按规则独立筛选 `same_direction_10d`、`severe_10d`、`severe_30d` 及满足监管资格的 `ordinary_3d`。
4. 次日按完整活跃池逐规则筛选，已触发的 10 日偏离和已达阈值的 10 日同向不再生成次日同规则卡，30 日偏离独立保留。其余可达性和普通卡资格按 PRD §2.3；独立普通风险提示不排除严重监管期内的 3 日候选。
5. 按 PRD §2.2 的 `effective_date` 重置后重算；窗口/摘要优先级不能整体排除股票或抑制其他独立规则。
6. 以 `{ts_code}-{ruleKey}-{targetTradeDate}` 生成稳定主键并原子写入。

阶段边界：`09:00` 前保留上一交易日结果；`09:00` 当前目标日的 `next_day` 候选集成为 today，`09:15` 进入盘中阶段，`15:00` 进入盘后阶段。盘中刷新只更新已有卡片状态，不新增或删除候选，保证同一交易日卡片身份稳定。盘后归档 today 时沿用此前以目标日前一交易日为基准生成的 `next_day` 候选身份（股票 + 规则），但价格、涨幅、实际偏离窗口、偏离值、触发状态和触发距离必须以每张候选股票及其所属指数的目标日落盘向量重新计算；盘后发布只保留已触发卡和目标日涨幅边界不超过板块单日上限的未触发卡，不得重新扫描全市场并改变候选名单。缺少完整前序候选集、任一候选股票/指数目标日基线时标记数据不可用，禁止用前一日字段回退展示。非候选股票停牌或缺行情不应清空有效候选集，但必须由历史覆盖接口和健康检查明确报告。

阶段输出包含 `phase`、`targetTradeDate`、`todaySourceScope` 和 `realtimeRefreshAllowed`。阶段值包括 `pre_open / dataset_open_pending / intraday / post_close_pending / post_close_confirmed / rest_day`，逐请求按上海时间及日历判定，不缓存跨边界结论。实时取价允许性取决于来源/Redis就绪，与市场阶段分别判断。09:00 至盘后新的下一目标日数据发布前，次日页不可用；休市日及下一交易日 09:00 前仍可读匹配目标日的次日集。空候选只有在输入完整且计算成功时才是有效空集。正式数据就绪后，today 使用同一候选身份及正式基线重算，next_day 按完整活跃池重算。

### 2.6 失败恢复

| 场景 | 处理 | 对外状态 |
| --- | --- | --- |
| 股票/指数一方缺失 | 使用稳定结果 | `fallback=true` |
| 正式任务失败 | 保留旧数据集 | `dataUnavailable=true`、`datasetStatus=failed` |
| 无历史成功集 | 不发布空成功 | 数据不可用 |
| 公告源全部失败 | 保留旧快照 | `stale=true` |
| 实时请求失败 | 保留稳定结果，返回回退或错误状态 | 不覆盖正式数据集 |
| 规则版本变化 | 重建数据集和缓存 | 新旧版本不混用 |

## 3. 接口设计总表

本章列出现行接口与字段。小程序单股/预测主链路使用 v2 上下文、授权读取及刷新；无 v2 前缀的详情、预测与刷新为兼容/运维入口，不能据其示例绕过读授权。重点监控、搜索、广告配置仍使用各自现行路径。

### 3.1 通用响应与字段

成功：

```json
{"code":0,"data":{},"message":"ok"}
```

失败：

```json
{"code":40001,"data":null,"message":"参数错误"}
```

日期比较先归一化为 `YYYYMMDD`。内部对象和存储可能保留 `YYYY-MM-DD`，但 `server/app.py::_json_bytes` 会在 HTTP JSON 序列化时递归将纯日期字符串转为 `YYYYMMDD`，包括 `targetTradeDate/baseTradeDate`、`monitorStartDate/monitorEndDate/monitorDates` 和 `futureTradeDates`。客户端仍兼容两种输入，不按混合格式直接排序。来源时间可为 ISO 8601 或上海时间 `YYYY-MM-DD HH:mm:ss`，不会被上述纯日期转换改写，不得一概要求带时区。百分比使用百分数数值，`100.0` 表示 `+100.00%`。`quoteUpdatedAt` 是行情事实时间，`updatedAt` 仅为技术兼容字段。

### 3.3 计算数据覆盖审计

`GET /api/market/history-coverage?offset=0&limit=100` 只读取 `stock_basic`、`stock_calc_base` 和 `index_calc_base`，不请求或保存日线、实时快照；另用 Tushare `suspend_d` 只读核对停牌日期，不持久化停复牌明细。以指数日期并集的最近日期为参照，要求每只活跃股票有 30 个共同收益点（对应 31 个交易日价格）；返回完整/不完整数量、分类计数和分页异常列表。分类包含缺股票向量、缺指数向量、新上市历史不足、指数历史不足、股票/指数基准错位、停牌造成的历史不足、已确认上游行情缺记录及停牌状态源不可用时的未分类缺口。

收益向量缺日期只能证明该日期无股票收益记录，不能单独区分停牌和上游漏数；该接口必须标为待确认，不可自行归因。`offset` 必须不小于 0，`limit` 范围 1～500；数据库不可用或读取失败返回 `50302`，参数错误返回 `40001`。

`GET /api/market/calculation-bases?ts_codes=600123.SH,000001.SZ&limit=100` 直接读取 `stock_basic`、`stock_calc_base` 和所需的 `index_calc_base`。返回股票基础资料、最新收盘基准和完整收益向量；3/10/30 日偏离、10 日同向次数及事件明细在请求时用该落盘向量和最新已确认规则重置事实，调用统一计算层重算，避免返回“新重置日期+旧聚合结果”。接口不请求 Tushare 日线、不读取或保存盘中快照。未传 `ts_codes` 时按活跃股票分页，单次最多 100 只，并返回 `containsRawDaily=false`、`containsIntradaySnapshot=false`。

`GET /api/market/dataset-status` 只返回 `prediction_dataset` 的角色、目标日期、基准日期、数据阶段、完整性、条数、排除统计、规则版本和错误状态，不展开预测卡片。预测卡片仍由 `/api/predictions?scope=today|next_day` 读取。

`GET /api/market/jobs` 只返回 `market_calc_job` 和 `prediction_job` 的任务尝试、成功日期、阶段、状态、重试标记和错误信息，用于发布验收；不触发任务、不修改数据库。

### 3.5 单股详情

`GET /api/stocks/detail?ts_code=000001.SZ`

`data` 至少包含：

```text

currentPrice, change, tradeDate, quoteUpdatedAt
marketStatus, marketStatusClass, statusReason, monitoring
monitoringStatus, monitoringStatusDisplay
status, statusDisplay, statusClass, statusIcon, warnings[4], alerts[], dataQuality
futureTradeDates, simulationBase, simulationThresholds, calculationInput
```

`warnings` 固定顺序为 3 日偏离、10 日同向、10 日偏离、30 日偏离，与单股详情四宫格布局一致。偏离项同时返回上涨最大偏离、下跌最小偏离、两侧阈值和触发状态；同向项区分上涨和下跌次数，并提供 `upEvents` / `downEvents` 明细。当前公告确认事件的 `startDate` / `endDate`（`YYYYMMDD`）均为事实日期，含 `sourceId`、`windowDays=3`、`direction`；其 `deviation` 可以为空，因为次数来自公告确认事实。行情计算候选另行作为证据，不进入公告确认事件数组。事件明细数量必须与对应方向次数相等，按公告事件日期裁剪滚动 10 日范围。正式详情只读本地 MySQL 计算基线；数据库不可用、股票或指数基线缺失、任一侧向量与自身基准日期不一致，或双方均有向量但没有共同日期时返回 `50302`，不得转去 Tushare 日线拼另一套正式结果。股票停牌、刚上市或上游缺记录造成两侧基准日期不同但仍有共同日期时，按共同日期对齐并返回已有有效窗口；刚上市首个交易日一侧合法为空时也返回详情，前三项显示暂无有效窗口。`dataQuality.commonDays` 标记覆盖范围；`calculationInput` 是前端模拟基础输入，模拟值变化仅在小程序本地计算，不重复请求后端。

模拟输入字段片段（省略了实际调用必需的完整日期/分窗向量及重置元数据；完整契约见 §5.3，不作为可直接提交的请求）：

```json
{
  "futureTradeDates":["20261013","20261014"],
  "simulationBase":{"stock":[0.5,-1.2],"index":[0.2,-0.4]},
  "simulationThresholds":{"3":{"up":20.0,"down":-20.0},"10":{"up":100.0,"down":-50.0},"30":{"up":200.0,"down":-70.0}},
  "calculationInput":{"stock":[],"index":[],"ordinaryDeviation":20.0,"severe10":{"up":100.0},"severe30":{"up":200.0},"sameDirectionThreshold":4,"ruleVersion":"..."},
  "dataQuality":{"commonDays":30,"requiredCommonDays":30,"ruleResetDate":""}
}
```

股票不存在返回 `40401`；实时行情不完整仍可返回稳定结果，但必须在 `dataQuality` 标记 fallback。

`simulationThresholds.3` 及各 `down` 字段为兼容旧客户端保留的完整规则字段；当前模拟表只消费 `simulationThresholds.10.up` 和 `simulationThresholds.30.up`，不读取下跌阈值。后端暂不删除兼容字段，避免接口版本分叉；顶部正式预警仍使用完整双向规则。

### 3.6 重点监控

`GET /api/monitor?status=current&type=all`

每项至少包含：`monitorKey`、股票代码和名称、标题、`riskTone`、`monitorType`、`eventDirection`、`monitorStartDate`、`monitorEndDate`、`monitorDates`、`days`、`daysTotal`、`monitorPeriod`、`sourceStatus`、`sourceUrl`/`sourceUrls`、`sourceRelation`、数据质量。`eventDirection` 是依据严重异动公告正文“涨幅/跌幅偏离”提取的本轮事实方向（`up`/`down`/空）；不得用最新单日行情代替。`sourceRelation` 可为 `severe-primary`、`ordinary-independent`、`severe-supporting` 或 `delisting-independent`；佐证来源使用 `supportingFacts`/`supportingSourceUrls` 返回，不得混入主来源列表。所有 `type` 均返回对应分类下的全部有效监管事实，包括页面会去杂隐藏的股票；可附最新落盘股票日收益 `marketChange` 和日期 `marketChangeDate` 供行情参考，但不得作为严重异动方向过滤字段。上涨型严重异动即使最新单日收益为负仍展示；明确为下跌型的严重异动仅在前端隐藏。风险提示不受涨跌影响，也不请求实时源。去杂只在小程序展示层执行。返回 `items`、`updatedAt`、`stale`、`dataQuality`、`sourceHealth`。

退市整理使用 `riskTone=delisting-warning`。按 PRD §2.4 检查 PDF 资格和可信 HTTPS 来源，公开响应提供 `pdfAvailable` 和签名代理地址。公开监控结果只保留展示所需字段，内部重置事实和核验明细见 §6.1。全部公告源失败时保留上一份快照并返回失败信息。

PDF 沿用服务本地文件缓存，缺失时按可信原件回源。过期记录停止阅读并清理缓存，保留事实元数据。签名有效期 5 分钟，前端续址见 §5.2。

### 3.14 S1/S2 读取与实时视图

S1 对应上下文绑定的已发布范围。上下文绑定页面、角色、证券或候选池、数据版本、规则版本及时间上下文。单股 token 不能用于另一股票，当日 token 不能用于次日。有效期取签发后 300 秒、业务切换时刻和视图有效边界中的最早值。

`ReadPublications.capture` 固定本次行情基线和公告事实；同一个 S2 内仍只使用其授权范围。2.0.5 对单股/预测的 `GET /api/v2/context` 传 `include_s1=1`，同一响应内附带 `s1`，内容等价于使用返回 token 的授权 GET，不包含内部 basis。先渲染该 S1，再 POST S2，首开及手动刷新通常从三个请求减为两个；后台没有 `s1` 字段时兼容原授权 GET。客户端核对 token、dataset、pool、规则和时间上下文，单股还核对证券；出现不一致直接失败，不请求 S2。同一 entry 重试必须返回该 entry 已固定的旧 S1，不能给旧 token 配新内容；一次新的手动操作使用新 entry，立即读取最新已发布内容。`include_s1` 是传输选项，不改变 scope 指纹，其他页面不通过该选项取得内部事实。

客户端 `refreshStockDetail/refreshPredictions` 默认表示手动刷新：先获取新 context 及最新 S1，再 POST S2。首次打开通过 `{reuseContext:true}` 复用刚显示的 S1。手动S1成功后通过 `onS1` 先更新已发布名单/事实/基线，S2完成前仍保持刷新中，不将S1当作本次实时取价成功。新 S1 成功且 S2 异常时返回新 S1 加 `failed/stale` 与原因；S1 失败直接报错、不拿旧 token 冒充最新读取。关闭的次日或不可刷新的证券按新 S1 返回，不再发 S2。旧 context、授权 GET 和 S2 接口保留兼容；所有 `/api/v2/` 响应 `Cache-Control: no-store`。

重新取 S1 只读取后台已发布内容，不抓公告、不扫名单外股票。手动读取可以切换到后台最新公布的名单；随后的 S2 只刷新新名单中已有证券和规则。切标签、同阶段返回、周期边界原有缓存策略不变。每个 S2 的新视图 token 不延长该 S1 的300秒授权，40902仍最多重取一次上下文后重试；晚到的旧证券/阶段结果照常丢弃。

单股 S1 返回 `calculationBasisId`：对 `simulationBase`、阈值、适用性及未来日期的规范JSON计算哈希，不含实时价格和 token。S2保持该值。前端模拟基准键包含它，保证同日有效重置改变基线时也能复位；基线未变的报价刷新则保留输入及展开态。

S2 使用同一上下文对所选证券或已发布名单请求最新报价。S1/S2 不可变读取视图保存在 MySQL `publication_record`（kind=`read`），默认保留 600 秒；短期结果携带视图标识，用原授权范围读取。视图身份包含授权 scope 和内容摘要，相同范围与内容可复用。`entry_id` 幂等记录也在该表，默认保留 86400 秒；不得与 token 300 秒或报价 3 秒 TTL 混用。过期短期记录按现有清理任务保留 300 秒清理宽限，但宽限不延长授权。共享任务未完成时返回 202、`queued/stale`、`job_id`、`retry_after_ms` 和原因，随后查询任务。最终结果复用 S2 响应字段。客户端轮询最多 24 次，间隔限制在 250～1000 毫秒。失败或仍在排队时保留稳定读结果并提示。遇到 `40902` 重新获取一次上下文后重试，跨页面或业务阶段的迟到结果丢弃。

### 3.15 广告配置与次日就绪

两接口返回 `Cache-Control: no-store`。配置接口独立于业务存储和行情读授权。

#### GET /api/client-config

成功：HTTP 200，`{code:0,data:<下方公开配置>,message:"ok"}`。配置不存在时返回内置关闭/free配置；格式无效时HTTP 503、code=50305、data=null，消息为“广告配置暂不可用”，不回显环境变量原文。此接口不要求行情授权上下文。

配置入口`CLIENT_ADS_CONFIG_JSON`为整个公开配置JSON。结构包括 4 个 `placements`、2 个 `rewarded` 和 2 个 `featureGates`。服务拒绝多余字段、错误类型、非法版本和 ID，以及彼此冲突的开关。当前默认版本白名单为`["2.0.0", "2.0.1", "2.0.2", "2.0.3", "2.0.4", "2.0.5"]`，包含最新版本并兼容旧版本。TTL固定600秒。单元 ID 使用 `adunit-` 加 1～64 位字母数字，未启用单元可以留空。`rewarded` 模式需要总开关和对应视频单元均开启。恢复免费按[生产操作手册](04-生产操作手册.md#7-广告启停)执行。

默认关闭路径不需要配置此变量。本地自动化使用注入配置与模拟平台，不使用真实广告ID、不修改云端环境变量。

配置缺省时的完整响应如下。

```json
{
```

### 4.3 IPO适用性实现

权威产品定义见PRD §2.0。`server/rules/listing.py`存放各板块IPO无涨跌幅交易日数量及纯适用性函数；`MarketService`用已存在的Tushare交易日历解析首个有效交易日，按上市日/板块缓存成功的日历结果，失败不缓存。老股票且向量已不含IPO期间时无需额外请求日历；长停牌后向量仍残留IPO历史时仍要裁剪，不能仅按上市时间久远放行。

后端在`_rule_vectors_for_stock`入口对股票和指数同时裁剪，之后才执行既有停复牌、公告重置及指标计算。实时收益追加后再次应用同一边界，避免实时刷新带回不适用日。IPO适用边界不是公告reset，不能加入`priceResetDates`或将首个有效日收益强制归零。无数据库结构迁移，原始收益向量不改；2.0.4 的派生版本为 v76，严格报价校验的变更按既有版本逻辑重建派生预测；板块阈值和 IPO 规则目录不变，原始行情不重抓、不清库。

详情返回`ruleApplicability`、`simulationApplicability`，以及`nextDayForecast.ruleApplicability`。包含`applicable`（true/false/null）、`reason`、`message`、`effectiveFrom`、新股期间长度与目标日；null表示元数据/日历不足，不推定为true。IPO期间四项warning的`availability=not_applicable`且无触发/计次数值；单股`priceLimitEnabled`按实际计算日覆盖基础属性。`stockState`分别保留适用性和公告监管状态，不以计算不适用清除事实。

预测生成、持久名单读取、既有名单实时刷新均按目标日应用同一规则，旧名单不能绕过；仍只刷新已发布名单。单股当日与下一交易日分开判断，第5日到第6日允许空有效基线的次日判断。前端四项卡片与模拟结果显示“暂不适用”；无数据故障时不混入“待核验”。公告模块、PDF阅读和重点监控采集筛选不增加IPO排除条件。

## 5. 前后端实现分工

### 5.1 后端

后端负责数据源、统一规则、资格过滤、预测生成、公告分类、监管期、数据集、失败回退、API 和健康检查。通用纯函数位于 `server/calculations/engine.py`，生产收益向量入口仍是 `MarketService._vector_metrics`；单股/预测/实时均复用该入口及其边界函数。不能把当前架构写成已经完成所有计算拆分。`server/core/abnormal_rules.py` 是兼容导入门面。

交易状态由 `server/data/trading_state.py` 判定，`build_stock_state` 只合并四个独立维度。详情读取证券基础资料、计算基准及 Tushare 停复牌证据：正常证券需有近期实际交易或明确复牌依据；S/R 按证券和日期筛选，临停按来源给出的时段判断，全天停牌当天盘后仍显示停牌。查询正常共用最近 7 自然日的停复牌响应，进程缓存 60 秒；长期滞后证券最多按代码补查最近 45 自然日，超出可核实范围为未知，不能仅凭行情尾部缺日断定停牌。该读取不进入预测全市场循环，不改变 PRD §2.2 的复牌重置逻辑。

活跃股票池中移除会留下 D 标记，因此仅凭该标记不直接宣布终止上市：需已确认且生效的 `delist_date`，缺少时按代码读取 `stock_basic(list_status=D)` 补核，成功结果缓存 6 小时；未确认则未知。状态源失败只影响该状态证据，不篡改已有行情计算。已知证券缺计算基线时返回四项不可用及状态，不再把证券卡整页隐藏；数据库不可用或证券不存在仍返回错误。

S1 将本股停复牌证据保存在 `stockState.tradingEvidence`，S2 使用同一份证据按当前上海时刻重判临停时段，不另抓事实；新公告/停复牌事件随下一次 S1 进入，沿用 §3.14 的授权边界。API 返回 `tradingState/tradingStateReason`，前端异常交易标签与监管列表同时显示；保存图读取同一 WXML。

### 5.2 前端

前端通过 `utils/api.js` 统一请求路径与授权。首开先读取 S1，再获取一次最新可用报价 S2，各时段均可取价。预测只刷新已发布名单。前端渲染后端预警和公告事实，并在本地计算用户填写的模拟。

| 页面 | 内存保留范围 | 复用条件 |
| --- | --- | --- |
| 异动预测 | 当日、次日各一份有效视图和各自 token | 同上海日期与阶段，次日仍开放且具有当前功能许可 |
| 重点监控 | 一份 all 列表 | 同上海日期，四个分类本地筛选 |
| 单股计算 | 最近使用的 8 只股票的详情、基线和各自 token | 同股、同上海日期与阶段。重新选股仍初始化 2 日模拟和激励会话 |

跨日或阶段清理相应缓存并重读 S1。手动刷新更新相应范围。页面销毁清理内存，空的有效结果可缓存，失败视图不能作为成功缓存。已展示数据保留原更新时间，token 到期后仅在后续请求时续取。监控签名地址自成功取得满 4 分钟后，在用户点开 PDF 时按公告身份读取新地址，续取失败时提示并结束本次操作。

开发者工具的 develop 默认走云服务 HTTPS，体验和正式包走 `callContainer`。只有明确联调本地后端时才设置 `LOCAL_DEVELOPMENT_ONLY=true` 并使用环回地址。运行版本引用 JS 模块，JSON 供发布对账。

### 5.3 T+N 模拟算法

1. 使用 `simulationBase` 作为历史收益序列，使用 `futureTradeDates` 生成未来行。
2. 用户修改一行后，将该行追加到历史序列，计算 10/30 日偏离：在各自最近最多 10/30 个收益率区间内，只枚举以当前模拟日为终点的连续子区间，各取最大偏离并保留实际区间长度。全为负值时仍取最大值，不选择下跌最小值；用户可以输入负涨幅。3 日偏离和 10 日同向不进入模拟表。
3. 模拟仅比较 `simulationThresholds.10.up` 和 `simulationThresholds.30.up`。“距最近阈值”是在该模拟日价格基础上，到最近上涨触发价格的额外涨幅百分比，不是偏离百分点差。对每个以该日为终点的有效区间，令股票累计价格因子为 `S=∏(1+r_stock/100)`、指数因子为 `I=∏(1+r_index/100)`、对应上涨阈值数值为 `U`，则所需额外涨幅 `x=((I+U/100)/S-1)×100`；等价于 `(U-该区间偏离值)/S`。指数按该行假设固定，股票最后一个价格再乘 `1+x/100`，不追加交易日。`additionalRiseToThreshold()` 枚举所有1至10日/1至30日有效区间，`nearestUpwardThreshold()` 取两类规则中最小剩余涨幅。不能只反算最大偏离区间。任一规则已触及显示“已触发”，否则两位小数和 `%`，微小正值显示 `<0.01%`；没有50%封顶，也不按单日涨停幅度截断。缺少任一已配置窗口数据时不假定另一个就是最近，返回 `--`；无有效上涨阈值/输入无效同样为 `--`。下跌阈值不参与模拟判断，顶部四项正式预警双向判断不变；本行反算值不写回输入、不参与后续行收益。
4. 只更新当前行及后续依赖行；输入框清空后保持空白展示，但该空值按 `0%` 参与当前行及后续行计算。
5. 不调用网络，不修改正式状态、预测结果或后端存储。
6. 后端 `simulationBase` 增加 `dates`、`datesByWindow` 和 `resetDatesByWindow`。按共同日期配对，历史数组只裁剪已生效重置，未来已确认重置保留为元数据。三日重置取普通/严重最新边界，10/30日仅取严重边界；兼容单值 `severeResetDate` 和可空数组。前端逐个模拟目标日应用该边界：生效日正式偏离固定为零，无该日可反算的触发边界，该窗口不参与最近剩余涨幅；若两类窗口均处生效日，显示 `--`。其后按正式 `_vector_metrics` 的相同基线计算和反算。日期严格升序，基线长度/收益和目标日校验失败返回 `--`；未知缺数不同于已知重置，不得静默忽略。
7. 模拟表列和单元格均以 `rowIndex` 作为WXML稳定列表标识，禁止对象使用 `wx:key="*this"`，避免编辑、展开或清空时重复key造成单元格复用错误。

### 5.4 官方广告实现

`server/client_config.py` 校验公开配置，`utils/ads-config.js` 提供位置资格及功能策略，`components/official-ad` 封装展示组件，`utils/rewarded-access.js` 管理页内许可。使用官方原生组件，独立于行情、公告和数据库。展示位置在页面前台、业务条件和配置允许时挂载，省略 `ad-intervals`。拦截点位于 10 日展开或次日标签切换前。广告许可用于界面功能，S1/S2 读授权仍按 §3.14。

#### 模拟入口

先检查详情及模拟适用性，再读取功能策略。`free` 直接展开。`rewarded` 先请用户确认，随后创建视频实例并监听关闭回调。收到有效的完整观看回调后展开，保留前两日输入。观看期间显示“解锁中…”，并合并重复点击。失败后可以主动重试。

有 `calculationBasisId` 时，用股票代码及该标识判断模拟基准：后端标识已包含发布时的模拟输入、阈值、适用性及未来日期；S1收盘日期和S2最新报价日期变化不额外认定为基准变化，避免手动中间态清空输入和10日展开。旧后台无标识时才以股票、数据交易日和首个未来交易日作为兼容基准。同基准的 S1/S2 更新只重算结果。换股、基准变更或显式初始化时恢复默认 2 日并清除许可。清空按当前布局恢复默认输入。

#### 次日入口

同阶段已有可用缓存且满足当前许可时直接恢复。`free` 可读取 S1。`rewarded` 先读次日就绪接口，确认目标日可用才请用户观看。完成后复查同一目标日仍可用，再读 S1。切回当日、页面销毁或时间边界改变使本次进行中的请求失效。初态升级为正式、同目标 token 续期和列表失败重试保留许可。目标日变化或阶段关闭时清除许可。

#### 配置与组件生命周期

各页面共用一次进行中的配置请求。成功缓存 600 秒，失败退避 60 秒，后续按用户操作或页面生命周期检查。首次失败使用内置免费配置。已确认的激励模式在配置失效时保留门槛，重新取得有效配置后才可开始新观看。确认弹窗关闭后复查策略。

首次挂载需满足页面前台、业务可见及配置允许。切标签和刷新只改变可见性。已挂载单元的 ID 变更时隐藏旧位，当前页面实例不重新挂载。配置关闭或组件销毁后忽略迟到的加载回调。视频导致的 `onHide/onShow` 保留会话。`show()` 失败最多重试一次 `load()` 和 `show()`。

## 6. 稳定性、安全、测试与发布

### 6.1 稳定性与低配实现

全市场计算由后台任务完成。正式数据集以 `dataset_role + target_trade_date` 为主键原子发布。业务失败保留上版并报告质量。服务端保管签名密钥，客户端只收到短期授权 token。现有 0.25 核 / 0.5 GB 规格通过以下措施限制开销。

- **监控响应**在公开副本剔除 `resetFacts` 和 `unresolvedFacts`。按股票去重批量附加最新日涨跌，保留同股多条事实卡、PDF 代理及质量字段。内部快照继续供重置和审计读取。
- **S1 读库**按授权范围去重。`MarketCalcRepository.read_inputs` 在一个连接内用两批 SQL 读取股票资料、收益向量和所需指数。空池直接返回。S1/S2 共用冻结输入，仅复制授权证券对应的公告事实。查询统一映射 ST 和价格限制字段。
- **报价协调**用 Redis `MGET` 读取同来源策略、同 3 秒时间桶的报价。缺失证券取得 10 秒租约后再次检查缓存，只回源仍缺失的证券。租约和写入使用 pipeline，分组键确保批量读与租约脚本适用 Redis Cluster 同槽要求。报价 TTL 为 3 秒，命中不续期，报价保留来源时间。冷缓存竞争、部分回源失败或 Redis 故障按 S2 语义返回排队或回退。
- **来源配置边界**：`SOURCE_POLICY_JSON/HASH` 继续验证启用来源身份、版本与原 JSON 内容哈希。`freshness_seconds/stale_seconds/max_quote_skew_seconds` 为已退休的历史兼容键，不进入运行契约；仍按原 JSON 验证哈希，现有云配置不需重填。新配置可省略这些键。运行配对上限只在 `realtime/validation.py` 定义为 60 秒，健康门禁 `quotePairing` 报告实际值及 `retiredTimingKeys`；不再保留第二套 5/30/300 秒判定。60 秒不是报价年龄，Redis 3 秒 TTL 不变。
- **主备源有效性**：腾讯→新浪→东方财富逐级处理剩余证券，先验价格/前收为有限正数、涨跌幅有限、来源与完整时间有效、非未来且日期不早于读取基准，再接收并缓存。某来源返回一条坏记录不能阻止其他证券或备源；东方财富逐证券异常隔离。只有有效报价进入 3 秒共享缓存，缓存命中也校验读取基准；所有源失败维持明确缺失，由 S2 保留确认值。单边来源不同不做共同重算。
- **后台互斥**用进程内单槽和跨实例 MySQL 命名锁 `stock-abnormal:background:heavy:v1`。专用连接非阻塞争锁，持锁覆盖完整任务。同一线程重入复用，失锁后停止写入。忙时保留调度尝试、待抓公告及待投递消息。启动同步和规则重建 60 秒后重试。成功同步的基础资料记录可由其他实例复用 600 秒。页面读请求、PDF 和 S2 各自独立。
- **并发上限**为公告正文每批 4 篇、2 工作线程。S2 为 2 工作线程、4 在途槽位，超额任务继续排队供后续认领。全市场历史日线逐日消费，并逐日释放 Tushare 当天的进程缓存。
- **存储分工**为 MySQL 存正式数据和公告事实，Redis 承载报价缓存及取价租约；MySQL `publication_record` 保存授权视图。S2 共享任务在 `publication_refresh_job` 按请求指纹和 3 秒桶合并，30 秒 owner 租约认领，完成时校验 owner 与有效期，防止被新owner接管的旧任务发布结果。不能把这条防旧写入链路描述成 Redis 视图 fencing。PDF 缓存为服务本地文件。

规格和扩容调整以高峰的实际指标为依据。运行观测方法见[测试规范与用例](03-测试规范与用例.md)。

### 6.3 2.0.5 读取性能

- context 默认仍兼容原响应；单股/预测显式 `include_s1=1` 时合并返回已授权 S1，按 §3.14 校验及恢复。不得省略 CODE-007 的手动最新读取，不把 S2 成功与 S1 新旧混淆。
- `PublicationStore` 每次读取监控先查 MySQL 活动发布指针，单个实例仅缓存该不可变快照的解析结果。命中指针才复用；指针改变立即读取新内容，查询失败不借旧缓存伪成功。单股按证券裁剪事实后再复制。缓存副本与调用方隔离，无新 TTL、Redis 键或数据库表。
- entry 幂等锁由全局锁改成 entry 哈希对应的 MySQL 命名锁，不同用户无需串行争同一把锁；同一 entry 的重试与 scope 冲突仍保持原判定。
- Tushare 缓存元数据锁内不执行网络读取或复制数据。缓存未命中时按 key 合并进行中的调用，同 key 共用结果/异常，不同 key 和已缓存结果独立。异常不缓存，成功 TTL 从读取完成起算；不改变各接口 TTL 或数据校验。
- `read_performance.py` 只按固定阶段累计 count/mean/last/max，覆盖 context capture/authorize/response、监控快照、预测集、基线读取、单股渲染、视图保存和 S2。通过 `/health.data.readPerformance` 读取本实例统计，无证券、令牌、查询参数或用户信息，不作为全实例 p95。
- 前端 `getApp().globalData.requestPerformance` 只在内存保留最近30次请求的路径模板、耗时、传输方式、HTTP状态和尝试数。任务ID替换为占位符，不保留查询、令牌、证券、输入或响应，不上传、不写本机存储。页面测试可据此区分网络等待与渲染。
- 本轮未改变腾讯→新浪→东方财富优先级、报价3秒缓存、60秒配对、S2线程数或容器规格；备源耗时与云端资源是否饱和仍按真实分段数据决定后续优化。不能将本地快速返回作为真机3秒验收已通过。
