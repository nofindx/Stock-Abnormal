# 异动查查目标架构设计（绿地方案）

> 架构版本：`ARCH-2026-10-24.4-review`
> 规则基线：`RULE-2026-10-24.1`（本架构不更改产品规则）
> 文档状态：供产品与技术评审；本稿不代表迁移或上线已完成。

## 1. 设计目标与结论

本设计从业务事实和一致性要求出发，不以现有代码目录、数据库或部署方式为前提。

系统的核心任务不是“抓公告后展示股票”，而是把四类不同性质的信息可靠地连接起来：

1. **观测数据**：股票、基准指数、交易日历、交易状态和公告原文。
2. **业务事实**：公告明确表达的普通异动、严重异动、风险提示、停牌、退市整理等事实。
3. **规则判断**：在指定规则版本、行情版本和重置上下文中，对四项规则作出的可复算判断。
4. **产品状态**：单股、重点监控、当日预测和次日预测所消费的同一版本结果。

推荐采用**模块化单体 + 独立任务进程**：一份后端代码库、明确领域边界；HTTP API 和后台 Worker 在微信云托管环境运行，可分服务/进程部署并共用模块与权威数据存储。保留现有微信云托管、CloudBase MySQL 和 Tushare Pro。当前业务不要求 Redis，目标架构不依赖 Redis；初期不拆微服务、不引入 Kafka 等重型流平台。MySQL承担事务、事实一致性和任务租约；单一受控 Worker 负责 Tushare 批量同步与并发控制。

事实与公告证据采用追加式账本，计算结果形成可重建的**已发布数据集版本**；不采用“所有写操作都是领域事件”的完整 Event Sourcing。外部行情和公告本身已有来源系统，保存来源证据、规范事实与重放版本即可满足审计/回放，完整事件溯源会增加事务和运维复杂度但不改善产品正确性。

目标部署单元：

```text
微信小程序
    │ HTTPS / versioned DTO
    ▼
微信云托管 `flask-9a5y`：API ───┐
微信云托管 Worker/定时任务 ─────┤ 同一后端代码与领域模块
                                ├── CloudBase MySQL（权威事实/结果/任务）
                                └── 对象存储（公告原文/附件）
                                      ▲
                       Tushare Pro ───┤ 行情/指数/基础资料/交易日历
                       公告来源 ──────┘ 公告正文与正式事实证据
```

## 2. 不可破坏的架构原则

### 2.1 观测、事实、判定、状态分开

- 来源返回什么，保留为来源观测；不等于已确认业务事实。
- 公告正文确认了什么，写为不可变、可追溯的公告事实；不等于计算结果。
- 计算结果由行情、规则版本和重置上下文确定；不等于交易所正式认定或已进入监管。
- 当前展示状态是以上事实按统一版本汇集的产品读结果；摘要不得覆盖底层事实。

因此同一股票可以同时处于“某项行情规则触发”“严重异动监管事实有效”“停牌”“行情不完整”。不能用一个互斥 `status` 丢失这些并存信息。

### 2.2 规则只定义一次，计算只实现一次

- 规则目录是板块阈值、方向、事件等级、窗口、重置范围和生效边界的版本化唯一来源。
- 计算引擎是纯逻辑：相同输入和版本必须得到相同结果。它不联网、不解析公告、不访问数据库。
- 单股、四项预警、当日预测、次日预测和模拟计算使用同一规则定义及计算实现；产品场景只能改变查询范围/目标日期，不能另造一套判定逻辑。

### 2.3 完整性优先于“看起来有答案”

- 缺数据、源失败、公告未解析、交易日历不确定都要成为显式质量状态。
- 未能计算不等于未触发；未找到公告不等于没有公告；任何失败都不能静默变成“安全”或 `0`。
- 每个判断可追溯到行情版本、指数、交易日、规则版本、重置记录和原始证据。

### 2.4 全页面读同一份已发布版本

单股详情、监控、当日预测和次日预测使用相同 `dataset_version_id/build_id`、规则版本和数据水位。盘中临时行情必须标记为非持久化覆盖值及其行情时间，不与盘后正式数据混成无来源的“当前值”。

## 3. 模块地图与上下游

```text
外部行情源 ─> 行情接入与标准化 ───────────────┐
交易日历 / 证券主数据 ─> 基础资料模块 ─────────┤
外部公告源 ─> 公告连接器 ─> 原文归档 ─> 事实解析/核验 ─┤
                                                ▼
                                DATA：权威实体、质量、水位、事实、版本
                                                │
规则目录 ───────────────┐                      │
重置策略 <── 已确认公告事实 + 规则 + 交易日历 ──┤
计算引擎 <── 对齐行情 + 规则 + 重置上下文 ──────┤
                                                ▼
                   产品查询用例：单股 / 监控 / 预测 / 规则说明
                              │                         │
                         API DTO                  后台构建/发布任务
                              │                         │
                         微信小程序 <──────────────────┘

观测审计：采集批次、计算批次、覆盖率、差异、告警（只读，不改业务事实）
```

依赖方向只能向下游端口调用：API 与 Worker 调用应用用例；应用用例编排领域模块；领域模块通过 DATA 端口读写；DATA 不反向调用规则或公告逻辑。公告源适配器不能写计算结果；计算引擎不能自行获取公告；前端不能重算正式风险。

| 模块 | 输入/上游 | 负责输出 | 明确不负责 |
|---|---|---|---|
| 小程序应用壳 | 微信生命周期、路由 | 导航、页面容器、错误边界 | 规则计算、公告解释 |
| 小程序搜索/单股模块 | 版本化 API DTO | 搜索历史、股票详情、四项展示、模拟交互 | 生成正式触发状态、擅自去除规则项 |
| 小程序监控模块 | 版本化 API DTO | 风险提示/严重异动/退市整理的筛选和展示 | 解析公告正文、计算监管期限 |
| 小程序预测模块 | 版本化 API DTO | 当日/次日分段切换、规则卡片展示 | 新增/删除预测候选、改变触发状态 |
| 小程序规则说明模块 | 版本化 RuleCatalog DTO | 展示规则版本、阈值、出处与产品解释 | 维护第二份可执行阈值 |
| 小程序共享模块 | DTO、组件输入 | API client、日期/百分比格式化、标签、分段控件、可访问交互 | 在格式化器中判定业务风险 |
| API / BFF | 请求、身份/频率上下文 | 参数校验、DTO、错误码、请求追踪 | 外部源访问、规则判定、跨域聚合算法 |
| 应用用例 | API 命令、Job 命令 | 编排同步、核验、计算、发布与查询事务 | 复制阈值、复制计算算法 |
| 证券与交易日历 | 官方证券资料、交易所日历 | 证券标识、板块、指数映射、交易日序列、上市状态 | 异动判定 |
| 行情接入 | Tushare Pro 日行情、指数行情、证券基础资料、交易日历；既有盘中实时行情适配器 | 原始与标准化 OHLC/收盘、来源质量、水位 | 修改规则或重置；盘中报价不能覆盖正式收盘序列 |
| 公告模块 | 巨潮等公告源、正文/附件 | 原文档案、抓取批次、结构化公告事实、证据与核验状态 | 直接写监控最终状态、直接重置指标 |
| 规则模块 | 规则原文与已批准产品口径 | 版本化可执行规则、来源、解释文本、重置策略 | 网络访问、读写业务数据 |
| 计算模块 | 标准行情、证券规则、重置上下文 | 四项独立结果、达标窗口事件、可复算证据 | 公告解析、持久化、产品筛选 |
| 重置模块 | 已确认正式公告事实、规则、日历 | 幂等重置决策、生效交易日、受影响指标 | 计算是否达阈值、删除旧数据 |
| DATA 数据模块 | 上述模块的规范输入/结果 | 事实存储、仓储、事务、已发布数据集版本、状态组装、质量/版本查询 | 自行解释业务规则 |
| 产品查询模块 | 同一已发布数据集版本中的 DATA | 单股、监控、预测等产品读模型/DTO | 反向更改底层事实或计算结果 |
| 任务与发布模块 | 调度信号、重建命令 | 有锁、可重试、幂等的任务执行和原子发布 | 复制各模块业务逻辑 |
| 观测与审计 | source/job/build/差异记录 | 健康、告警、覆盖率、回放报告 | 静默修补或覆盖业务事实 |

状态组装明确属于 **DATA 模块内部能力**，不是独立微服务/独立业务投影模块。DATA 可以维护物化读视图以提升查询效率，但它必须可从规范事实和计算版本重建；物化视图本身不等同于已发布数据集版本。

## 4. 规则、事件与重置的权威语义

以下是系统实现必须遵守的已确认产品口径，不宣称它们全部是交易所原文定义：

| 指标 | 产品分类 | 计数/计算来源 | 重置影响 |
|---|---|---|---|
| 3 日偏离 | 普通异动 | 股票与所属基准指数的收盘行情，按板块阈值独立判断涨跌方向 | 正式公布普通异动后重置 3 日基线 |
| 10 日同向 | 严重异动 | 滚动十交易日内，按收盘行情判断每一个达标三日窗口；每个达标窗口单独计一次，重叠窗口也分别计次，涨跌分开计数 | 普通异动公布不清除此计数；正式公布严重异动后重置 |
| 10 日偏离 | 严重异动 | 独立计算实际行情窗口和对应方向阈值 | 正式公布严重异动后重置 |
| 30 日偏离 | 严重异动 | 独立计算实际行情窗口和对应方向阈值 | 正式公布严重异动后重置 |

四项结果始终全部产出，不互相抑制；状态摘要、优先级和预测卡片筛选不能删改四项底层结果。公告事实不作为 10 日同向计数前提，也不在行情窗口计数之外额外 `+1`。

### 4.1 三种事件不可混用

1. `AnnouncementFact`：公告正文确认的事实，如普通异动、严重异动、风险提示、退市整理、停牌。包括来源、正文哈希/文档引用、证据段落、方向/区间（如正文明确）、解析器版本、确认状态。
2. `QualifyingWindowEvent`：计算引擎依据完整收盘行情确认的三日达标窗口。窗口起止日、确认日、方向、偏离值、股票/指数输入版本、规则版本均保存。`confirmationTradeDate` 固定等于三日收益窗口的 `windowEndTradeDate`。唯一身份为 `(security_id, rule_version, window_start_trade_date, window_end_trade_date, direction)`；每天滚动产生的新达标窗口是独立事件，不能按日期重叠合并。
3. `ResetDecision`：由已确认的正式公告事实按规则产生的重置效应，保存来源事实 ID、生效交易日、受影响指标、决策版本和审计说明。重新采集同一公告不得重复应用。

十日同向的统计日窗定义为以基准日 `T` 结尾的最近十个市场交易日，首尾包含，即 `[T-9, T]`；只要求达标三日窗口的确认日落入该区间，不要求三日窗口的起始日也落在区间内。每次重算对当前 build 的窗口事件集合去重并重新聚合，禁止定时任务增量 `+1`。同一窗口关联多份公告只增加证据关系，不增加事件数。

若预期交易日行情缺失，可能有达标窗口漏算，则同向次数标 `partial/unknown`，不能把观测到的次数当最终值或显示安全。若覆盖完整但因新股上市或规则重置而有效历史不足十日，则次数可以是精确的“当前可用区间计数”，同时返回 `historyCoverage=short_history` 和有效交易日数；这与数据缺口导致的 `partial` 不同。公告可佐证、解释或触发重置，但不能替代缺失行情而静默生成产品定义的行情计数。

### 4.2 计算/重置顺序

```text
收盘行情落库并完成覆盖校验
  -> 读取已生效的 ResetDecision，构造各项计算基线
  -> 逐股计算 3/10/30 日偏离与所有达标三日窗口
  -> 按确认交易日裁剪滚动 10 交易日窗口并分别统计上涨/下跌事件
  -> 严重异动公告确认后，生成生效于规则指定交易日的全项 reset
  -> 从 reset 生效边界重算受影响股票和后续窗口
  -> 构建新数据集版本，校验后原子发布
```

重置生效日采用版本化规则政策确定；当前产品口径为正式公告日期后的下一市场交易日。该日收盘作为重置后首个收益区间的终点，前一市场交易日收盘是新的基准价格点；跨越重置边界的三日收益窗口不成立。普通重置保留既有十日同向窗口事件和十/三十日偏离历史，仅不再用重置日前的收益拼接新三日窗口；重置后须有连续三个有效收益日才可能生成新三日窗口。严重重置对四项均建立新基线，但不删除历史事实和历史 build。

多个重置决策按生效日排序；同一生效日合并作用范围，严重重置覆盖四项、普通重置只覆盖三日指标，原始决策全部留档。对任一指标，计算使用其生效日前最新的一条适用重置边界。停牌日不生成收益 bar；具体有效交易日集合来自交易日历与证券交易状态，不得在公告模块、计算模块和前端各自定义日期边界。

严重异动“行情规则触发”和“公告确认已进入监管”是两个独立字段。前者不能伪装成后者；已监管股票后续再发生普通异动，计算与公告/处置事实并存，不相互覆盖。

## 5. 数据架构与一致性

### 5.1 数据层次

1. **来源原始层**：不可变保留来源记录、公告 HTML/PDF 或可靠归档引用、行情源记录、交易日历版本及抓取批次。二进制正文放对象存储；数据库保存来源 ID、URL、时间、哈希、对象引用和抓取状态。
2. **规范事实层**：证券主数据、标准行情序列、公告事实、行情窗口事件、监管/交易事实、重置决策。事实采用追加和更正记录，保留来源与版本，不以覆盖当前值代替历史。
3. **派生结果层**：四项规则结果、当前状态读模型、当日/次日预测候选、质量结果。均能由规范事实、规则版本和计算版本重建。
4. **发布控制层**：`dataset_build`、数据水位、版本元数据、校验结果、`active_dataset_version` 指针、任务运行记录。

内部交易日期主键统一为 `YYYYMMDD`；API 日期可按 DTO 格式化，但不能改变内部交易日身份或时区语义。百分比字段须注明单位是百分数值还是小数比例，避免 `100` 与 `1.0` 混淆。

### 5.2 主要实体及关系

```text
SourceRun 1 ── N RawMarketRecord / RawAnnouncement
RawAnnouncement 1 ── N AnnouncementFact
AnnouncementFact N ── N QualifyingWindowEvent   (仅证据关联，不合并计数身份)
AnnouncementFact 1 ── N ResetDecision
MarketBars + IndexBars + RuleVersion + ResetContext
    └──> CalculationBuild ──> RuleResult[4] + QualifyingWindowEvents
RuleResult + AnnouncementFacts + TradingFacts + Quality
    └──> VersionedStockState ──> PredictionDataset / MonitorDataset / StockDetail
```

CloudBase MySQL 作为规范实体、事实账本、重置记录、计算结果、任务状态和发布控制的权威存储；对象存储用于不可变公告正文/附件。当前股票池与日频数据通过批量 Tushare 接口同步，云托管 Worker 用 MySQL 租约确保只有一个全市场同步/发布任务运行，足以控制现有的上游调用并发，不需要单独增加 Redis。

Tushare Pro 是正式日频行情、指数、证券基础资料和交易日历的主要上游适配器，不等于交易所对异动的正式认定；来源偏差、接口更正和补数都必须保留来源批次并可回放。Tushare Token 只保存在云托管密钥/环境配置，不进入小程序、日志或 DTO。Tushare 返回数据先落 MySQL 并带来源/交易日/抓取批次，再参与正式计算。盘中实时行情继续走独立实时行情适配器，不污染 Tushare 收盘基线；公告由公告模块的来源适配器获取，不能把 Tushare 行情源当公告事实源。初期不需要数据湖、Redis 或 Kafka；如后续规模/延迟指标达到明确门槛再增加。

**Redis 结论**：虽然腾讯云 Redis 实例和云托管环境参数已配置，但当前代码没有 Redis 客户端/运行时读取，预测、任务、行情结果不依赖它。Redis 不进入本项目目标架构，也不作为上线前置条件。确认该实例没有被其他服务/任务共用后，可删除本应用对应环境参数；删除整个 Redis 实例前须先核查腾讯云实例的其他消费者。若未来观测到数据库读缓存、跨多 Worker 限流或任务队列确有瓶颈，再单独评估引入 Redis，届时仍只作可重建加速层、不保存权威事实。

### 5.3 原子构建与发布

- 全市场任务写入隔离的 `build_id` staging 数据，不覆盖当前已发布数据集版本。
- 校验规则版本、行情/公告水位、证券覆盖、四项结果完整性、预测数量、质量比例和审计摘要。
- 通过后用单事务切换 `active_dataset_version` 指针；失败保留上一有效版本，并显式显示其 as-of 日期和 stale 状态。
- 单股详情、监控和预测均指定/返回同一 `dataset_version_id/build_id`；详情分页或多次查询不得混读版本。
- 重建/回滚只切换版本指针，不删除原始事实或历史结果。

## 6. 端到端流程

### 6.1 行情与盘后计算

1. Market Ingestion Job 通过 Tushare 适配器获取 `stock_basic`、`trade_cal`、`daily`、`index_daily` 及所需日频指标；同一交易日记录接口、抓取批次、来源时间、水位和完整性。Worker 采用 MySQL 租约和有界并发，MySQL 是正式落盘入口。
2. 标准化模块做证券代码映射、复权/价格口径检查、重复和缺口检查，并确保股票与所属指数日期正确对齐。
3. 规则服务按规则版本、证券板块和重置上下文提供配置；不按代码散落阈值。
4. 计算引擎产出四项结果和每个达标窗口事件。任何缺失项携带 `unavailable_reason`，不填零。
5. DATA 依据结果和公告/交易事实构造正交状态；预测生成器按独立规则结果生成候选和排除理由。
6. Build Validator 审计并原子发布同一版本供所有 API 读取。

### 6.2 公告采集与正式事实

1. 每个来源有独立 SourceRun、游标、抓取覆盖区间、页数、成功/部分失败状态和失败原因。
2. 原文/附件先归档，解析随后运行；正文抓取失败也保留命中记录，不可视为“无公告”。
3. 解析器输出候选事实及证据坐标/正文哈希；冲突或字段不足进入待核验队列，不猜方向、不触发重置。
4. 已确认事实写入追加式事实账本。多来源转载用 relation 关联；公告更正保留历史修订。
5. 重置策略只消费符合证据与来源条件的正式事实，形成幂等决策，再触发受影响证券回放。
6. 公告状态和行情计算结果分别返回，产品状态可同时表达“计算触发但公告未确认”。

### 6.3 API 与小程序读取

API 作为 BFF 提供稳定版本化 DTO：

- `StockDetail`：证券、行情时间、四项完整结果、公告/监管事实、交易状态、数据质量、计算和规则版本。
- `MonitorDataset`：有效监管事实、起止日期、来源链接、事实类型和采集新鲜度。
- `PredictionDataset(today|next_day)`：目标/基准交易日、逐规则候选、触发条件、计算证据、质量和数据集版本。
- `RuleCatalog`：版本、板块规则、定义与官方原文/产品解释标识。

前端按 API 提供的数据展示；顶部标签可以根据返回的状态摘要展示优先级，但四项卡片始终逐项呈现。模拟计算可在小程序本地执行，但只消费正式返回的规则参数并明确“模拟”，不写回、不覆盖正式状态。

## 7. 状态与质量模型

DATA 保存正交状态，不以单一枚举充当全部真相：

| 维度 | 示例 | 判定来源 |
|---|---|---|
| `ruleAssessment` | 每项规则的静态等级、方向、实际值/次数、阈值、触发、次日候选、可判定性 | 计算结果；四项分别保存，摘要不能取代它 |
| `marketEventState` | 无触发/普通异动窗口/严重异动规则触发/不可判定 | 行情窗口事件及四项结果，不代表正式监管 |
| `regulatoryState` | 无已确认监管事实/风险提示/严重异动监管/监管延续提示/退市整理风险提示 | 已确认公告事实 |
| `tradingState` | 正常/临时停牌/停牌/未知 | 交易状态源 |
| `listingLifecycleState` | 上市/退市整理期/已摘牌/未知 | 上市状态和正式公告；不混入交易状态 |
| `marketDataQuality` | complete/partial/stale/unavailable | 股票和指数数据覆盖、水位 |
| `announcementQuality` | complete/partial/stale/unavailable/pending | 来源覆盖和正文事实状态；只有来源、时间区间、分页、正文抓取均达覆盖门槛才可 complete，关键词搜索成功本身不代表全市场完整 |
| `datasetVersionState` | ready/building/failed/stale | 已发布数据集版本的构建状态 |

可以附加 `summaryStatus` 供页面优先展示，但必须能从上述维度重建，不能反向覆盖它们。页面状态“安全”只有在相关规则数据完整且全部未触发时成立；数据不可用不能呈现为安全。

## 8. 运行、失败和安全边界

- API 服务与 Worker 在微信云托管运行，可分开扩缩容；生产服务名 `flask-9a5y` 继续提供 HTTP API。Worker 采用 MySQL 租约/幂等键防重复执行和有界并发。慢公告/PDF 处理不得阻塞 API。
- 多 Worker 使用 MySQL 共享租约和唯一 build 锁；重启后可恢复或安全重试。Schema 变更按 expand-migrate-contract 部署，兼容旧 DTO/客户端版本。
- 健康检查分别报告 CloudBase MySQL、Tushare、公告源和对象存储；Tushare 超时/配额错误则暂停对应采集并保留上次已发布数据集版本，明确其数据日期和 stale 状态。
- 外部源设超时、限流、熔断和按来源重试；单源失败只降低该源覆盖状态，不清空其他源已有事实。
- 行情缺失时，受影响规则为 unknown；上一已发布数据集版本可继续服务但标 stale/as-of，不能无提示覆盖为新鲜结果。
- 公告来源失败、正文不可读、正文与行情冲突均需可观测、可追踪和待处理队列；不能转成空列表。
- 所有任务记录请求/任务 ID、输入水位、规则/代码版本、耗时、重试、输出 build 和差异摘要；敏感凭据仅放密钥管理，不进日志或文档。
- 数据库和公告对象归档需要跨可用区备份及恢复演练；上线前定义并验证 RPO/RTO。对象存储暂时不可用时保留公告命中和待处理引用，公告事实不可标 confirmed，行情计算可独立继续但整体公告质量降级。
- 对外 API 做请求频率限制、输入白名单、响应字段最小化；原始公告正文只提供合规且必要的访问。

## 9. 验收与迁移策略

目标架构最终一次交付验收，但迁移过程必须可分批验证与回滚。不得通过一次大改绕过可观测性。

1. **契约冻结**：规则版本、公告事实类型、ResetDecision 生效边界、数据质量枚举、DTO 版本和事件身份通过评审。
2. **DATA 基座**：建立规范实体、仓储端口、迁移脚本、原文归档、数据集版本 build 与恢复演练。
3. **领域核心**：规则目录、纯计算引擎、独立公告事实、重置策略全部可单测和历史回放；以黄金案例核验四项及重叠窗口逐次计数。
4. **用例/API**：单股、监控、预测统一读同一已发布数据集版本；契约测试确保字段和状态跨页面一致。
5. **小程序**：页面逻辑薄化到 feature 模块，页面只负责生命周期/事件/展示；真机、开发者工具和无障碍验证。
6. **全市场重放**：用已归档行情、公告、规则版本重建，输出逐股、逐日、逐项差异；所有差异必须能归因。
7. **影子期与切换**：新旧计算并行，比较结果和性能；达标后切换 `active_dataset_version`，保留回滚窗口。
8. **上线验收**：source freshness、任务成功、active build、API 健康、详情/监控/预测同版本、真机体验和恢复演练通过后发布。

必须有的测试包括：每板块涨跌阈值、10 日同向逐窗口/重叠/方向/滚动边界、普通与严重重置边界、公告重复和更正、不同来源转载关联、缺行情/缺指数/停牌/复牌/新股、局部公告源失败、数据集版本构建失败与回滚、跨 API 同版本、预测候选与四项规则一致、时区/交易日历边界。

## 10. 需要评审确认的架构决策

以下是架构运行参数，不应由实现人员暗自推断：

1. **来源事实的权威优先级**：同一公告的交易所、发行人和转载源内容冲突/更正时，如何确认正式事实及保留旧版本。
2. **Tushare 主源数据质量与复核策略**：哪些接口/字段必须校验、源数据更正如何触发回补，何时用交易所/其他正规源核验。
3. **公告正文的归档期限和展示授权**：原文/附件对象存储周期、访问控制、来源链接失效策略。
4. **规则原文与产品推断的发布格式**：页面和规则说明应明确区分“交易所明确条款”与“产品口径/解释”。
5. **质量门槛与过期时长**：不同页面可接受的行情/公告最大延迟，以及达到何种缺口时整份预测集不可发布。

重置范围、下一市场交易日生效、三日窗口不得跨普通重置边界、严重重置四项、同向统计按窗口结束日纳入最近十个交易日等产品契约已在本稿明确，不列为开放问题。剩余问题是来源优先级、运行 SLO 和合规存储期限，不得由实现人员默默推断。
