## 2. 达标结论

| 方案 | 综合 | 是否达标（≥4.5） | 结论 |
| --- | --- | --- | --- |
| **A 清单流** | **4.59** | ✅ 达标 | **推荐采用** |
| **B 卡片流** | **4.53** | ✅ 达标（压线） | 合格备选 |
| **C 双列网格** | **3.89** | ❌ 不达标 | 否决 |

### 方案 C 被否决的判定（三位评审一致）

> 「上下严格对齐」这条硬要求，C **不成立**。

- 字面层 C 成立：所有卡片同一模板、padding/gap/字号一致、卡高写死。
- 目的层 C 不成立：左列名称起点 x≈30、右列 x≈210，**同一列表存在两条垂直轴**。沿列表向下扫读时字段在两条轴之间来回跳，「名称对齐名称、数值对齐数值」只在**同一列内**成立，约 50% 的跨列配对无法直读比对，阅读路径由 F 形退化为逐卡 Z 形。
- 评审②原话：*「C 用『列内对齐』偷换了『上下对齐』，按硬性验收 2 判不达标。」*

附加问题（C 独有）：
1. 已出监管卡底 `#F2F3F5` **与页面底同色（1.00:1）**，仅靠 1rpx 边框，低端屏/低亮度下容器"消失"→ 硬性验收 6 在弱环境失效。
2. 卡高写死 `156rpx`，但卡内 4 行未定义 `line-height`，按 normal 实占 ≈157rpx → 必然溢出/裁切，`space-between` 失效。
3. 右上角再加「已出」角标 = 第五个视觉元素，与类型列已有的灰字「已出监管」冗余（违反"四要素"）。
4. 文档自证的卖点有误：一屏条数实为 ≈14 条而非 16 条（与 A 持平），"条数不减反增"不成立；名称可用宽 ≈8 字而非 4.5 字（不影响否决结论）。

## 3. 三位评审的主要意见

### 3.1 推荐意向（存在分歧，需你拍板）

| 评审 | 推荐 | 理由摘要 |
| --- | --- | --- |
| ① 交互可用性 | **A** | A 的两个失分点（行高、行间隙）是**参数**问题不是结构问题，改两个常量即可拿到 B 的防误触收益，无需引入卡片层；A 在成本与业务上各领先 0.25/0.30。**若团队把"误触率"列为上线 Top-1 风险，B 是可接受替代。** |
| ② 视觉设计系统 | **B** | B 只领先 A **0.01，本质平手**。容器正是"误读风险"主因，B 用 6px 间隙 + 卡边界换来误读 4.5；代价是一屏少 2–3 条。**同时明确表示"若更看重极限极简与密度，选 A 同样成立，我不反对"。** |
| ③ 小程序工程化 | **A** | 硬验收 2 是本项目唯一"灵魂"约束，A 是唯一把它做成**视觉连续**的方案（B 被 6px 缝隙削弱，C 直接放弃）。A 的三个坑都是**写代码时改**而非改设计。 |

**汇总：** 2 : 1 推荐 A；三位均认为 A 与 B 差距极小（0.06 分），且评审②判定二者"本质平手"。**结论取 A**，B 保留为误触敏感场景下的备选。

### 3.2 方案 A 的优点（三位共识）

- 固定 Grid 列位是三套中唯一零歧义的实现，同名/同码/同类型/同数值在整列成竖线，**对齐红利最扎实**。
- 结构最浅：单层 `view`、无边框/圆角/阴影，改一列全局生效，维护面最小。
- 行间零间隙 + 全列表同一 grid 模板，是唯一把"上下对齐"兑现成**视觉连续**的方案。
- 白底不依赖 `1rpx` 边框，规避旧内核边框不绘制。
- 业务匹配最高（4.80）：白底细线是唯一完全"不像内容 Feed"的呈现，与"不做内容运营"零张力。

### 3.3 方案 B 的优点（三位共识）

- 6px 卡间距把"一条 = 一块"变成物理边界，**误触/串行显著低于 A**（可用性 4.45 > A 的 4.31）。
- 列宽与 A 一致，继承 A 的对齐红利（注：评审③指出实际 gap 与内边距与 A 有差值，共用组件会错位——见 §4 P0-3）。
- 容器层天然承载未来展开态，后续维护最高。
- 已出监管用灰底 + 灰边 + 灰字三重冗余，不靠颜色单通道。

## 4. 评审发现的必改项（P0 / P1）

> 以下为三位评审独立提出、且**交叉验证一致**的问题。它们是拉低分数的主要原因，也是"综合分未达 4.8"的全部差距所在。

### P0（上线前必改）

| 编号 | 问题 | 证据 | 修法 |
| --- | --- | --- | --- |
| **P0-1** | **对比度不达 WCAG AA**。`#9CA3AF` on `#FFFFFF` 实测 **2.28–2.54:1**（文档写的 2.8:1 也不准），而它承载了「代码」这一四要素、TabBar 未选中态、已出监管代码、免责底注。`#0E9F6E` 3.39:1（跌绿 12px）、`#E0501F` 3.94:1（10 日严重异常 10px）同样未过 AA | 评审②实测 | `#9CA3AF` 降级为纯装饰色；语义灰统一用 `#6B7280`（4.83:1）或 `#767676`（4.54:1）；`#0E9F6E → #0A7F58`（5.01:1）；橙色档改为「24rpx 粗体 + 浅底 chip」，由底色承载而非加深字色（加深会与 30 日档 `#C0271E` 撞色） |
| **P0-2** | **列宽余量仅 2rpx，必然溢出**。A 五列合计 692rpx / 可用 694rpx，iOS 亚像素 rounding 或任何额外 padding 即溢出，右对齐数值列会漂 1px | 评审①、③ | 总宽降到 ≤650rpx（如 `152/112/156/72/120` + gap 10rpx），留 40rpx 容差 |
| **P0-3** | **B 声称"列宽与 A 完全相同"不成立**：gap 12rpx→8rpx、右内边距 32rpx vs A 的 28rpx，数值列右边缘差 4rpx；两处共用同一 `stock-card` 组件会直接错位 | 评审③ | B 与 A 统一为同一套列宽/间距常量，或明确 B 是独立组件不共用 |
| **P0-4** | **类型列 172rpx（86px）装不下「30日严重异常 · ST」**。按 20rpx 估算该串约 84–90px，叠加 Android 字宽即溢出，而 ST 后缀是硬性要求 | 评审① | `类型列 200rpx / 代码列 104rpx`（总宽不变），或 ST 仅出现在单股页 |
| **P0-5** | **`wx.switchTab` 不支持 url 带参**，方案 A §2.3 的 `stock/index?code=xxx` 参数必被丢弃 | 评审③ | 改 `wx.setStorageSync('pendingCode', code)` + 目标页 `onShow` 消费后立即清除（防重复消费），或 `getApp().globalData.pendingCode` |
| **P0-6** | **用 rpx 表达触控下限会在小屏跌破**：`88rpx` 在 320pt 屏 = 37.6px < 44px | 评审③ | 触控容器写 `min-height:44px`（WXSS 支持 px，不随屏缩放）；chip 补 `height:56rpx; min-height:44px` |
| **P0-7** | **T+N 表 7 列在 375px 放不下**，「安全上涨空间」表头必换行/截断，与"列序固定"冲突 | 评审③ | 首列 `position:sticky;left:0` + `scroll-view scroll-x`，或表头缩为「空间」并在规则页给全称 |
| **P0-8** | **数值对齐不能只靠 `font-variant-numeric`**：旧 X5 内核不生效，且 `+9.98` 与 `+203.11` 位数不同，右对齐也对不上小数点 | 评审③ | `utils/format.js` 统一 `toFixed(2)` 并补 `+`/`-` 号再渲染，CSS 仅作兜底 |

### P1（应改，影响体验但不阻塞）

| 编号 | 问题 | 修法 |
| --- | --- | --- |
| P1-1 | 三套均未写 `hover-class` / `hover-stay-time`，小程序 `view` 默认无按下态 → 点击零反馈 | 卡片与 chip 补 `hover-class="cell-hover"` + `hover-stay-time="70"` |
| P1-2 | `env(safe-area-inset-bottom)` 单声明在旧内核整条 `calc()` 失效 → `padding-bottom` 归零；且**使用官方 tabBar 的页面本就不需要它**（tabBar 已含安全区，加了是重复留白 34px） | 先写 `padding-bottom:100rpx;` 再写 `padding-bottom:calc(100rpx + env(safe-area-inset-bottom));`；仅自定义底栏 / 无 tabBar 二级页启用 |
| P1-3 | 分隔线写 `1px` 在 3x 屏 = 3 物理像素偏粗，写 `1rpx` 在 320pt 屏 = 0.43px 可能不绘制 | 统一 `1rpx` + 在 320pt 机型验证，必要时用 `0.5px` 兜底 |
| P1-4 | 已出监管卡底 `#FAFBFC` vs 页底 `#F2F3F5` 仅 1.08:1、边框 1.06:1，容器通道实际为零——B 的"材质级差异"被高估 | 把容器通道补到 ≥1.2:1 的底色台阶，或明确由「分组标题 + 类型列文字」单一通道显式承担 |
| P1-5 | 现有工程 `miniprogram/` 是 `pages/rules`、无 `forecast`，与方案 A 的 `pages/stock/rule`、`pages/stock/forecast` 命名冲突 | 落地上线前统一目录命名 |
| P1-6 | A 的视觉差异化仅 3.0–3.5 分：白底细线＝小程序默认观感，零品牌记忆点 | 可在不增字段前提下，用档位色相 + 数值字重建立记忆点（P0-1 的 chip 方案顺带解决） |

## 5. 为什么综合分是 4.59 而不是 4.8

三位评审给 A 的失分几乎全部集中在**可修正项**，而非结构缺陷：

| 失分子项 | 当前 | 修完预期 |
| --- | --- | --- |
| 无障碍（对比度） | 3.5–4.0 | 4.5（P0-1 修完） |
| 跨机型稳健（列宽容差、触控下限） | 3.5–4.5 | 5.0（P0-2 / P0-6 修完） |
| 视觉差异化 | 3.0–3.5 | 4.0（P1-6 修完） |
| 设计还原难度 | 4.0–4.5 | 4.5（P0-2 / P0-8 修完） |

**汇总判断：P0 八项全部修完后，方案 A 的预期综合分落在 4.75–4.85 区间**，可达到 4.8 目标。当前 4.59 是"未修正稿"的真实水位，不是方案上限。

---

## 6. 最终结论

1. **采用方案 A（清单流），综合 4.59，达标。**
2. **方案 B（卡片流）4.53，压线达标，保留为备选**——若上线前把"误触率"列为 Top-1 风险，或列表常年 >40 条，切 B。
3. **方案 C（双列网格）3.89，不达标，否决**——唯一原因是违反"上下严格对齐"硬要求，非分数问题。
4. **P0 八项必须在开发启动前定稿**（尤其 P0-1 对比度、P0-2 列宽容差、P0-5 switchTab 传参），修完预期可达 4.8。
5. **PRD 缺失**是本次评审的边界，恢复后需重跑一次覆盖度核对。
