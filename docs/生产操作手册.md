# 生产操作手册

适用服务：微信云托管 `flask-9a5y`。生产发布只使用微信云托管控制台；本手册不使用 CloudBase CLI。

## 1. 盘中链路与发布验收

1. 盘中行情和预测刷新结果只在请求生命周期内使用，不写入 MySQL、Redis 或进程缓存，因此不需要为这条链路配置 Redis。
2. 发布后执行：

   ```text
   redis://:<password>@<host>:<port>/0
   ```

   TLS 实例使用 `rediss://`。密码只写入云托管环境变量，不提交到 GitHub。
5. 保存并重新发布服务。发布后执行：

   ```bash
   curl -fsS https://flask-9a5y-319926-10-1496305218.sh.run.tcloudbase.com/health
   curl -fsS https://flask-9a5y-319926-10-1496305218.sh.run.tcloudbase.com/health/ui >/tmp/stock-abnormal-health.html
   python3 server/tools/api_contract_check.py \
     --base-url https://flask-9a5y-319926-10-1496305218.sh.run.tcloudbase.com \
     --require-data
   ```

   `/health` 应返回实时源来源级聚合统计、股票基础资料覆盖、预测数据集状态和任务错误；不再检查 `intradayState`。浏览器打开 `/health/ui` 查看人类可读摘要。
3. 盘中刷新接口返回 `dataStage=realtime` 和完整 `items`；随后 GET 仍返回稳定数据集；`POST /api/quotes/realtime` 返回 `persisted=false`。

## 2. 补齐价格限制字段

服务启动时会调用 Tushare 最新 `stock_basic`，通过独立的基础资料事务填充价格限制字段，不更新行情计算任务日期。发布后重启服务即可执行同步；若上游暂时不可用，再使用下方 SQL 回填。已知 SSE、SZSE、BSE 的主板、创业板、科创板、北交所记录填 `1`；非活跃记录填 `0`；未知交易所保持 `NULL`，继续排除出预测。

回填前备份：

```sql
CREATE TABLE stock_basic_price_limit_backup_20261010 AS
SELECT ts_code, price_limit_enabled, updated_at
FROM stock_basic;
```

回填已知板块：

```sql
UPDATE stock_basic
SET price_limit_enabled = 1,
    updated_at = NOW()
WHERE list_status = 'L'
  AND market IN ('SSE', 'SZSE', 'BSE')
  AND board IN ('主板', '创业板', '科创板', '北交所');

UPDATE stock_basic
SET price_limit_enabled = 0,
    updated_at = NOW()
WHERE list_status <> 'L';
```

回填后核验：

```sql
SELECT
  COUNT(*) AS active,
  SUM(price_limit_enabled IS NOT NULL) AS active_with_price_limit,
  SUM(price_limit_enabled = 1) AS enabled
FROM stock_basic
WHERE list_status = 'L';
```

然后运行：

```bash
python3 server/tools/prediction_migration_check.py \
  --require-complete-stock-basic
```

`stockBasicCoverage.complete` 必须为 `true`。上市首日、退市整理、ST 和无涨跌幅限制的业务排除仍由规则层执行，不通过静态字段伪装为可预测。

## 3. 关闭并删除旧预测表

规则版本升级后，服务会自动在单一后台任务中重抓最近 31 个有效收盘点并重建预测，无需额外设置环境变量。只有健康检查确认规则版本正确但计算基础数据仍需人工强制重建时，才临时增加：

```text
FORCE_MARKET_HISTORY_REBUILD=1
```

重新发布并重启服务。服务启动后会在同一协调任务中重新拉取最近 `31` 个有效收盘日的股票和所属指数正式数据，重建 `stock_calc_base`、`index_calc_base`，并重新生成 `prediction_dataset` 的 `today`/`next_day`。规则升级自动重建与此开关不会并行执行。该任务不读取、不写入 `prediction_cache`。

重算完成后检查 `/health` 中两个数据集均为 `status=ready`、`dataQuality=confirmed`、`datasetQuoteComplete=true`，再删除 `FORCE_MARKET_HISTORY_REBUILD` 环境变量并重新发布，避免每次重启重复全市场抓取。确认新数据接口和 contract test 通过后，若要立即完成迁移，将 `PREDICTION_CACHE_COMPAT_READ` 改为 `0` 并重新发布；本次全量重建已验证新表可用，不要求继续双读观察。

如未执行全量重建而采用渐进迁移，观察期保持云托管环境变量 `PREDICTION_CACHE_COMPAT_READ=1`，每个交易日收盘后保存一次：

```bash
python3 server/tools/prediction_migration_check.py
```

连续 7 个不同交易日均满足以下条件后可进入关闭步骤；全量重建并通过 contract test 后可立即关闭：

- `fallbackReadsSinceProcessStart=0`；
- `predictionDatasetRows > 0`；
- `legacyReadFree=true`；
- API contract test 通过。

每次旧表回退读取都会写入 `prediction_cache_read_audit`，因此服务重启不会丢失迁移观察记录。核验输出中的 `legacyReadAudit` 保存最近 30 个日期和读取次数；任一交易日 `read_count` 大于 0 都要重新开始连续计数。

将 7 次输出和日期保存到 `docs/验收记录/prediction-migration/`。第 7 个交易日后：

1. 在云托管环境变量设置 `PREDICTION_CACHE_COMPAT_READ=0` 并重新发布。
2. 检查 `/health.data.marketCalc.predictionMigration.compatReadEnabled=false`。
3. 运行 today/next_day contract test，确认 `prediction_dataset` 两个角色都为 `ready`、`confirmed` 且 `dataset_quote_complete=true`。
4. 先备份旧表，再删除：

   ```sql
   CREATE TABLE prediction_cache_backup_20261012 LIKE prediction_cache;
   INSERT INTO prediction_cache_backup_20261012
   SELECT * FROM prediction_cache;
   DROP TABLE prediction_cache;
   ```

5. 再次检查 `/health`，`predictionCacheTableExists=false`。旧表备份保留 14 天后再删除。

回滚时将 `PREDICTION_CACHE_COMPAT_READ` 改回 `1`，从备份恢复 `prediction_cache`，重新发布并验证 API。
