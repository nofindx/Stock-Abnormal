# 页面缓存与0.25核/0.5GB优化方案

> PERF-LOCAL-20261112.1。目标规格保持0.25核/0.5GB。本轮已实现前端缓存与开发者工具取数修复，仅在本地；后端与云配置优化为待实施方案，未部署。冻结1.0.21及线上1.0.20测试包不变。

## 1. 依据与目标

用户观察到313实例数从5回落到1，符合弹性运行可能表现，但未取得控制台事件，不能据此确定扩容指标或把上限5当成实际长期运行5个。当前不通过锁死单实例来掩盖耗时问题。

2026-11-12约16点的公网HTTPS低频抽样：预测上下文2.5–9.4秒，固定列表0.4–0.5秒，单次实时刷新1.4–1.7秒；重点监控未压缩约737KB，其中resetFacts约693KB，页面未引用该字段。声明Accept-Encoding=gzip时网关返回gzip约102KB，说明现有压缩已有效；不能再把“增加gzip”当成尚未实现的主要优化。公网结果不等同真机callContainer耗时，也没有证明CPU、内存或MySQL哪项已经饱和。

目标是减少重复业务请求、数据库往返和重复CPU/内存开销，保留原规则、实时来源、预测名单与公告事实。暂不新增服务、数据库迁移、用户系统或持久化客户端授权。

## 2. 已实现的前端缓存定义

| 页面 | 保留内容 | 重用条件 | 重取条件 |
| --- | --- | --- | --- |
| 异动预测 | 当日/次日各一份最近有效结果、显示字段和对应read_token | 同页面、同上海日期/业务阶段；次日还需开放且满足当前门槛 | 首次进入未加载标签；手动刷新；跨日；9:00、9:15、15:00阶段变化 |
| 重点监控 | 一份all列表，全部/风险/严重/退市均本地筛选 | 同页面、同上海日期 | 首次进入；手动刷新；跨日；已有后台采集未结束时沿用有界查询 |
| 单股计算 | 最近8只股票的原始行情/计算结果及对应read_token | 同页面、同股票、同上海日期/业务阶段 | 首次查该股或被淘汰；手动刷新；跨日/业务阶段变化 |

缓存为页面内存，页面销毁/小程序重启清除，不写wx永久存储。已有搜索历史仍按旧规则保存，但不把行情、签名地址、授权token、模拟输入或广告许可混入搜索历史。缓存结果显示原有更新时间，不把恢复视图伪装成刚刷新。

单股重新选择/进入仍按已确认规则初始化2日模拟与该股激励会话；复用的是行情与计算基线，不恢复上次股票的模拟输入或观看许可。8只上限按最近使用淘汰，避免长时间搜索导致内存无界增长。

预测切标签不触发S2；已加载且同目标的rewarded次日视图需具有当前会话许可才能恢复。首次解锁前后仍检查元数据；普通缓存不能越过激励入口。业务边界、目标改变或后端返回次日关闭后，旧次日缓存不能继续恢复。配置按既有600秒策略单独检查，不等同业务列表重取。

各范围保留自己的授权，不能拿当日token刷新次日或拿A股token刷新B股。可见缓存不因5分钟授权到期立即消失；下次手动请求沿用API层40902→取得新上下文→重试一次的原恢复逻辑。空的有效列表也能缓存；不可用结果不作为可复用的成功视图。晚返回的旧S1/S2不能覆盖切换后的页面。

监控倒计时不保存多份筛选副本，避免“07天→01天”的旧标签副本闪动。跨日先清旧结果再读新列表，前端不自行修改公告确认的监管期。PDF代理链接仅有效5分钟；从列表成功取得链接满4分钟后再点击公告时，按需读取新列表并匹配同一公告的新链接；续取失败不继续下载旧地址。没有新增PDF后台轮询。

## 3. 已修复的开发者工具取数

根因是上一轮把“只在本地开发、不发布”实现成了默认强制127.0.0.1，但本地8787端口未运行后端。它造成开发者工具无数据，线上测试包不受影响。

现恢复冻结版连接方式：develop用原HTTPS云服务，trial/release用原callContainer。显式`LOCAL_DEVELOPMENT_ONLY=true`的环回隔离能力仍保留给以后有本地后端的联调，但默认false。广告新接口在线上尚不存在时，配置读取失败按已确认的关闭/free默认运行，不以此阻断行情业务。

本地开发者工具重新编译后即可应用；本轮路由回归已验证真实App默认配置，不只验证测试里手填的地址。尚未取得用户重新编译后的可视化/真机验收，不能称已完成手机验证。

## 4. 后端优化顺序与确定实现方案（尚未实施）

### P1：小响应与批量数据库读取

1. `/api/monitor`在响应层排除内部resetFacts、unresolvedFacts，保留items、updatedAt、snapshotDate、refreshing、error和页面使用的数据质量等展示字段。只裁剪公开响应副本；内部公告快照、S1核验、重置与PDF生成继续读取完整事实。按现有样本可去掉约94%的未压缩JSON；不承诺总耗时同比下降94%。
2. 监控列表最新日涨跌由逐卡get_calc改为一次批量查询，按ts_code去重后映射回每张事实卡；同股两条监管事实仍保留两张卡。
3. 预测/单股S1 capture的股票计算输入和指数输入改为按授权名单批量读取，去重后使用少量请求内连接。选股只读所需股票资料，不为一只股票重复加载/规范化全市场列表。保留已冻结输入、scope、版本和日期的绑定。
4. 数据库先使用请求内连接复用与批量SQL，不先引入大连接池。当前每次get_calc/get_index都会建立、关闭连接；削减这些往返比单纯延长前端超时更优先。

### P2：用现有Redis减少重复回源

现有3秒报价缓存与短租约保留。当前_fetch_realtime_many主要在竞争失败后读缓存，正常取得租约的调用仍会回源；改为先读同source-policy、同quote-bucket的缓存，只取缺失证券/指数，取得租约后再检查一次，合并命中与本次结果。相同证券在单股和预测中可共用报价，授权视图仍各自独立。

TTL维持3秒，不将低配优化变成缓存几分钟的旧实时价格，不跨桶兜底冒充最新。保留来源真实时间、质量与失败提示；Redis故障按原可用性策略处理，不用空字典假装报价成功。后续以并发相同股、不同股、预测名单交集测试实际回源次数，不以Redis ping正常替代命中验证。

### P3：后台重活单份执行、降低峰值

每实例仍可承接用户请求，但基础资料同步、行情更新/全市场预测生成及公告采集各自使用跨实例单执行保护。现有部分Lock只在本进程有效；不能因扩容让几个实例同时做全量计算。优先复用MySQL命名锁（专用持锁连接、非阻塞获取、任务结束释放），无需新增表；拿不到锁的调度周期跳过，不能阻塞用户请求。对写入时序沿用现有原子发布与旧版本防覆盖校验。

单实例后台CPU重任务最多1个；公告正文解析/下载并发从4以2为候选，实时S2工作线程从4以2为候选，保留有界队列与queued语义；具体降低是否增大等待用小并发回归决定，不凭线程更少就宣布更快。全市场处理逐批完成，及时释放DataFrame/正文临时对象，不缓存PDF二进制到进程或Redis。真实任务必须完整执行，不能删除公告重试或收盘计算来省CPU。

### P4：云规格与扩缩容建议（尚未更改）

- 保持0.25核/0.5GB，最小实例1，保证现有容器内后台调度持续运行。
- 小流量初始建议最大实例2，作为突发余量与费用上限；上线此配置前需取得当前扩容策略与最近CPU/内存曲线，确认不会使请求持续排队。不把1实例写死，也不声称上限2适合任意并发。
- 沿用平台扩缩容机制；若支持CPU阈值，70%左右可作为初始评估值，实际监控再调。冷却时间与指标需按控制台实际选项确认，不填未经核验的参数。
- 当前只有1个实例并不证明CPU内存足够。观察收盘、夜间公告、冷启动和正常查询，不能只看空闲时段。
- 按此前刊例价，仅容器CPU/内存，单个0.25核/0.5GB实例连续30天约21.42元；两个全天运行约42.84元。扩容实际按运行时长计费，MySQL/Redis/流量另计，账单以账户抵扣与实际计费为准。

## 5. 验收目标与边界

以下为待测目标，尚未达成线上承诺：

| 项目 | 目标/方法 |
| --- | --- |
| 前端重复切换 | 同阶段已加载预测标签、监控分类、已缓存单股的业务请求增量为0；保持页面内容与原更新时间 |
| 前端更新正确性 | 跨日、9:00/9:15/15:00边界、手动刷新、旧回包、token到期、PDF续期均有自动化用例 |
| S1性能 | 同网络下预热后上下文P95争取≤2秒；固定列表P95≤1秒 |
| 完整首屏 | 正常上游时首屏至最新报价P95争取≤5秒；来源故障如实提示，不硬保时间 |
| 监控响应 | 无内部事实全集，当前25卡样本未压缩目标≤100KB；API契约与PDF可读不变 |
| 资源 | 对5/10个并发用户的小规模本地/测试测量记录CPU、RSS、排队、回源和连接数；覆盖收盘与公告峰值 |
| 低配稳定性 | 无OOM/重启；持续内存争取≤配额80%，峰值留有余量；后台任务完整且不重复发布 |

若批量读取、缓存命中与任务保护落实后，后台仍持续占满CPU或内存接近上限，应明确0.25核/0.5GB不足，届时再比较0.5核/1GB，不能承诺代码优化能无限替代算力。
