冷缓存并发争用者仍可能在源请求完成前取得部分报价/queued；S2会依原规则保留S1、显示stale，不会伪造全部fresh。后续同桶请求可命中已经完成的报价。本轮并发数据明确记录cold_queued_partial，不把它们算作已取到完整行情。

本轮未修改WXML/WXSS；沿用11月12日已通过的微信离线编译证据。没有重复宣称本轮完成真机验证。日志中的既有LibreSSL依赖提示未导致用例失败，运行依赖未变。

## 3. 复查修正

1. 将逐日重建引入的内部order字段从bootstrap保存向量中移除，保持原持久化结构与收益结果。
2. 原测试假定同一时刻连续刷新必回源，现明确在下一3秒桶取得新报价，另加TTL、policy及桶隔离测试，未放宽计算触发断言。
3. 单纯释放业务层DataFrame还会被Tushare客户端缓存持有，已增加精确到已消费日期的缓存释放，不清除日历或其他日期。
4. Redis租约释放改为原子归属校验，并验证hash tag同槽，避免旧主人删除后继租约及集群Lua跨槽错误。
5. 公告采集设置attempt状态也纳入finally保护，写状态异常后不会永远停留refreshing。

## 4. 验收范围与下一阶段

已完成本地实现、源代码复核、自动化回归、两进程锁模拟、隔离Redis/Lua适配器测试和5/10用户模拟。未连接生产MySQL/Redis、未改云规格或扩缩容、未推送Git、未部署或上传小程序。没有数据库迁移需求。

模拟Redis/MySQL不是腾讯云实测；本机CPU、RSS、warm毫秒值也不是0.25核/0.5GB云端性能承诺。后续获准发布时，在同一网络对照S1、监控、S2和真机耗时，再观察收盘/夜间CPU、RSS、排队及实例数量。P4扩缩容本轮未执行。真实广告仍等待流量主资格及真实单元测试。
