## 环境变量补齐清单

旧配置可继续复用，不需要重建 MySQL、Redis 或 Tushare 连接。vNext 额外需要：

| 变量 | 值要求 | 处理方式 |
| --- | --- | --- |
| `VNEXT_CONTEXT_SECRET` | 随机强密钥，至少 32 字节 | 用户在云托管控制台录入，不进入仓库、聊天或日志 |
| `MONITOR_PDF_TOKEN_SECRET` | 与 context 密钥不同的随机强密钥，至少 32 字节 | 用户在云托管控制台录入，不进入仓库、聊天或日志 |
| `SOURCE_POLICY_JSON` | `server/fixtures/vnext/source_policy_continuous.env.json` 完整内容 | 已提取为可直接录入的数组；不要粘贴带外层 `entries` 的 manifest；后端逐条验证 `content_hash` |
| `SOURCE_POLICY_HASH` | `160daec9f2503eafc4cd710c2420c0ce6dcf494620425faaee99933615f47f87` | 必须是 `policy_hash({"policies": entries})` 的集合哈希；不是整个文件的字节 SHA-256 |
| `VNEXT_EXPLICIT_MIGRATIONS` | `1` | **仅在两份迁移成功且新表核验通过后**启用；提前开启会让 API 因缺表拒绝访问。应用启动仍不会自动执行 DDL |

录入前应刷新控制台并确认原有 VPC/子网绑定没有变化；来源策略 JSON/哈希同时补齐、复核后再保存。迁移开关按下述步骤在迁移成功后单独开启。密钥只能由用户在控制台输入。若控制台或运行记录曾明文展示过任何凭据，应轮换对应凭据。

## MySQL 迁移与恢复

- `001_vnext_foundation.sql`、`002_vnext_core.sql` 是 vNext 新增结构的增量迁移，不是旧版预测缓存迁移；不能用旧迁移替代。
- DDL 使用 `CREATE TABLE IF NOT EXISTS`，迁移 runner 以 `schema_migration` 记录文件 SHA-256，并拒绝已应用后被修改的迁移。其幂等性由本地 runner 单测覆盖，但不是云端迁移成功证据。
- 本机无法访问云端私网 MySQL。本轮没有执行生产 DDL、备份恢复或恢复演练。
- 云端执行前必须确认目标库身份、备份可读且恢复至隔离目标成功，再比较旧 schema 与 vNext 新增表；之后通过容器内显式命令执行迁移，核验 ledger、表清单和重复执行结果。不可在生产库上做破坏性恢复测试。

1. 在云托管控制台确认原 VPC/子网绑定及两项签名密钥，录入来源策略 JSON/哈希。**此时不要提前启用** `VNEXT_EXPLICIT_MIGRATIONS=1`；任何步骤均不输出或保存密钥到代码/日志。
