## 1. 结论

同意专家团的主要诊断：产品骨架已经清楚，主要风险是工程实现没有建立统一数据版本、事实身份、可重放计算和可靠发布机制。应继续采用当前确定的模块化单体，不另起技术栈，不拆成多个业务微服务。

但七份报告不能直接拼接后作为开发规范。报告之间仍存在规则版本、日期角色、缺因枚举、发布门禁、实时刷新、停复牌窗口和回滚标准等冲突；部分性能、成本与覆盖率是估算，部分“已拍板”是评审人员内部建议，并非本次用户确认。应先收敛为一份开发设计，再按依赖推进。

建议结论是：**允许启动不依赖待定口径的工程基础工作；规则和展示口径完成本文第 5 节的确认后，才能冻结计算契约并接入生产。** 当前不能据此认定现网已可靠定版。

本地抽查确认了以下高风险路径：

- `server/app.py`：服务双向回调注入，HTTP 启动时启动后台调度；访问日志直接关闭。
- `server/services/market_service.py`：预测筛选直接排除 `same_direction_10d`；逐股请求日线；部分事实读取异常返回空字典。
- `server/calculations/engine.py`：存在按事件起始日入窗和 episode 合并路径。
- `server/services/market_calc_repository.py`：逐次建立数据库连接、启动式建表迁移；现有结果表未形成 vNext 发布版本机制。
- `server/services/monitor_service.py`：默认 SQLite 与 PDF 目录位于 `/tmp`。这是默认配置风险，不能仅凭默认值断言生产实际挂载、备份或对象存储配置不存在。

## 3. 采纳并收敛的工程方案

1. **保留五个后端业务模块**：数据、规则、计算、公告、业务服务；前端独立。编排、发布、查询是业务服务的内部包，不再增加产品模块数量。
2. **MySQL 保存结构化事实与版本关系，PDF 沿用后端实例临时缓存和受控代理**；小程序内点击公告后直接打开 PDF 阅读；不使用 COS/Redis 保存 PDF。保留腾讯云 Redis 环境，正确性不依赖 Redis；新版本启用前通过跨实例门禁。
3. **不可变输入修订 + 不可变数据集 + 原子发布指针**。行情、规则、公告事实和映射都固定到修订；不能只给结果增加版本号，却仍读可变的“最新原始数据”。
4. **事实与来源证据分离**。一个正文可以支持多个独立事实，一个事实可以有多条证据；更正与撤回生成修订，不改写历史数据集。
5. **计算是纯函数，业务服务统一编排**。公告先提供证据；公告事实负责正式计次和事实重置，计算负责行情核验、差异记录和指标计算；页面不生成正式状态。
6. **API、worker、migrate 按运行角色隔离**。任务必须有持久化记账、租约、fencing token、幂等键与补跑，不能只依赖单实例或进程锁。
7. **统一展示契约和缺因目录**。安全必须有完整依赖依据；不可用是数据状态，不新增监管业务状态。明确保留的严重事实不会因无关指标缺数而消失。
8. **一套门禁注册表，三种执行范围**：数据集发布、软件发布、定时巡检。所有适用项有记录，不能要求每次数据集发布重复真机测试或执行二十日重放。
9. **新旧并行但不混算**。影子数据集与生产数据集分离，一个数据集只采用一个规则包版本；新旧客户端通过兼容接口逐步迁移。
10. **预测首次打开按两阶段刷新**。先读取/更新一次已发布股票池数据集，再在交易时段获取一次固定名单内实时行情；这是两个逻辑阶段，不限定 HTTP 请求数。盘中不扫描/扩充名单，也不刷新未收盘的次日预测；单股仅刷新所选证券。次日名单由收盘数据构建发布。

## 4. 对专家建议的修正

| 议题 | 综合意见 | 原因及开发设计落点 |
| --- | --- | --- |
| D1、D11：次日反解、指数为 0% | 建议采纳，明确是产品情景假设 | 不能加 `r* >= 0` 限制；次日小跌仍可能满足上涨阈值。必须使用个股当日合法价格集合和最小报价单位验算。见开发设计 §7 |
| D2：是否保留同向预测 | 不再列为新需求待定，按 PRD 保留 | 当前直接排除是迁移缺陷；正式计次与次日条件预测分开 |
| D3：逐事实计次 | 按已定 PRD 执行 | 多个独立事实可重叠；转载不增次；以 `fact_end_date` 入窗，不能机械按滑动窗口计数 |
| D4：停牌原因未知 | 采纳“不猜清零或延续”；修正“安全侧”说法 | 截断偏离不必然更保守。按依赖范围标不可用，不影响有证据的监管事实 |
| D5：默认关闭实时行情 | 不采纳 | 实时行情功能按用户要求保留；盘中数据源以当前实现为准，Tushare 仅承担盘后静态数据，重构需验证来源、时效、限流和回退 |
| D6：板块/指数变化 | 采纳有效期映射，不自动重置 | 映射切换不是当然的监管重置事件，须由适用规则决定 |
| D7：统一因子复权计算 | 不直接采纳为监管收益口径 | 存原始价、官方前收盘、涨跌幅和因子；监管收益定义另行取证冻结，不能把投资收益复权口径代替监管口径 |
| D8、D9：新股、退市整理 | 采用证券/日期级适用规则 | 缺价格界限仅影响可达性；不能把所有新股、ST、退市整理都按一个固定涨跌停幅度处理 |
| D10：更正撤回 | 采纳不可变修订和新数据集 | 已发布的事件、结果不原地改 `counted=0`；变化体现在新版本视图 |
| D12：证据优先级 | 改为发布主体、法定职责、时效与更正关系判定 | 巨潮是披露渠道，不能简单把“巨潮”排在“发行人”之上；券商提示不替代正式监管认定 |
| 同一数据集混用两套规则灰度 | 不采纳 | 霍报告 §4.6 与版本唯一门禁冲突；采用两套独立数据集和灰度路由 |
| 状态不得降级、差异率超过 0.5% 一律失败 | 修正 | 修复误计次和重置错误本来就可能降级。禁止的是无依据变化；有证据且经审核的预期差异可以通过 |
| 预警触及与重置的关系 | 按用户最新解释重新界定 | 阈值触及只产生计算预警；普通公告事实按方向直接计入 10 日同向并按生效日重置 3 日，严重公告按规则重置四项；计算只做核验，差异修正系统计算/数据 |
| 一个缺因使全部状态变灰 | 不采纳 | 已知严重事实或已触发严重指标不能因无关依赖缺数而被隐藏；“已知风险 + 部分不可用”可以同时表达 |
| `reasonCode` 一律强制未知色 | 修正 | 未开放次日、非交易时段、筛选排除是信息原因，不是数据失败；不能把正常状态都渲染成不可用 |
| 31 张表、按年分区、只读副本作为开工前提 | 不采纳为首期强制 | 先满足版本、身份与索引；按实际量测再拆表、分区、引入副本，避免增加成本和一致性风险 |
| 数据集号固定两位并按字典序判断新旧 | 修正 | 展示号与内部 ID 分离，序号可扩展；新旧顺序和回滚用指针 generation，防止回滚后无法恢复及 ABA 问题 |
| 多页面“同帧”切换 | 改为同一读取令牌下确定一致 | 独立网络响应无法承诺同帧；以服务端日期上下文、有效期和切换后重新取数验收 |
| 09:00 切换做纯函数 | 采纳并补边界 | 使用版本化日历与服务端时间，切换展示日期不冒充新收盘数据已发布；不得把旧结果直接改日期 |
| PDF 临时文件的有效期与事实期 | 按冻结版实现 | 后端当前有效监控快照提供受控 PDF 入口；监管展示期结束后清理实例临时 PDF，不设计持久对象版本/保全状态机 |
| 30 点收益无法计算 30 日 | 修正措辞 | 30 个收益点可计算 30 日复合收益，或需要 31 个收盘点。现状真正缺陷是原地覆盖、输入不完整、不能重放 |
| 存储、QPS、P95 与 13 周工期 | 改为待实测的预算 | 1.82 GB/三年与 24 MB/日不相容；响应耗时不等于 CPU 耗时；不能据此采购或保证交付日期 |

数据源定版：**Tushare 用于盘后静态日频数据，盘中实时行情沿用仓库当前腾讯/新浪/东方财富适配与回退实现**。迁移须验证运行配置、逐股票/指数来源和时间戳，不能把 Tushare 写成盘中源，见开发设计 §4.2。

## 5. 需要在 PRD 定版前确认的一项产品口径

| 编号 | 问题 | 建议 | 当前约束 |
| --- | --- | --- | --- |
| Q1 | 次日“可能触发”怎样定义 | 已按用户确认，保持现有次日预测反解；指数次日 0% 只是条件假设 | 已确认，不再改算法 |
| Q2 | 重置边界与状态来源 | 用户已确认：普通公告按方向计次并重置 3 日；严重公告按审定生效日重置四项；监管状态来自公告事实，计算触及只形成预警。严重公告日期结合正文、行情触发日和规则审定；D 日收盘触发且当晚公告确认同一事实时 D+1 生效 | 已解决；文档待用户评审 |

除权、复牌首日和基准指数映射等监管收益构造，由规则/数据负责人按适用交易所文件与可核验公告样本完成取证、对账并交付证据；若确有仍无法确定的边界，再带证据提交用户，不把研究工作转嫁为产品选择题。

其他事项中，同向逐事实计次、普通/严重重置范围、首次打开两阶段刷新、已发布名单边界、当日已触发的同一严重规则不在次日预测重复出卡、小程序内 PDF 阅读及附件清理、数据不可用不等于安全，均有明确产品指令，不重复请求决策。

## 6. 实施计划与分工

以下为建议工作包，不代表已有人员承诺。人员角色分别为产品/规则、后端/数据、前端、测试、运维；开发设计由技术负责人维护。**人日是工作量，不是可直接相加的交付日期。** 20261028 是计划编制日，T0 指本设计及阻塞口径确认后的实际开工日。

| 阶段 | 工作与主责 | 依赖 | 建议工作量 | 必须交付的通过证据 |
| --- | --- | --- | ---: | --- |
| P0 契约定版 | 产品/规则 + 技术负责人：把已确认口径同步到 PRD/架构；补齐监管收益规则来源证据、缺因、日期语义、API 样例 | 本文评审 | 3–5 人日 | 口径决策记录、契约 schema、来源清单与测试预期 |
| P1 数据及工程地基 | 后端/数据 + 运维：版本化迁移、输入修订、MySQL 事实、角色隔离、日志、租约与 CI | P0 的公共契约；可与规则取证并行 | 8–12 人日 | 空库/旧库迁移、恢复演练、失租写入被拒、备份核验 |
| P2 规则与计算 | 后端 + 规则 + 测试：唯一规则包、区间收益、匹配、计次、重置、次日反解与本地模拟夹具 | P0；P1 输入接口 | 8–12 人日 | 全边界夹具、公告事实样本、确定性重放、无四项抑制 |
| P3 公告与重建发布 | 后端/数据：批次覆盖、正文解析、事实修订、临时 PDF 缓存/清理、编排、统一门禁、CAS 发布 | P1；P2 可先用夹具并行 | 8–12 人日 | 多源幂等、补采闭环、候选失败不动指针、并发发布及回滚 |
| P4 前端与接口迁移 | 前端 + 后端：统一读取令牌、四项展示、S1/S2、版本守卫、模拟、PDF 打开与旧版兼容 | P0 契约即可 mock；联调依赖 P3 | 6–10 人日 | 两系统真机录屏、跨页同值、首开实时、09:00 切换、不伪造时间 |
| P5 全量审核与试运行 | 测试主责：最近至少 20 个交易日回放、全市场核验、压测、故障注入、迁移差异归因 | P2–P4 | 5–8 人日 | 自动报告、全部差异有结论、未解释风险降级为 0、回滚和恢复证据 |
| P6 灰度发布与验收 | 运维 + 测试 + 产品：后端、数据集、小程序分别发布，旧版兼容验证 | P5 全部阻塞项闭合 | 3–5 人日 + 观察期 | 影子至少 5 交易日、内部体验至少 3 交易日、生产至少 5 交易日；证据包 |
| P7 旧链路退役 | 后端/运维：停旧调度与兼容读取、归档、验证清理 | P6 稳定且回滚窗口结束 | 1–2 人日 | 旧路径访问为 0，至少 14 自然日观察/回滚窗口后再清理 |

建议总工作量为 **42–66 人日**。多个角色可并行，但观察交易日不能用并行开发抵消。具体日历工期在人员和云资源配置核对后再排，不承诺“必定 13 周”或本周全部上线。

执行顺序是：**先冻结公共契约和三项口径 → 先保护事实与输入 → 建纯计算与公告匹配 → 建统一发布 → 接前端 → 全市场回放与真机 → 分层灰度 → 最后删除旧链路。** 不在新数据链路验收前让新页面接管生产，也不先删除能回滚的旧数据。
