> 版本：ARCH-NEXT-20261029.20
> 对应产品定义：PRD-NEXT-20261029.21
> 状态：架构评审稿；仅定义目标边界，不表示已完成代码重构。
> 评审状态：本轮联合复核后条件通过，待用户最终评审。  
> 本次修订：明确跨实例 PDF 短期签名凭证、独立密钥和本机临时懒取，不将附件写入 Redis/COS。

## 1. 架构结论

系统按前端、后端、数据三层组织。后端采用云托管中的模块化单体，不先拆微服务。下图表达职责依赖和证据流，不表示任务执行的先后顺序；实际运行顺序以业务服务编排流程为准：

**数据是基石 → 规则给出唯一口径 → 计算生成候选结果 → 公告采集、解析和核验事实 → 业务服务编排并调用计算匹配 → 发布统一答案 → 小程序展示。**

实际运行时序为：行情、证券/日历与公告并行采集 → 规则解析 → 行情候选计算 → 公告事实应用、核验差异记录和重置重放 → 完整性门禁 → 原子发布。上方箭头只表达职责依赖，不表示公告必须等待计算或计算必须等待公告。

10 日同向只以公告正文确认且可独立识别的 3 日偏离类普通异动事实为计次来源，换手率类、单日偏离类等不计次；仅正文明确标识多个独立事实/区间时才分别计次，模糊“多次”待核验。对应收盘计算只做日期、方向和阈值核验。计算先形成可复算候选，公告模块提供结构化事实和证据；业务服务编排核验请求，若不一致则记录并修正系统计算/数据，不能阻止公告事实计次或重置。公告模块不直接改数据库结果，业务服务也不另写规则。

## 2. 系统边界与调用方向

```text
外部行情/证券/日历源 ─────→ 数据层：接入、对齐、质量、持久化、版本
巨潮/交易所/发行人源 ─────→ 公告：采集、正文、事实证据 ─┐
                                                        │
                                          规则：适用规则和版本
                                                        │
                                          计算：候选、确定性匹配、正式结果
                                                        │
                                          业务服务：编排、校验、发布、查询
                                                               │
                                                               └→ 小程序
```

Redis 是运行基础设施，不是第六个业务模块。实时行情适配器负责从已批准来源取数；业务服务负责编排刷新范围和结果发布；数据层定义可重建缓存接口及其有效期；规则/计算模块不直接读写 Redis。Redis 只保存临时行情、短期盘中视图和刷新租约/限流计数，MySQL 仍是事实、重置、正式计算结果和已发布数据集的唯一结构化真相源。

边界约束：

- 小程序不重算正式状态、监管期限、重置、预测资格或四项指标。
- 公告模块不写最终次数、监管标签或预测名单。
- 规则模块不抓数据，不依赖数据库或页面。
- 计算模块不联网、不自行判定公告事实、不直接发布数据集。
- 数据层保存来源证据与版本，不自行解释规则或决定产品状态。
- 业务服务是唯一产品流程编排者；单股、监控、预测从同一已发布数据集读取。

## 3. 前端模块

小程序保持现有页面结构和视觉交互，内部按页面与公共展示能力组织，不把组件拆成独立服务。主要页面为单股计算、重点监控、异动预测、规则说明、隐私与用户协议。

前端输入为同一数据集版本的接口结果，输出为查询、刷新和本地模拟操作。前端分别呈现交易状态、公告确认的监管事实、四项当前/次日计算结论及其数据状态。当前四项计算齐全且未触阈值即可确定计算安全，不等待当日公告采集结束；公告覆盖和正文状态只影响监管事实“安全”确认、10 日同向正式计次与重置依赖，不能抹掉已确定的行情计算结果。计算触及只影响预警及可能触发提示，不升级监管事实。状态标签和文案必须由接口字段驱动。唯一的本地计算是模拟计算，不能回写后端。

次日预测名单不重复展示当日已触发的同一严重规则；其他严重规则仍独立筛选。已有严重监管事实期间，3 日普通规则可能触发时也须生成关联预测卡。上述均为名单展示策略，不影响计算模块输出的任何指标，也不影响单股四项卡片。

计算触及阈值可形成对应规则预警，但不能创建监管公告事实、升级监管状态或产生重置边界。公告模块输出并确认的普通异动事实，按方向产生一次 10 日同向正式计次，并在规则审定的生效日重置 3 日偏离；严重异动事实按规则审定的生效日重置全部四项。行情计算是对公告事实的核验，不是计次或重置门槛；不一致属于系统计算/数据问题，不能压掉公告事实或其效果。业务服务不得把行情“触发”布尔值当作 reset 命令。

首次进入异动预测或单股详情时，前端触发两个顺序逻辑阶段：S1 取得并固定当前最新已发布股票池数据集的 dataset/pool/rule/time context，不重建候选池；预测页只按交易时段判断是否执行 S2，S2 请求一次已发布名单内证券及所需指数的实时行情；单股页除交易时段外还须确认所选证券可交易，再请求所选证券及对应指数行情，形成带时间戳的盘中覆盖层。预测 S2 仅使用 S1 固定的已发布名单，不扩池、不盘中重建或重新筛选名单。非交易时间不请求实时行情。两页面使用相同编排，且不依赖下拉刷新。

刷新按每次页面进入会话去重，不使用永久首次标志。预测 S1 固定已发布名单版本，S2 仅刷新该名单及对应指数，允许首屏优先和名单内分批；不增加盘中全市场筛选、不扩充名单、不重算次日。单股仅刷新所选证券及对应指数，不反向补入预测名单。

单股页顺序为股票状态卡、四项预警卡、模拟计算卡。预测页是相同结果的筛选视图；若预测项存在，单股四项中必须有同一规则、日期、数值和方向的对应结果。

## 4. 后端核心模块

### 4.1 数据模块

**职责：** 接入并对齐证券身份、板块和指数映射、日行情、盘中行情、交易日历与计算结果；执行数据质量检查；提供公告模块使用的持久化接口；保存公告模块提交的结构化事实和结果；管理候选与已发布数据集版本。数据模块不抓取或解析公告正文。

**来源职责：**

| 来源 | 用途 |
| --- | --- |
| Tushare 日频 | 历史日行情、指数、证券资料、交易日历、`suspend_d` 等静态盘后数据 |
| 盘中实时行情 | 每批最多 100 只；腾讯优先，新浪补缺，东方财富再补缺；记录逐证券/指数实际 source、quote time、失败和回退链。Tushare 不作为盘中源 |
| 巨潮资讯 | 公告模块的当前主源，按栏目/关键词采集；不得宣称全量覆盖 |
| 交易所、上市公司官方页面 | 公告模块的补充、核验以及关键事实来源 |

数据层持久化行情、身份映射、日历、公告链接与正文证据、监管事实、重置边界、同向事件、四项结果和发布版本。MySQL 保存结构化数据；公告 PDF 沿用冻结版实例临时缓存，不使用 Redis/COS 存储。监控列表由服务端签发 5 分钟 HMAC 阅读凭证，绑定受信来源 URL 与监管结束日；任一实例都可验签后从白名单来源按需重取，不能接受客户端任意 URL。`MONITOR_PDF_TOKEN_SECRET` 至少 32 字节并独立于 S1 密钥。PDF 代理初始工程护栏为单文件最大 `20 MiB`、连接超时 `5s`、读取空闲超时 `10s`、总下载期限 `30s`；真实样本和并发验收后写入版本化配置并冻结。代理校验来源主机/重定向、超时、大小、PDF 文件头后原子写入本机缓存，再提供小程序内下载。重取失败返回明确不可用，不影响事实；展示期结束清理临时 PDF，保留公告事实、正文证据和来源信息。

数据层的规则证据实体按 `rule_version + rule_key` 保存来源类型、来源 URL/条款定位、必要摘录与内容哈希、适用范围、生效日期、审核状态及证据 ID；规则包必须显式引用证据 ID，缺失/冲突/未审核的必需证据阻断对应规则包发布。公告 PDF 阅读范围与产品定义一致：普通异动公告（包括普通异动风险提示/股票交易异常波动）、严重异动、退市整理支持可信 PDF 的小程序内阅读；与本产品事实无关的一般风险提示不提供入口。

### 4.2 规则模块

规则是无副作用、带版本的唯一口径源。输入证券类型、目标日期及规则版本，输出适用的阈值、指数、区间、计次条件、颜色等级、重置范围、状态组合、交易时间切换和预测筛选政策。

规则以已批准的 `product_policy` 为本版本唯一执行口径。当前产品基准映射为：沪市主板 `000002.SH`、深市主板 `399107.SZ`、创业板 `399102.SZ`、科创板 `000688.SH`、北交所 `899050.BJ`；映射以版本化规则证据表为准。证据表覆盖四板块核心参数、基准映射、公告重置、关键停复牌/复牌基线和除权边界，并记录产品规则依据、生效日期、内容哈希和夹具；条目缺失或冲突时阻止受影响规则包发布，不回退到其他指数。使用少量可复算案例验证关键边界，不建设全市场逐证券逐日法规数据库。规则说明页、正式计算、模拟计算输入和接口都引用同一规则版本。

规则证据由数据模块持久化，至少包含规则版本/规则键、来源类型（`product_policy`）、产品依据、可选补充 URL、内容哈希、夹具引用、适用范围和生效日期、审核状态及审核记录；规则包显式引用证据 ID。缺失或冲突时仅阻断受影响规则包，不用其他板块或指数兜底。

### 4.3 计算模块

计算模块按纯函数/可重放作业设计，输入固定行情、证券属性、日历、规则版本、已确认公告事实和生效重置边界，输出带证据的候选与正式结果。

计算分阶段：

1. **行情候选计算：** 逐项产生 3/10/30 日偏离及 3 日事件候选，包含区间、方向、收益、阈值和输入完整性。
2. **事实匹配：** 接收业务服务编排传入的公告模块确认事实，按证券、日期区间、方向、事实类型和证据标识执行确定性匹配。
3. **正式结果计算：** 公告正文确认的每项独立普通异动事实按公告方向计入 10 日同向，并按正式生效日重置 3 日偏离；对应行情候选用于一致性核验。若不匹配，生成计算/数据差异记录并修正，不抑制计次或重置。应用严重公告重置和停牌复牌边界，生成四项当前/次日结果及理由。其他公告仅在正文确认本产品已定义的具体事实时，更新相应事实；未确认具体事实不新增监管状态、异动计次或重置。

同一输入和规则版本必须得到相同输出。重置计算是计算模块内部职责：规则定义条件，公告提供事实，计算确定边界，数据持久化。严重规则指标各自独立，触发一项不得短路其他项。

### 4.4 公告模块

公告模块是唯一的公告采集责任方：从来源取列表和正文，抽取证券、披露日、事实区间、方向、普通/严重异动类型、监管期限、停复牌/终止上市事实及来源证据。负责去重、公告更正关联、正文完整性和事实置信状态；数据模块只接收并保存其输出。

公告输出为原始材料引用、正文证据、结构化事实和匹配所需字段。无法读取、未找到、源失败、来源冲突是不同结果。公告模块不直接增加 10 日同向、不执行重置、不改监管状态；正式事实经业务服务编排，并由计算按规则使用。

同一公告正文可能描述多个不同日期的 3 日偏离类普通异动事实；每项事实只有在正文可独立定位时才形成独立 `fact_id`，使用正文区间最后一个交易日 `fact_end_date` 作为 10 日窗口唯一入窗日。仅写“多次”但无法定位各事实区间时待核验，不由解析器猜拆；换手率类、单日偏离类等普通事件不计入 10 日同向。每项已确认事实直接按正文方向计次；正文未写方向时，由计算模块基于正文精确区间、对应行情、规则指定基准和固定规则版本补足。行情候选只用于补方向、核验并发现系统差异，不是已确认事实计次/重置的门槛。一个事实被多来源转载只是一项事实，多一条证据，不多计一次。公告批次完成条件按“来源 × 公告类型/栏目 × 交易所/板块 × 查询日期范围”记录：分页游标到末页、预期分页/总量校验通过、查询水位覆盖目标时段、关键来源请求成功，且不存在未处理的可定位失败；不满足任一项时，未找到只能标记待核验。仅对完成并通过覆盖校验的具体范围，才能确认该范围未发现新增事实，不得外推为全市场所有来源均无公告。

### 4.5 业务服务模块

业务服务负责前台查询和后台更新两类产品流程，是模块间唯一编排层。

**后台更新/发布流程：**

1. 建立本次候选数据集和目标日期，固定数据源截止时间。
2. 读取/更新行情、证券资料与交易日历，做证券、指数和日期对齐检查。
3. 采集公告列表与正文；保留来源覆盖情况及失败/待核验项。
4. 调规则模块解析适用规则，调计算模块生成行情候选。
5. 将候选和公告确认事实交给计算模块：公告事实独立产生普通计次和对应重置边界；候选计算用于校验公告所述区间与方向，发现差异则进入计算/数据异常处理，不阻断公告事实。随后形成四项正式结果和统一状态。
6. 运行完整性、一致性和跨页面契约检查；保存所有输入引用、规则版本、事实证据和结果。
7. 通过后原子发布 `dataset_version`；失败则保留上一已发布版本并提供数据更新时间/过期说明。

业务服务不得在 API 层重新实现规则，不得由单股、重点监控、预测各自生成不同状态。它只编排匹配调用，不复制匹配算法。三页读取同一已发布收盘数据集，并使用同一时点、同一来源版本的盘中行情覆盖层；盘中结果作为带行情时刻的临时结果，不覆盖收盘发布集。

收盘数据构建与盘中刷新是两个流程：前者按正式输入生成全市场基础结果及预测名单；后者只更新名单内证券或单股所选证券的当前结果，不执行全市场扫描或 next 重算。预测首次打开在一个会话内按顺序执行两个逻辑阶段（不限定 HTTP 请求数）：S1 刷新并读取当前最新已发布股票池数据集，固定 `dataset_version + pool_version + pool_hash + pool_count + rule_version + time_context_id`，不重建/重新筛选名单；S2 仅在交易时段读取该固定名单内实时行情及所需指数。S1 失败不得启动 S2；S2 不得增删名单。跨页一致性在相同读取上下文下验收，不承诺独立网络请求同帧到达；短期共享实时视图、读取令牌及缓存协议详见开发设计，不新增业务模块。

业务服务按目标业务日过滤持续严重监管事实的有效期；未来才生效的严重事实不能提前覆盖当前状态，已失效事实不能继续进入重点监控。普通异动公告事实直接产生计次和 3 日重置，但不自动形成持续监管期或重点监控资格。该有效期过滤不删除 10 日同向事件：正式计数仍按 `fact_end_date`、严重清零边界和事实更正/撤回处理。缺少某个窗口的历史行情时，只让依赖该窗口的结果不可用，不得让预测接口的空规则把单股结果改成安全。

质量门禁包括来源新鲜度、交易日完整性、证券/指数映射、公告批次覆盖、正文可读率、`event_without_fact` 和 `fact_market_mismatch` 两类独立指标；前者表示正式计次事件没有公告事实，必须阻断发布，后者表示公告事实存在但行情复算有差异，保留计次/重置并生成修正任务与告警，不得被前者门禁混淆。重试、回退、补采、告警和重放用于把数据不可用降到最低，但不能把失败改写成安全。

**查询流程：** 单股、重点监控、预测固定读取同一个已发布数据集；业务服务负责权限/参数校验、页面筛选和字段组装。预测筛选不能改变底层四项结果。

## 5. 数据版本与一致性

一个 `dataset_version` 固定行情、证券资料、日历、公告事实、重置边界、计算结果和 `rule_version` 的引用关系。它不要求复制全部历史原始数据，但必须能重放当次结果。

发布前校验至少包括：

- 三个主要页面使用同一版本和业务日期；
- 单股与预测的共同规则结果在数值、方向、阈值、日期和触发状态上相同；
- 四项结果分别保留可用性和缺因，单项缺数不清空其他项；
- 公告事实与同向事件一一关联，有证据、区间、方向和匹配状态；
- 重置基线可追溯到公告/停复牌事实及生效日；
- 未核验事实、行情源失败和版本过期不能被压成安全或 0 次。

单股、监控、预测不得各自缓存成不同事实。缓存若存在，键必须包括数据集版本、证券、页面日期角色和规则版本，发布后可失效或自然淘汰。

新版本盘中视图在同一 `read_token`/`realtime_view_id` 下共享；该令牌固定数据集版本、目标交易日、页面日期角色、规则版本和视图修订。令牌外的独立刷新可获得较新视图，不承诺跨请求同帧，但必须返回各自真实行情时间。Redis 缓存只能加速已定义的取数与展示，不能改变上述版本和一致性契约。

## 6. 状态和时间责任

统一状态模型由规则定义、计算形成、业务服务组装、数据版本保存、前端展示。四组分别是交易状态、由公告事实决定的监管/风险提示状态、四项当前/次日计算预警和数据状态。普通异动态只表示有效普通风险事实，不代表已进入严重监管或重点监控；严重状态才对应有效严重监管事实。行情触及只产生预警，不改变公告确认状态。不可用不是第五种监管状态，未知状态仅属于交易状态。

时间由交易日历和目标数据集确定，不由页面本地时钟独立推断。业务服务在 09:00 切换 D/N 角色，盘中读取带时戳实时行情，15:00 后等待收盘集；周末/休市使用最近完成交易日和下一交易日。公告披露日、公告正文事实区间、市场数据复算的实际触发日、`fact_end_date`、重置生效日和监管起止日分别保存。严重异动公告日期审定以正文事实和经核验触发数据为核心，公告页面日期只作证据之一；D 日收盘触发且当日晚间公告确认同一事实时，D+1 为重置生效日。停牌不生成虚构日收益，复牌以适用规则确定基点；旧收益不跨停牌拼接。普通事项停牌复牌保留已确认 10 日同向事件；因严重异动停牌或严重异动公告后停牌，复牌时与严重重置一并清零同向事件。

## 7. 部署形态和基础设施

- 后端初期一个代码库、模块化单体；API 和重任务可按进程角色分开部署，不形成独立微服务。
- 保留微信云托管、MySQL、Tushare 和腾讯云 Redis。当前冻结正式版不依赖 Redis；新版本通过云托管同网络的连通性验收后启用 Redis 实时能力。
- Redis 是可重建的临时协作存储，不新增业务模块：职责限于短时行情缓存、盘中视图共享、跨实例同范围刷新合并及按需上游限流；绝不保存唯一监管事实、正式重置或正式数据集，也不决定任何规则结果。
- Redis 故障不会回退为逐实例独立访问行情源，也不读取后端实例本地实时副本。正式查询仍读取 MySQL；S2 可持久排队等待 Redis 恢复，或明确返回 `failed/realtime_unavailable`。前端可保留本机已渲染且带原始报价时间的数据作为 stale 画面，但不得把它用于当前触及/安全判定。不影响 MySQL 正式读接口。缓存内容带版本和报价时间，写入采用有界 TTL 与原子视图指针切换。
- Redis 租约只负责去重，不是最终写入授权。每个实时刷新 scope 使用 MySQL 持久化单调递增 fence；发布前以事务/CAS 校验最新 fence、owner、任务有效状态和目标 dataset/pool/rule 版本。MySQL 记录最终 active view id/generation，Redis 仅保存该精确版本的可重建视图与活动加速引用。切主/短分区导致 Redis 租约状态丢失时，新 worker 必须取得更高持久 fence；旧 worker 恢复后写入必须被拒绝。读取端按 MySQL 授权的 `realtime_view_id + generation` 校验 Redis 对象；对象丢失或版本不符就返回 queued/unavailable/context_expired，不静默换新视图或逐实例直连上游。
- 持久 fence/active view 槽位按完整读取上下文隔离，包含 dataset、pool version/hash、rule hash、time_context、目标日期、role、market phase、scope 成员哈希、source policy 和 quote bucket。行情上游请求去重可使用更粗的证券/名单 scope，但不得复用持久 fence key 来代替完整上下文 key。
- 启用门槛：云托管容器内 PING、TTL 读写、内存策略/容量、租约互斥、过期接管、持久 fence 拒绝旧持有者、跨实例并发、Redis 短分区/failover、报价时间偏差及 Redis 故障演练全部通过。不能仅以控制台显示“运行中”认定应用已接通。
- 事务、任务幂等、旧任务写入保护、来源限流、备份、可观测性和告警属于实施文档的工程要求，本稿不指定表结构和迁移步骤。

## 8. 评审及完成标准

此架构设计通过评审的条件：

1. 数据、规则、计算、公告和业务服务各有唯一职责，公告与计算双向匹配不产生互相写最终状态的环。
2. 10 日同向可从公告正文事实追到行情计算、匹配证据、事件次数和窗口进出。
3. 普通/严重公告及停牌复牌边界可重放，监管事实和计算触发不混为一谈。
4. 单股、重点监控、预测只消费同一已发布数据集；预测只是筛选，不产生孤立状态。
5. 数据失败、公告正文待核验和证券历史不足有各自缺因；公告待核验不会伪装成监管事实安全，也不会覆盖行情依赖齐全的计算安全。
6. 数据源覆盖边界、临时 PDF 缓存生命周期、Tushare 盘后静态数据与当前盘中实时链路、预测名单刷新范围在产品、架构与开发设计中保持一致。
