# 异动查查模块化架构与迁移计划

> 架构基线：`ARCH-2026-10-24.1`
> 产品规则基线：`RULE-2026-10-24.1`
> 状态：目标边界已定；代码正按阶段迁移，不表示重构已全部完成。

## 1. 架构决策

系统先划分为三个一级边界：

1. **小程序前端**：页面、交互、展示、离线/错误体验，以及唯一允许的本地 T+N 模拟。
2. **后端应用**：公告、规则、计算、重置、产品用例、API、后台任务和运维编排。
3. **数据平台**：所有原始输入、规范化事实、行情、规则结果、监管状态、质量状态、任务状态和版本元数据的权威存储与读取。

规则解释与机器参数由规则模块维护；计算模块只消费规则定义；重置模块消费已确认事实并生成规则计算边界；数据模块拥有数据及其当前状态，不再设置独立“状态投影”服务。数据状态是权威数据模型的一部分，不是 API 或页面临时拼出来的副本。

```text
外部行情源 ─┐
公告来源 ───┼─> 数据接入与质量登记 ─> 公告事实 / 行情标准数据
交易日历 ───┘                           │
                                        ├─> 公告模块解析并输出候选/确认事实
                                        │                 │
                                        │       行情核验 + 规则定义
                                        │                 │
                                        └────> 数据账本 <─┘
                                                   │
                                      重置机制生成计算边界
                                                   │
                                  计算模块按规则独立计算四项指标
                                                   │
                                      数据模块保存结果与当前状态
                                                   │
                         产品用例（详情/监控/预测） -> API -> 小程序
```

## 2. 前端模块

| 模块 | 职责 | 禁止事项 |
| --- | --- | --- |
| 应用壳与导航 | 生命周期、Tab、全局主题、页面进入/离开 | 处理公告和规则事实 |
| 单股功能 | 搜索、股票状态与四项结果、监管事实展示 | 重算生产异动、从标题推断监管 |
| 本地模拟 | 将后端提供的基础收益向量与用户输入计算 T+N | 写回服务端或生产数据 |
| 重点监控功能 | 分段筛选、刷新、卡片和公告入口交互 | 自行判断监管期限或公告类型 |
| 异动预测功能 | 当日/次日切换、候选卡、盘中刷新结果 | 重新筛选/计算后端候选或删除已触发卡 |
| 规则与隐私页面 | 展示后端/随包发布的版本化文本 | 在 UI 代码里复制规则参数 |
| 共享 UI | 分段控件、风险标签、卡片、空态、时间/百分比格式化 | 混入业务状态判定 |
| API 客户端 | 路径、参数、超时、错误响应和 DTO 归一化 | 在页面内直接拼 URL 或改变规则结果 |

目标前端结构：`app/`、`features/stock/`、`features/monitor/`、`features/prediction/`、`features/rules/`、`shared/components/`、`shared/format/`、`shared/api/`。现有小程序先以 `pages/` + `utils/` 兼容结构运行，按功能边界迁移，不一次性改路由和页面生命周期。

## 3. 后端模块

| 模块 | 输入 | 输出/所有权 | 主要职责 |
| --- | --- | --- | --- |
| API / Transport | HTTP 请求 | 稳定 API DTO | 参数校验、认证边界、响应/错误包装；不计算规则 |
| 产品用例 / Application | API 命令、查询 | 页面业务结果 | 编排单股详情、监控读取、today/next_day 预测、刷新；不拥有规则定义 |
| 公告模块 | 巨潮、18.cn、中泰原始公告、附件/正文读取结果 | 原始公告、规范事实、待核验事实、采集覆盖状态 | 来源适配、分页与重试、正文抽取、分类、事件去重、事实证据与来源关系；公告失败必须是失败/部分覆盖，不能变成“无事实” |
| 规则模块 | 交易所规则、板块 | 版本化规则定义与解释 | 四项规则、板块阈值、触发方向、类别等级、重置范围、展示语义的唯一来源；规则说明和机器参数绑定同一版本。当前参数与机器定义位于 `server/rules/catalog.py` |
| 计算模块 | 行情标准数据、板块规则、计算上下文 | 四项原始计算结果及证据 | 交易日对齐、收益/偏离、普通异动识别、10 日同向计数、严重规则判定、可达距离；不得获取公告或自行决定重置事实。算法位于 `server/calculations/engine.py` |
| 重置机制 | 已确认普通/严重事实、规则版本、交易日历 | `ResetDecision` 与生效边界 | 普通事实仅重置 3 日基线；严重事实按产品基线重置四项。包含事实 ID、作用范围、生效日、证据和应用版本；不删除历史账本。不得自行拉公告或计算行情。当前决策基础位于 `server/resets/decisions.py` |
| 数据模块 | 各模块写入的规范数据 | 权威仓储/快照/当前状态 | 原始公告、解析事实、待核验、交易日线、指数、证券主数据、重置账本、四项结果、监管/停牌/退市/未知状态、覆盖质量、作业状态与规则版本；提供事务、幂等、查询和重建入口 |
| 后台任务 / Jobs | 调度时间、数据版本 | 可观测任务运行记录 | 盘后行情计算、全市场预测构建、公告采集、失败重试、补抓/回放；只调用应用用例，不复制业务逻辑 |
| 运维 / Observability | 数据与任务运行 | 健康、告警、审计 | 源覆盖、延迟、重建进度、失败原因、数据集版本、规则版本和线上验收指标 |

目标后端结构：

```text
server/api/                 HTTP 路由与 DTO
server/application/         产品查询/命令用例
server/announcements/       来源适配、正文解析、事实确认
server/rules/               规则定义、版本、解释
server/calculations/        纯计算引擎
server/resets/              重置决策和计算上下文
server/data/                数据契约、仓储、账本、当前状态
server/jobs/                调度与后台任务入口
server/observability/       健康、质量和审计
```

`MarketService`、`OfficialMonitorService` 在迁移期作为兼容门面保留；新逻辑进入上表的单一职责模块，逐接口迁移后再移除门面，禁止先大规模改名再补测试。

## 4. 公告—规则—计算—重置—数据协同

1. **公告输入**：适配器按来源拉取原始公告及正文/附件，记录来源、分页游标、抓取时间、成功/部分失败状态。部分来源失败不丢弃成功来源结果。
2. **公告解析**：解析器输出带原文链接、正文哈希、公告日期、证券、事件类型、方向/日期证据和解析状态的事实候选。无法读取或无法判断时写待核验，不等价于“没有事实”。
3. **普通事件方向核验**：公告事实与公告日期对应的股票/指数共同交易日行情交给规则计算能力核验。普通异动公告对应的三日方向由收盘行情确定；不满足/无法对齐时保存未确认及原因，不静默增加同向次数。
4. **事实入账**：已确认和待核验分别幂等写入数据账本；公告 ID/URL 是稳定来源键。重复采集更新状态，不重复计次；原始证据保留以支持回放。
5. **重置决策**：重置模块只读取已确认的公告事实、规则版本和交易日历，产出有据可查的作用范围和 `effective_from`。事实原件不改写、不删除。
6. **最终计算**：计算模块读取市场数据与重置上下文，分别输出 3 日偏离、10 日同向、10 日偏离、30 日偏离；四项互相独立，并附实际窗口、方向、输入版本和质量。
7. **统一数据状态**：数据模块在同一版本/批次保存四项结果、公告监管事实、停牌/退市/风险警示事实、未知原因、源覆盖和有效状态。当前状态由这些权威数据在数据域聚合生成；API 不另建状态投影。
8. **产品读取**：详情、监控和预测用例从数据模块取同一快照。产品资格只决定是否展示候选，不改变事实、指标或触发状态。API 转成 DTO，前端原样呈现。

## 5. 统一数据契约

所有数据以 `YYYYMMDD` 作为内部交易日主键，展示日期才转换。关键实体：

- `SourceRun`：来源、查询范围、分页覆盖、开始/结束时间、成功/部分/失败。
- `AnnouncementRaw`：来源 ID、URL、标题、原始正文引用/哈希、披露日期、抓取日期。
- `AnnouncementFact`：公告事件类型、证券、方向、事件截止日、证据、解析器版本、确认状态。
- `ResetDecision`：事实 ID、重置类型、作用指标、规则版本、生效交易日、决策状态。
- `MarketSeries`：证券/指数、交易日、收盘及所需行情、数据源与质量。
- `RuleResult`：证券、基准日、四项独立结果、实际窗口、证据、规则版本、计算版本。
- `StockCurrentState`：独立保存 `marketRiskState`、`regulatoryState`、`tradingState`、行情覆盖状态、公告事实覆盖状态和总体 `dataState`，连同规则结果和来源链接；`status` 只是可选摘要，不能覆盖这些轴或删减四项结果。行情数据完整性和公告源完整性不可混成一个布尔值。
- `DatasetSnapshot`：today/next_day 目标日、行情基准、规则版本、计算版本、条数、完整性及可见状态。

任何状态必须指向事实/数据源或明确的数据质量原因。缺少事实只在公告采集覆盖充分且读取成功时才能解释为空；源失败、正文失败、未对齐行情均保持 `partial`/`pending`/`unknown`。

## 6. 依赖约束

```text
前端 -> API DTO
API -> Application -> Data + domain services
Announcement -> Data
Calculation -> Rules + normalized market input
Reset -> Rules + confirmed facts + trading calendar
Application -> Calculation + Reset + Data
Jobs -> Application use cases
```

- 规则定义不依赖数据库、HTTP、公告采集或小程序。
- 计算模块不依赖公告服务、SQL 或页面 DTO。
- 公告模块不直接修改行情指标；只输出事实与证据。
- 重置模块不做行情计算，只给出明确的重置边界。
- 数据模块不复制规则判断；保存规范实体和模块产出的版本化结果，负责原子发布/一致读取。
- 监控、单股和预测不能各自保存一份互不相干的状态真相。

## 7. 性能与可靠性

- 全市场行情按交易日批量加载，指数按板块只读一次；逐股计算不得产生 Tushare/API/SQL N+1 请求。
- 公告来源并行但有独立限流、超时、重试和熔断；解析与行情确认分阶段批处理。
- 数据集按 `targetTradeDate + ruleVersion + calculationVersion + sourceWatermark` 做幂等构建，临时构建后原子切换；失败保留上一成功版本并标记 stale，不发布空成功。
- 事实账本不可变、派生状态可重建；计算输入、重置决策、解析器版本均可追溯。
- 单股读取使用同一数据集版本；预测读取整批快照；盘中报价只作为请求期输入，不污染正式持久化状态。
- 缓存键包含目标日、规则版本、计算版本及必要数据水位；升级失效对应缓存，不混用旧数据。

## 8. 本地迁移阶段与验收门槛

| 阶段 | 工作 | 完成判定 |
| --- | --- | --- |
| A 架构基线 | 定义模块、数据实体、依赖方向和规则版本绑定 | 本文、PRD、测试规范一致 |
| B 核心域拆分 | 规则定义与计算算法分开；公告解析/确认与采集分开；重置决策独立；所有规范事实归数据域 | 导入依赖无环；原服务成为薄门面；每模块有契约测试 |
| C 读写统一 | 单股、监控、预测从同一数据仓储读取版本化事实和当前状态 | 同一快照对账一致；失败不会显示为安全 |
| D 回放和性能 | 建立原始事实回放、全市场重算、旧新差异审计和批量性能基准 | 全市场差异可解释、无单项规则缺失、性能达标 |
| E 发布验收 | 完整回归、数据集重建、健康/API/真机验收、版本同步 | 所有环境规则版本和数据集版本一致 |

当前代码已先落地规则目录、独立计算包、数据事实账本/股票状态和重置决策上下文等边界；公告子模块、全量数据仓储、应用用例和 API 包尚未完成迁移。本轮只完成 A 和 B 的部分起步，不代表数据迁移、全市场重算或线上验收完成。每一阶段均先在本地验证，达到门槛后再提交/部署。
