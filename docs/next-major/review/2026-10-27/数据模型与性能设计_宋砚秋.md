# 异动查查 vNext 数据模型与性能设计评审

> 评审人：宋砚秋（阿客实验室研发部 · 数据库设计与优化）
> 评审日期：2026-10-27
> 评审对象：`PRD-NEXT-20261027.6`、`ARCH-NEXT-20261027.5`、`模块化架构评审回执_2026-10-27`
> 代码基线：`server/`（1.0.x 现网实现，抽查文件见文末「证据索引」）
> 本文只做评审与设计建议，**未修改任何现有代码或文档**。

---

## ① 总评结论

**总判：PRD 与架构文档在「规则口径、状态模型、版本化」三件事上已收敛到可实施的程度，但现网 1.0.x 的数据层与该目标之间存在「结构性落差」，不是补字段能解决的。**

具体判断分三层：

**1）目标是对的，但现网数据结构承载不了。**
PRD §10 要求每个结果携带 `dataset_version`、`rule_version`、行情截止日、事实截止日、来源、状态和缺因，并要求「历史版本可重放」。现网 MySQL 只有 8 张表，其中最核心的 `prediction_dataset` 把全部预测卡片塞进一个 `items JSON` 列（`market_calc_repository.py:156`），既无 `dataset_version` 列，也无行式结果表，无法做「单股与预测共同规则结果一致」这类跨页对账（PRD §11 验收标准 #4）。

**2）最关键的两个产品口径，在 DB 约束层完全没有落点。**
- 「同一事实多源转载只计一次」：现网事实主键 `source_id = sha256(url)`（`monitor_service.py:1133`、`1189`、`1217`），URL 不同即为不同事实，多源转载必然重复计次。
- 「单公告多事实分别计次」：现网一个公告 URL 只能产生一个 `source_id`，要靠调用方手工拼 `"ordinary-reset:" + source_key` 这类字符串前缀造第二个 ID（`monitor_service.py:1088`），无约束保证，属于隐性契约。

**3）「不可重放」是当前最大的工程风险。**
现网明确不保存原始日线，只保存滚动 30 天收益向量 JSON（`market_calc_repository.py:4` docstring「不保存原始日线、成交量或换手率」，表定义见 `101-112`）。当公告事实更正、板块/指数映射变更、规则版本升级时，无法用同一输入重算出新结果——只能"原地覆盖"，而原地覆盖与 PRD §10「不允许页面自行推断、历史版本可重放」直接矛盾。

**4）文档与代码存在事实性出入，需先修文档再设计。**
PRD §9.3（第 220 行）与 ARCH §7（第 139-140 行）都声称「保留……腾讯云 Redis 当前集成」，但 `server/requirements.txt` 无 Redis 客户端、`server/` 全量代码无 redis 引用，且 `docs/生产操作手册.md:7-8` 明确写着「当前后端没有 Redis 客户端，也不依赖云托管中的 Redis 环境参数」。评审回执（第 28 行）也把「命名与迁移方案」列为待验证项。**建议：先把 PRD/ARCH 中关于 Redis 的措辞从「当前集成」改为「可选、待评估」，再进入数据层实施。**

**放行建议：** P1 共 10 项，**建议 P1-1～P1-5 在进入开发实施文档编写前必须定稿**（它们决定表的主键与分区键，后改代价极高）；P1-6～P1-10 可与实施并行，但必须在首个灰度数据集发布前完成。

## ② P1 阻塞问题清单

> P1 定义：不改则 vNext 数据层无法落地，或上线后会产生错误监管结论（把"不可用"变成"安全"、把"一次"计成"多次"）。

### P1-1 事实幂等键含来源标识，导致「多源转载重复计次」

**证据：**
- `server/services/monitor_service.py:1133` `source_id = hashlib.sha256(source_key.encode("utf-8")).hexdigest()[:24]`，其中 `source_key = announcement["url"]`（1132 行）
- `server/services/monitor_service.py:1189` / `:1217` 同样用 `sha256(alert["url"])`
- `server/data/fact_ledger.py:105` `_source_id` 的兜底材料为 `symbol|announcementDate|title|sourceUrl`——**同样含 sourceUrl**
- `server/data/fact_ledger.py:66` `source_id TEXT PRIMARY KEY`

**问题：** PRD §4.3（第 107 行）「同一事实被多来源转载或重复采集只计一次」，验收标准 #11 再次确认。但当前主键直接由 URL 派生，巨潮、交易所官网、18.cn、中泰转载同一份公告时 URL 必然不同 → 生成多条 `announcement_fact` → 10 日同向计数被放大。

`engine.py:355-405` 的 `confirmed_same_direction_event_ledger` 试图用 `(event_date, direction, content_hash)` 归并，但存在两处失效：
1. `content_hash` 来自 `sha256(title\nbody)`（`monitor_service.py:1094`），不同来源 PDF 抽取的正文文本不同 → hash 不同 → 不归并；
2. 当 hash 不稳定时（第 393 行 `stable_hash` 为 False），退回 `source_id or (event_date, direction, start_date)`，而 `confirmed_events` 中 `startDate == endDate == event_date`（`market_service.py:1958-1959`），反而是**不稳定 hash 才会归并**——与代码注释「Cross-source copies are the same fact only when a stable announcement body identity is available」的意图正好相反。

**建议改法：**
- 拆成两层身份：
  - `fact_key`（事实身份，跨源稳定）= `sha1(ts_code | fact_type | fact_start_date | fact_end_date | direction)`，**不含任何来源字段**；
  - `source_id`（证据身份，源级幂等）= `sha1(source_code | source_ann_id)`。
- 在 `regulatory_fact` 上建 `UNIQUE KEY uk_fact_key (fact_key)`，`INSERT ... ON DUPLICATE KEY UPDATE` 只更新证据/置信字段，不新增计数。
- 跨源归并不得依赖正文文本 hash（抽取噪声太大），应依赖**结构化事实字段**（证券 + 事实区间 + 方向 + 事实类型）。
- 所有唯一键列必须 `NOT NULL DEFAULT ''`（MySQL 唯一索引对 NULL 不生效，这是最容易踩的坑）。

### P1-2 「单公告多事实分别计次」无约束保证

**证据：**
- `server/services/monitor_service.py:1088` `source_id = hashlib.sha256(f"ordinary-reset:{source_key}".encode("utf-8")).hexdigest()[:24]`
- `server/services/monitor_service.py:1051-1053` pending 记录同样用 `"ordinary-reset:"` 前缀拼 ID

**问题：** 一个公告 URL 只能对应一个 `source_id`。公告里描述两个不同日期的普通异动事实时，靠调用方手工加 `"ordinary-reset:"` 前缀造出第二个 ID。这是字符串拼接层面的隐性约定，DB 层无法校验其正确性，任何人漏拼/拼错就会静默丢计数或重复计数。

**建议改法：**
- `regulatory_fact` 主键改为自增 `fact_id`（或雪花 ID），来源信息下降到 `fact_evidence` 子表。
- 唯一键 `uk_fact_key` 由**结构化事实字段**生成，天然支持「一个公告 URL → 多条不同 `fact_key` 的事实」。
- 「分别计次」由 `same_direction_event.fact_id UNIQUE` 保证：N 条事实 → 至多 N 条事件，重复写入幂等。

### P1-3 不保存原始日线，历史版本不可重放

**证据：**
- `server/services/market_calc_repository.py:3-4` docstring「只保存股票基础资料、滚动收益率、已计算指标……**不保存原始日线、成交量或换手率**」
- `server/services/market_calc_repository.py:101-112` `stock_calc_base.stock_return_vector JSON`，且 `updated_at` 直接覆盖（`:618` 「在一个事务内更新当前计算数据，**不保留旧版本**」）
- `server/services/market_service.py:1124` 向量硬截断 `ordered_stock[-30:]`

**问题：**
1. 只有 30 个收益点，无法重算 30 日窗口（30 日窗口需要 31 个收盘点）之外的任何历史边界；
2. 停牌/复牌基线重置、普通/严重公告重置的生效日一旦变化，旧窗口无法重建；
3. PRD §10「历史版本可重放，不允许页面自行推断」在结构上不可能满足。

**建议改法：**
- 新建 `daily_bar` 原始日线表（见 §④-C），保存 ≥3 年（建议 5 年热数据）。
- **前复权/未复权取舍：主存「未复权收盘价 + 复权因子（`adj_factor`）」，前复权序列在读取时按当日最新因子实时换算，不落库。**
  理由：前复权序列会随每一起除权事件整体变化，若落库则同一 `dataset_version` 在不同日期重放会得到不同数值，直接破坏「可重放」。监管口径本身以实际收盘价为准（`core/models.py:54` 注释「监管口径通常优先使用实际收盘价」）。若确需固化，可在 `dataset_version` 中记录当次使用的因子快照版本号。
- `security_return_vector` 作为派生加速表保留，但仅用于查询，不作为重放依据。

### P1-4 缺少 `dataset_version`，发布不是原子切换

**证据：**
- `server/services/market_calc_repository.py:150-170` `prediction_dataset` 主键为 `(dataset_role, target_trade_date)`，无版本列；`status` 只有 `ready`
- `server/services/market_service.py:2816-2921` `_generate_prediction_datasets`：先 `save_prediction('today')` 再（下次调用）生成 `next_day`，两次独立事务
- `server/services/market_service.py:618` `upsert_market` 原地覆盖 `stock_calc_base`

**问题：** 行情基线更新与预测集发布是两个独立事务，中间窗口内：单股页读到新行情基线 + 旧预测卡片；预测页读到另一组合。这违反 PRD §9.3（第 224 行）「单股、重点监控、异动预测只能读取同一发布版本」和验收标准 #4。

**建议改法：** 见 §⑤ 两阶段发布 + 单行指针表。核心是：明细全部写入带 `dataset_version` 的行，发布动作 = 更新一行 `dataset_pointer`，事务耗时 < 50 ms。

### P1-5 10 日同向「入窗日」口径与 PRD 不一致，且窗口合并策略与 PRD 冲突

**证据：**
- PRD §4.3（第 107 行）：「事件唯一归属日为公告正文所述异动区间的最后一个交易日（`fact_end_date`）」；PRD §11 验收 #1：「重叠公告事实可分别计次」
- `server/services/market_service.py:488-491`：窗口过滤用的是 `item.start_date`（`recent_start <= item.start_date <= recent_end`），**不是 `end_date`/`fact_end_date`**
- `server/calculations/engine.py:302-303` docstring：「A continuous run of overlapping windows in one direction is **one occurrence**」，`:338-345` 实现把重叠窗口合并为 episode

**问题：** 两处都与 PRD 相反——入窗日用了区间首日而非末日；重叠窗口被合并为一次，而 PRD 要求「分别计次」。在长假、连续异动场景下这两种口径会给出不同的 10 日同向次数（一个偏小一个偏大），直接影响"严重异动"红牌判定。

**建议改法：**
- 表结构中把 `fact_end_date` 作为一等公民（`regulatory_fact.fact_end_date`、`same_direction_event.fact_end_date`），窗口过滤条件统一为 `fact_end_date BETWEEN window_start AND window_end`。
- 窗口合并策略改为：**只对「同一 fact」的窗口去重（由 `same_direction_event.fact_id UNIQUE` 保证），不对不同 fact 做 episode 合并**。若产品确实要保留"连续 episode 视为一次"的口径，必须写进 `rule_version` 配置项并显式标注为产品推断（PRD §4 第 74 行要求区分官方明文与产品约定），且新旧口径各占一个 `rule_version` 以便对账。
- 迁移期用影子计数：同时按两种口径计算并落 `quality_check_result`，对比差异后再切。

### P1-6 预测页完全排除「10 日同向」卡，与 PRD §7 冲突

**证据：**
- `server/services/market_service.py:266-271`
  ```python
  def _prediction_item_allowed(self, item, monitored_codes, scope="") -> bool:
      rule_key = str(item.get("ruleKey") or "")
      # 同向次数仍参与单股状态判断，但不再生成或展示预测卡片。
      if rule_key == "same_direction_10d":
          return False
  ```
- `server/services/market_service.py:3106-3109`：`rules` 列表初始只含 `severe_10d`、`severe_30d`，`same_direction_10d` 从未进入候选

**问题：** PRD §7（第 176 行）明确要求「预测只筛选严重异动结果：**10 日同向**、10 日偏离、30 日偏离当前已触发或在目标日可能触发」。现网实现把 10 日同向整体排除在预测池之外，导致：
1. 预测页缺失一个严重异动维度；
2. 单股页展示四项、预测页只展示两项，与验收标准 #4「单股、重点监控、预测同一数据集、规则版本和结果」的可对账性要求相悖（虽然方向是"预测是单股的子集"，但 §7 已明确列出三项严重规则）。

**建议改法：**
- 若产品确认排除，需在 PRD §7 中删除「10 日同向」并说明原因（例如"事件数无法给出连续阈值距离，不适合距离式预测卡"），并同步更新验收标准；
- 若保留，则 `metric_result` 中 `same_direction_10d` 的 `date_role='next'` 项需定义"可能触发"的计算口径：当前计数 + 1 ≥ 阈值 且 窗口内存在一个未匹配的 3 日计算候选，则 `status='possible'`；否则 `safe`。
- **无论哪种，都必须在 `rule_version` 中显式记录口径**，避免实现与文档再次漂移。

### P1-7 公告与事实库跑在 SQLite 容器临时盘上，与云托管多实例部署冲突

**证据：**
- `server/services/monitor_service.py:62` `MONITOR_DB_PATH` 默认 `/tmp/stock-abnormal/monitor.db`
- `server/data/fact_ledger.py:14` `import sqlite3`；`:50-54` 在 `Path` 下建库
- `server/services/monitor_service.py:195` `MONITOR_PDF_DIR` 默认 `/tmp/stock-abnormal/monitor-pdf`（PDF 落临时盘，非对象存储）

**问题：** 微信云托管多实例 + 滚动发布时，容器临时盘不共享、不持久。事实账本（PRD §6「先入账，再由规则和计算使用」）会随容器重启丢失或在不同实例间不一致；PRD §6 与 ARCH §4.4 要求的对象存储地址/哈希/清理记录也不存在。回执第 31 行要求的「匿名事实计数、生产必须为 0」因此无法审计。

**建议改法：**
- 公告原始、正文证据、监管事实、事件账本、重置边界全部迁到 MySQL（与 `prediction_dataset` 同库），删除 SQLite 依赖。
- PDF 二进制迁对象存储（COS），MySQL 只存 `pdf_object_key` / `pdf_sha256` / `pdf_size_bytes` / `pdf_url`；清理走 `pdf_cleanup_log` 留痕（PRD §6 第 168 行、验收 #13）。
- 迁移期保留 `MONITOR_DB_PATH` 只读兼容，用 `prediction_migration_status` 同款开关（`market_calc_repository.py:24-27`）做灰度下线。

### P1-8 三个互不相同的「规则版本」标识符共用一列

**证据：**
- `server/rules/catalog.py:14` `RULE_VERSION = "RULE-2026-10-24.1"`
- `server/services/market_service.py:62` `PREDICTION_RULE_VERSION = "v67"`
- `server/services/monitor_service.py:45` `MONITOR_RULE_VERSION = "2026-10-zts-effective-date-cninfo-official-ordinary-event-direction-fact-ledger-ocr-v28"`
- 落库列：`prediction_dataset.rule_version VARCHAR(128)`（`market_calc_repository.py:209` 注释「历史 VARCHAR(40) 不足以容纳当前版本」）

**问题：** 三个概念（阈值口径版本、预测生成版本、公告分类版本）共用一个字段名，无法判断某条结果是因哪个口径变化需要重算；也无法按 PRD §4.5 要求「规则版本变化 → 新增规则版本并重算数据集」。

**建议改法（命名与迁移映射）：**

| 概念 | 新字段名 | 载体表 | 取值示例 |
| --- | --- | --- | --- |
| 阈值/板块/计次/重置口径版本 | `rule_version` | `dataset_version` | `RULE-2026-10-24.1` |
| 预测生成代码版本（仅排障用，不参与口径判定） | `generator_version` | `dataset_version` | `gen-67` |
| 公告分类口径版本 | `announcement_parse_version` | `announcement` / `regulatory_fact` | `ANN-2026-10-28` |
| 数据集版本（发布单元） | `dataset_version` | 所有明细表 | `DS-20261027-1` |

- `metric_result` 同时冗余 `dataset_version` 与 `rule_version`（避免联表），但以 `dataset_version` 为准。
- 现有 `prediction_dataset.rule_version` 迁移时按 `PREDICTION_RULE_VERSION` 取值规则映射：若值匹配 `^v\d+$` → `generator_version`；否则 → `rule_version`。

### P1-9 交易日历与停复牌无持久化，且每次审计重复打上游

**证据：**
- `server/services/tushare_client.py:169-177` `trade_cal` 仅进程内 `_cached(43200s)`
- `server/services/tushare_client.py:193-201` `suspend_d` 仅进程内 `_cached(3600s)`
- `server/services/market_service.py:600-607` 历史覆盖审计时按 10 天分块循环调 `suspend_d`
- `server/services/market_service.py:665-689` `_trade_dates` 在日历源不可用时**退化为周一至周五**——文档注释承认「绝不把自然日冒充交易日」，但代码实际就是这么退化的

**问题：**
1. PRD §9.3（第 218 行）明确要求 MySQL 保存「日历」，ARCH §4.1 也把交易日历列为数据层职责，现网无表；
2. 每次覆盖审计产生 N 次 `suspend_d` 上游调用，无缓存复用、无限流；
3. 日历降级会把节假日当交易日，直接进入窗口计算 → 错误的偏离值和错误的 10 日同向窗口。这与「不可用不得变安全」冲突（宁可 `unavailable`，也不能用错日历算出一个"安全"）。

**建议改法：**
- 建 `trade_calendar`（按交易所）+ `suspension` 表，启动时增量拉取并落库；
- **日历缺失/上游失败时不允许降级为工作日**，必须标记 `availability='unavailable'` + `missing_reason_code='calendar_source_unavailable'`；
- 覆盖审计改为只读本地表，上游调用收敛到每日一次增量任务。

### P1-10 无版本化迁移机制，schema 变更不可回滚

**证据：**
- `server/services/market_calc_repository.py:75-230` `ensure_schema()`：`CREATE TABLE IF NOT EXISTS` + 一串 `ALTER TABLE ... ADD COLUMN` 包在 `try/except Exception: pass`（194-217 行）
- `server/services/monitor_service.py:99-107` 同样的 `PRAGMA table_info` + `ALTER TABLE ADD COLUMN` 模式

**问题：** 无迁移版本号、无迁移历史表、失败静默（`except: pass`）、无回滚脚本。在云托管多实例滚动发布期间，新旧实例会同时跑不同 schema；一旦某次 `ALTER` 在生产失败被吞掉，后续计算结果会静默缺列。PRD §9.3 要求的「候选数据集通过完整校验后原子发布；失败继续提供上一成功版本」在数据层无法保证。

**建议改法：** 见 §⑧ 迁移步骤，核心是引入 `schema_migration` 表 + 向前兼容的两阶段 DDL（先加列 → 双写 → 切读 → 删旧列）。

## ③ P2 问题清单

> P2 定义：不阻塞上线，但会显著影响可维护性、成本或可观测性。

### P2-1 预测/监控结果缓存在进程内存，多实例间不一致
**证据：** `market_service.py:194` `self._prediction_cache`、`:197` `_prediction_state_cache`、`:191` `_stocks_cache`、`:193` `_daily_cache`。
**影响：** 云托管扩容到 2+ 实例时，不同用户刷到不同 `updatedAt` 与卡片集合；滚动发布期间新旧版本混跑。
**建议：** 迁 Redis（见 §⑦），进程内缓存降级为 5 s LRU，且键必须含 `dataset_version`。

### P2-2 文档声称已集成 Redis，代码与运维手册均无
**证据：** PRD §9.3 第 220 行、ARCH §7 第 139-140 行 vs `server/requirements.txt` 全文无 redis、`docs/生产操作手册.md:7-8`。
**建议：** 改为「Redis 为可选组件，仅用于可重建缓存/租约/限流，缺失不影响正确性」；ARCH §7 第 141 行已声明「本稿不指定表结构和迁移步骤」，本文即为该补充。

### P2-3 每日行情重算无任务租约，可能并发重算
**证据：** `market_calc_repository.py:126-133` `market_calc_job` 无 `lease_until`/`owner`；而 `prediction_job`（`:171-185`）有 `lease_until` 且 `claim_prediction` 用 `SELECT ... FOR UPDATE`（`:763`）。
**影响：** 多实例同时触发 `update_market_data` → 重复写 `stock_calc_base`、重复打上游（Tushare 有调用频率限制）。
**建议：** 统一到 `task_lease` 表（见 §④-J），`market_calc_job` 与 `prediction_job` 合并为一张任务表 + 一张租约表。

### P2-4 `stock_calc_base` 无历史，无法回答「昨天显示的是什么」
**证据：** `market_calc_repository.py:617-618` docstring「不保留旧版本」。
**影响：** 用户投诉与监管问询无法复现；PRD §10 可解释性要求落空。
**建议：** `metric_result` 按 `dataset_version` 保留 ≥14 个发布版本，冷数据转归档表。

### P2-5 缺因是自由文本，无法统计与门禁
**证据：** `server/data/stock_state.py:99` `data_error` 为 `str`；`monitor_service.py:1063-1067` `reason` 也是自由字符串。
**影响：** 无法按缺因聚合告警；无法在发布前阻断。
**建议：** 缺因收敛为枚举码表 `missing_reason_code`（见 §⑨）。

### P2-6 搜索走全表 `LIKE '%x%'`
**证据：** `market_calc_repository.py:244-252`，四列 `LOWER(...) LIKE %s`，`LIMIT = limit*20`，扫描 `stock_basic` 全表；随后在 Python 里做子序列排序（`market_service.py:521-559`）。
**影响：** 5500 行全表扫描，高频搜索下 CPU 浪费；且 `LIMIT limit*20` 会让"BJGF"这类首字母查询漏结果（超过 100 行候选时被截断）。
**建议：** 落 `name_initials` 列 + `KEY(symbol)` / `KEY(name_initials)`，改为前缀匹配优先；或外接轻量倒排。

### P2-7 `prediction_cache` 兼容读仍默认开启
**证据：** `market_calc_repository.py:24-27` `PREDICTION_CACHE_COMPAT_READ` 默认 `"1"`；`:136-149` 兼容建表；`:727-743` 回落读取。
**影响：** 迁移窗口被无限延长，且回落计数只在进程内存（`:28`），多实例下统计不准。
**建议：** 设明确下线日期；回落计数落 `quality_check_result`。

### P2-8 事实与快照双写，快照承载 `resetFacts`/`unresolvedFacts`
**证据：** `monitor_service.py:128-132` 先写 `fact_ledger` 再写 `monitor_snapshot`，快照 payload 内再嵌一份 `resetFacts`（`:1287-1300`）。
**影响：** 同一事存在于两处，可能不一致；PRD §6「事实先入账」被快照 JSON 稀释。
**建议：** 快照只存展示投影 + 指向 `regulatory_fact.fact_id` 的引用。

### P2-9 无分区与归档策略
**证据：** `market_calc_repository.py` 全部表无 `PARTITION BY`。
**影响：** 3 年后 `daily_bar` 超 400 万行，全量重放与历史删除变成大事务。
**建议：** 按年 RANGE 分区（见 §⑥）。

### 4.0 通用约定

| 项 | 约定 |
| --- | --- |
| 字符集 | `utf8mb4` / `utf8mb4_0900_ai_ci`；代码类列显式 `CHARACTER SET ascii` |
| 业务日期 | `CHAR(8)`，格式 `YYYYMMDD`，时区 `Asia/Shanghai`（PRD §2） |
| 时间戳 | `DATETIME(3)`，列以 `_at` 结尾，存 `Asia/Shanghai`，禁止与 UTC 混用 |

| 外键 | **不建物理外键**（云托管在线 DDL 与批量写入代价高），改由应用层 + 每日一致性校验保证 |

**前复权/未复权取舍（明确结论）：**

| 方案 | 结论 | 理由 |
| --- | --- | --- |
| 只落前复权 | ❌ 不采用 | 前复权序列随每起除权事件整体变化，同一 `dataset_version` 在不同日期重放会得到不同数值，违反 PRD §10「历史版本可重放」 |
| 只落未复权 | ⚠️ 风险 | 除权日的"跌幅"是虚假收益，若未处理会污染 3/10/30 日窗口 |
| **落未复权 + `adj_factor`（推荐）** | ✅ | 监管口径以实际收盘价为准（见 `core/models.py:54`）；读取时按当日因子快照换算前复权，换算所用因子版本号记入 `dataset_version.source_snapshot_hash`，保证可重放 |

- 表上保留 `adj_type` 维度是为了支持「监管口径（raw）」与「展示口径（qfq）」并存；默认只写 `raw`，`qfq` 行仅在需要加速时按需物化，避免双倍存储。
- **除权日处理**：`daily_bar` 增加 `is_ex_right`（或由 `adj_factor` 变化推断）标记，计算模块在该日不生成虚假收益区间，而按 PRD §4.1「不把停牌日当作上涨或下跌」的同源原则处理。

>
> PRD §4.4 只写了「公告次一交易日起重置」，**没有规定生效日落在停牌期间怎么办**。现网 `_trim_vectors_after_rule_reset` 用 `date >= reset_date` 一刀切（`market_service.py:1398-1399`）：
> ```python
> stock_trimmed = [item for item in stock if cls._date_key(item.get("date")) >= reset_date]
> ```
> 若重置生效后证券仍连续停牌，该窗口会退化为空列表 → 偏离值返回 `None` → 被上层当作"数据不足"而非"停牌中"，语义错位。
>
> **取值规则：**
> ```
> effective_date     = 公告披露日之后的第一个交易日（PRD §4.4）
> first_return_date  = min{ d : d >= effective_date
>                           且 d 为股票与基准指数的共同有效收盘日 }
>                     —— 即复牌后首个有效共同交易日；仍停牌则为 ''
> ```
> - 窗口起点与比较基点一律用 `first_return_date`；
> - `first_return_date = ''` 时，对应三项偏离结果必须置 `availability='unavailable'` + `missing_reason_code='SUSPENSION_WINDOW_INCOMPLETE'`，**禁止**输出 0% 或安全；
> - `baseline_close` / `baseline_index_close` 固定为**停牌前最后一个有效收盘价与指数点位**（PRD §4.4 原文要求），不随生效日漂移。

## 附录 A：与顾图南《架构评审与模块开发设计》的取值对齐（2026-10-27）

分工：本文负责物理表 / 索引 / 分区 / 事务 / 缓存键；顾图南报告负责模块边界 / 接口签名 / 内存结构 / 算法伪码 / 里程碑。以下 4 处为双方交叉确认后的定稿。

### A-1 事实身份锚点 —— **诊断采纳，处方驳回**

| 项 | 顾图南建议 | 本文结论 |
| --- | --- | --- |
| 诊断（正文 hash 不稳定） | ✅ 成立 | 采纳。`sha256(title\nbody)` 随 OCR 置信度抖动，不能做幂等键 |
| 处方（`fact_id = sha256(source_url)`） | ❌ 驳回 | **URL 属于来源标识**，正是 P1-1 认定的根因 |

**驳回理由**：巨潮、交易所官网、18.cn、中泰转载同一份公告时 URL 必然不同，`sha256(source_url)` 会把一件事拆成多条事实 → 10 日同向重复计次。这与现网 `monitor_service.py:1133` 的 `sha256(announcement["url"])` 是同一个错误。

**同理，`sha256(pdf_bytes)` 也不能作为跨源身份锚点**：不同来源的 PDF 由不同生成管线产出（水印、时间戳、Producer 元数据不同），**字节通常不同**。

**最终定稿（三层身份，职责不重叠）：**

| 层 | 字段 | 生成方式 | 作用 | 是否跨源稳定 |
| --- | --- | --- | --- | --- |
| 事实身份 | `regulatory_fact.fact_key` | `sha1(ts_code│fact_type│fact_start│fact_end│direction)` | **唯一幂等键**，决定"一件事" | ✅ 是 |
| 证据身份 | `fact_evidence.source_id` | `sha1(source_code│source_ann_id)` | 源级重复采集幂等 | ❌ 否（本就应区分源） |
| 内容指纹 | `fact_evidence.object_sha256` | `sha256(pdf_bytes)` | 解析缓存键 + 内容完整性/更正检测 | ❌ 否（仅限同源） |
| 解析质量 | `announcement_body.body_hash` | `sha256(body_text)` | 解析质量证据、OCR 置信度关联 | ❌ 否（**不参与幂等**） |

**归并解析顺序（唯一键无法表达"兼容则合并"，必须由解析步骤实现）：**
1. 按 `fact_key` 精确匹配 → 复用该 `fact_id`，追加证据行；
2. 未命中则按 `(ts_code, fact_type, fact_end_date, direction)` 匹配，且 `fact_start_date` 兼容（相等或一方包含另一方）→ 复用 + 追加证据；
3. 命中多条且互不兼容 → **不合并**，`confidence_state='conflicted'`，落 `quality_check_result`（`FACT_UNMATCHED`）并告警；
4. 均未命中 → 插入新 `regulatory_fact`。

> 该顺序必须实现在公告模块的**事实解析**阶段（ARCH §4.4 明确"公告模块负责去重、公告更正关联、正文完整性和事实置信状态"），不得下沉到 DB 唯一键或上浮到业务服务。

> **★ 与前端契约的对齐结论（夏小笺 §④-0.3 / ARCH §5）：**
>
> 1. **`dataset_version` 字符串格式采用 `YYYYMMDD-NN`（如 `20261027-01`）** —— 采纳前端草案，放弃我原稿的 `DS-YYYYMMDD-N`。
>    - 理由：定长 11 位、零填充，字典序即时间序，可直接用于 `ORDER BY` 与缓存键拼接；前缀 `DS-` 在上下文中冗余且会破坏纯数字前缀的可读性。
>    - `NN` 为**同一业务日内的发布序号**，从 `01` 起单调递增（事实更正、补采重算会触发同日 +1）。
>    - DB 侧另设 `dataset_id BIGINT AUTO_INCREMENT` 作为内部连接键，避免 120 万行结果表按 VARCHAR(32) 关联。
>
> 2. **关于「同一 version 内 businessDate/dateRole 是否唯一」——结论：不唯一，这是设计而非缺陷。**
>    - 一个 `dataset_version` **同时包含** `date_role='current'`（as of D）与 `date_role='next'`（for N）两组结果行；
>    - 唯一性由 `metric_result.uk_result (dataset_version, ts_code, rule_key, date_role, direction)` 保证；
>    - **版本级**的唯一约束是：`(business_date, status='published')` 全局至多一行（即同一业务日只有一个已发布版本）。
>    - 因此**前端版本守卫的正确比较对象是 `datasetVersion` 字符串本身**，不要用 `businessDate + dateRole` 复合判断，否则在正常发布下就会误判为"跨版本"。


**关系说明：**
- 一个 `dataset_version` 固定：`rule_version` + `quote_cutoff_date` + `fact_cutoff_date` + `calendar_version` + `source_snapshot_hash`；
- 所有明细表（`metric_result`、`same_direction_event`、`reset_boundary`、`regulatory_fact`）冗余 `dataset_version`，**查询以 `dataset_version` 为前缀，永不按 `updated_at` 排序取最新**；
- 发布 = 更新 `dataset_pointer` 的一行（ARCH §5「它不要求复制全部历史原始数据，但必须能重放当次结果」即由此实现）。

## ⑤ 事务与一致性方案

### 5.1 目标
1. 原子发布：要么整个新版本对外可见，要么完全不可见；
2. 失败保留上一版本，并给出 `数据更新时间` 与过期说明（PRD §9.3 第 224 行）；
3. 三个页面（单股/监控/预测）在任意时刻读到同一版本。

### 5.2 两阶段发布

**阶段 0 — 领取租约**
```sql
-- 任务租约（防止多实例并发重算）
UPDATE task_lease
   SET owner = %s, generation = generation + 1,
       lease_until = UNIX_TIMESTAMP(NOW(3)) * 1000 + %s, heartbeat_at = NOW(3)
 WHERE job_name = 'daily_rebuild' AND lease_until < UNIX_TIMESTAMP(NOW(3)) * 1000;
-- affected_rows == 0 → 放弃本次执行
```

**阶段 1 — 构建候选（不可见、可重试、全程幂等）**
```sql
INSERT INTO dataset_version
  (dataset_version, business_date, next_business_date, quote_cutoff_date,
   fact_cutoff_date, calendar_version, rule_version, generator_version,
   announcement_parse_version, source_snapshot_hash, status, previous_version)
VALUES (... , 'building', %s);
```
随后按序写入（每 1000 行一个独立事务，`INSERT ... ON DUPLICATE KEY UPDATE`）：
1. `trade_calendar` / `suspension` 增量
2. `daily_bar` / `index_daily_bar` 增量
3. `announcement` + `announcement_body` + `announcement_pdf_object`
4. `regulatory_fact`（靠 `uk_fact_key` 幂等）→ `fact_evidence` → `fact_correction`
5. `reset_boundary`
6. `same_direction_event`（靠 `uk_event_fact` 幂等）
7. `metric_result`（靠 `uk_result` 幂等）

阶段 1 全程**不触碰 `dataset_pointer`**，因此对外完全不可见；任意步骤失败 → `status='failed'`，旧指针不变，无需回滚已写明细（下次重跑靠唯一键收敛）。

**阶段 2 — 校验 + 原子发布（单事务，目标 < 50 ms）**
```sql
START TRANSACTION;
-- 1) 校验结果落库
INSERT INTO quality_check_result (dataset_version, check_code, severity, passed, ...) VALUES (...);
-- 2) 判定门禁（应用层聚合；任一 severity='block' 且 passed=0 → ROLLBACK）
SELECT COUNT(*) FROM quality_check_result
 WHERE dataset_version=%s AND severity='block' AND passed=0;   -- 必须 = 0

-- 3) 锁指针行，串行化发布
SELECT published_version FROM dataset_pointer WHERE id=1 FOR UPDATE;
-- 4) 旧版本归档
UPDATE dataset_version SET status='archived'
 WHERE status='published' AND dataset_version <> %s;
-- 5) 切换指针
UPDATE dataset_pointer SET published_version=%s, published_at=NOW(3) WHERE id=1;
-- 6) 新版本置为 published
UPDATE dataset_version SET status='published', published_at=NOW(3) WHERE dataset_version=%s;
COMMIT;
```

**为什么不直接按 `updated_at DESC LIMIT 1` 取最新：** 现网 `get_prediction`（`market_calc_repository.py:705-725`）正是这么做的，配合 `prediction_dataset` 的原地 upsert，导致「读到半新半旧」。指针表把"可见性"收敛成一行，MVCC 下读者要么看到旧指针要么看到新指针，不存在中间态。

### 5.3 读取路径（三页同版本）

```
请求进入
  → 读 dataset_pointer（本地 5s 缓存 / Redis 30s）
  → 得到 V = published_version
  → 本次请求内所有查询强制 WHERE dataset_version = V
  → 若处于交易时段且证券可交易：叠加盘中覆盖层（带 quote_ts，不写库）
```

- 请求上下文里固化 `V`，跨接口调用（单股 → 预测 → 监控）沿用同一个 `V`，避免跨请求版本漂移。
- 若 `V` 对应的 `dataset_version.quote_cutoff_date` 早于当前业务日 → 返回 `availability='unavailable'` + `missing_reason_code='dataset_stale'`，**不返回上一版本数值、不返回安全**。

### 5.4 并发与锁

| 场景 | 机制 |
| --- | --- |
| 多实例触发每日重算 | `task_lease` 行锁 + `generation` 单调计数；租约 900 s，心跳 60 s |
| 构建期重复写入 | 所有明细表唯一键 + `ON DUPLICATE KEY UPDATE` |
| 发布互斥 | `dataset_pointer WHERE id=1 FOR UPDATE`（全局单行，发布 QPS ≈ 2/日，无热点风险） |
| 旧任务写入保护 | 明细写入前比对 `generation`；generation 落后则中止并回滚本批 |
| 上游限流 | Redis `INCR` + `EXPIRE`（来源级 QPS 上限）；Redis 不可用时退化为进程内令牌桶 |
| 长事务 | 禁止。批量 1000 行/事务，单事务目标 < 300 ms |

### 5.5 失败与保留

- 阶段 1 失败：保留 `status='failed'` 记录 + `job_run.error_message`；`dataset_pointer` 不变；界面沿用上一 published 版本并展示 `数据更新时间`。
- 阶段 2 门禁不通过：`status='validated'` 但不发布；不删除明细，供排障与后续补采后重投。
- 版本保留：热数据保留最近 14 个 `published` 版本（≈14 天），更早的 `metric_result` 按月归档到 `_archive` 库后删分区。

### 6.4 索引策略（"覆盖查询就够"，不堆索引）

`metric_result` 上只保留 3 个索引：`uk_result`（幂等 + 点查）、`idx_result_filter`（预测筛选）、`idx_result_stock`（单股历史对账）。

**理由：** 写入量为 88 K 行/日，每多一个二级索引约增加 15–25% 写放大和 B-tree 维护成本。查询侧 99% 的读是「某版本 + 某股票」或「某版本 + 某时间角色 + 某状态」，两个索引已完全覆盖；剩余 1% 的运营类查询走归档库或离线。

`daily_bar` 上：`PRIMARY KEY (ts_code, trade_date, adj_type)` + `idx_bar_date (trade_date, adj_type, close)`。
- 前者服务「重放某股 N 年窗口」（顺序扫描，无排序）；
- 后者服务「取某日全市场收盘」（覆盖索引，`close` 在索引内，无需回表）。
- **不建** `(ts_code, close)`、`(pct_chg)` 之类——无查询支撑。

### 6.5 批处理：增量 vs 全量重放

| 场景 | 策略 | 频率 | 目标耗时 |
| --- | --- | --- | --- |
| 日常更新 | **增量**：只拉最近 5 个交易日的 `daily_bar`/`index_daily_bar`/`suspension`，只对「有新增事实或行情变化的股票」重算 4 项 | 每交易日 15:30 后 | < 3 分钟 |
| 规则版本变更 | **全量重放**：不动原始行情，只按新 `rule_version` 重算 `metric_result` | 按需 | < 8 分钟 |
| 公告事实更正 | **定向重算**：按 `fact_key` 定位受影响的 `ts_code` + `fact_end_date` 窗口，重算该股全 4 项 | 按需 | < 10 秒/股 |
| 历史回溯审计 | **冷重放**：从归档库读 `daily_bar`，产出独立 `replay_run`，结果不写入生产 `metric_result` | 按需 | < 30 分钟 |

**增量判定水位**：`dataset_version.source_snapshot_hash` 记录「行情截止日 + 事实截止日 + 日历版本 + 规则版本 + 解析版本」的指纹；指纹未变且无新公告 → 跳过重算，直接复用上一版本的 `metric_result`（通过复制行并写入新 `dataset_version`，保证幂等与可追溯）。

### 6.8 读写分离与异步化

- **读写分离**：发布任务与采集任务写主库；三个查询接口读只读实例。可接受的主从延迟上限 **1 s**——但**不能靠"等 1 s"解决一致性**，因为 `dataset_pointer` 切换必须在主库事务内完成，读接口若从从库读到旧指针，会返回旧版本（这是安全的，因为旧版本也是一个完整、通过门禁的版本）。**返回时携带 `dataset_version` 与 `published_at`，前端按版本展示，不做跨版本混合**。
- **异步化（硬门槛，非可选项）**：顾图南测算串行基线 8–20 min，其中 **OCR 串行占 150–420 s，是绝对瓶颈**；公告快照 O(N×M) 遍历占 30–120 s。因此：
  1. **PDF 下载与 OCR 必须从采集主流程剥离**，进 `announcement_parse_queue`（用 `job_run` + 状态字段实现，无需引入 MQ）；
  2. **公告快照必须建 `ts_code` 倒排索引**（一次 `GROUP BY ts_code` 分组后按股取值），把 O(N×M)≈4.3×10⁶ 降到 O(N+M)≈6×10³；
  3. 未满足以上两项前，SLO 只能承诺 25 min 硬上限。
- 正文不可读时先落 `pending`（`regulatory_fact.confidence_state='pending_verification'`），由后台补采任务重试；**当前实现只在进程内存缓存成功结果**（`announcement_service.py:289-294`），容器重启即丢失待核验状态，必须落表。

## ⑦ 缓存设计

### 7.1 原则
1. Redis **只缓存可重建数据**，不得作为唯一事实源（PRD §9.3 第 220 行、ARCH §7 第 140 行）；
2. 缓存键**必须包含 `dataset_version`**，使版本切换天然失效，无需批量 `DEL`；
3. 缓存不得改变「不可用」语义；
4. Redis 不可用 → 降级为直连 DB，**不允许用空结果/默认值兜底**。

### 7.2 键设计

```
# ── 后端侧（服务端缓存，键含 dataset_version）────────────────────
# 版本指针
sa:ds:current                                    -> "20261027-01"        TTL 30s（发布时主动 DEL）

# 单股详情（四项当前/次日 + 状态卡 + 事实投影）
sa:stock:{ds_version}:{ts_code}                  -> JSON                 TTL 300s

# 预测列表（筛选视图）
sa:pred:{ds_version}:{date_role}:{page}:{size}   -> JSON                 TTL 300s

# 重点监控
sa:monitor:{ds_version}                          -> JSON                 TTL 300s

# 盘中覆盖层（必须带行情时间戳，不覆盖收盘发布集）
sa:quote:intraday:{ts_code}:{quote_ts}           -> JSON                 TTL 60s

# 任务租约（SET NX PX）
sa:lease:{job_name}                              -> "{owner}:{generation}"  TTL = lease_ms

# 刷新协调（短期并发刷新去重）
sa:refresh:{scope}:{ds_version}                  -> "1"                 TTL 30s，SET NX

# 来源限流（分钟级滑窗计数）
sa:rl:{source_code}:{yyyymmddhhmm}               -> counter             TTL 120s
```

> **★ 与前端缓存的边界（夏小笺 §④，格式 `yidong:v4:{page}:{datasetVersion}:{dateRole}:{param}`）：**
>
> | 层 | 键前缀 | 生命周期 | 是否可含"不可用"结果 |
> | --- | --- | --- | --- |
> | 小程序本地 `wx.setStorage` | `yidong:v4:…` | 页面级/短 TTL | 是，必须原样缓存 |
> | 服务端 Redis | `sa:…` | 30–300 s | 是，必须原样缓存 |
>
> - 两侧键都含 `datasetVersion`，**版本切换时前端本地缓存自动失效**，无需后端下发失效指令；
> - `dateRole` 取值统一为 `current` | `next`（对应 PRD 的 D / N），前端键里的 `{dateRole}` 直接复用该枚举；
> - **前端本地缓存不得做"缺结果 → 补默认值"的兜底**：`pages/stock/index.js:668` 现有 `quoteUpdatedAt || tradeDate` + 拼「 15:00」的伪造时间必须移除，改为直接渲染接口返回的 `publishedAt`。

**变量说明：**
- `{ds_version}` = `dataset_version`（如 `DS-20261027-1`）——**版本变化即换键，旧键 300 s 内自然淘汰，不需要发布时扫库清理**；
- `{date_role}` = `current` | `next`（PRD §8.1 日期角色）；
- `{quote_ts}` = 行情时间戳（毫秒），盘中覆盖层**必须**带时间戳，禁止用"最新"覆盖（PRD §7 第 180 行「盘中结果标记行情时间，不覆盖收盘事实」）；
- `{rule_version}` **不需要进键**：`rule_version` 已被 `dataset_version` 唯一固定（`dataset_version.rule_version`），进键属于冗余且会造成键膨胀。

### 7.3 失效策略

| 事件 | 动作 |
| --- | --- |
| 新版本发布 | `DEL sa:ds:current`；其余键因含 version 自动淘汰 |
| 公告事实更正 | 生成新 `dataset_version`（PRD §6「事实更正会生成新数据集版本并重算」），同上 |
| 规则版本变更 | 同上 |
| 盘中刷新 | 只写 `sa:quote:intraday:*`（TTL 60 s），不动任何 `sa:stock:*` |
| 数据源失败 | **不缓存**失败结果；返回 DB 中的上一 published 版本并标记 `stale` |

### 7.4 「不可用不得变安全」如何与缓存共存

这是本设计里最容易出事的地方，给出五条硬规则：

1. **缓存要连"不可用"一起缓存。** `metric_result.availability='unavailable'` 且 `missing_reason_code` 非空的行，照常写入缓存，不跳过、不过滤。不能出现"因为这项不可用所以没进缓存 → 前端拿到空 → 渲染成安全"的路径。
2. **缓存 miss 必须回源 DB，禁止默认值。** DB 也不可用 → 返回 `availability='unavailable'` + `missing_reason_code='result_unavailable'`，并在响应里带上上一成功版本的 `dataset_version` 与 `published_at` 作为"结果日期"标注（PRD §3.5 第 2 条）。
3. **禁止缓存"简化派生值"。** 例如只缓存 `triggered: false` 而丢掉 `availability`。必须缓存完整契约字段（数值/阈值/方向/区间/规则版本/可用性/缺因）。
4. **版本即隔离。** 因为键含 `dataset_version`，不存在"缓存了新版本的四项 A、旧版本的四项 B"导致三页不一致。
5. **租约/限流类键不参与正确性判定。** Redis 挂了 → 退化为 DB 行锁 + 进程内令牌桶，最坏结果是"任务重复执行"，由唯一键幂等吸收，不会产生错误结论。

### 7.5 容量与淘汰

- 单股详情峰值：5,500 股 × 平均 12 KB ≈ 66 MB（单版本）；保留 2 个版本 ≈ 132 MB。
- 全局：`maxmemory-policy` 设为 `allkeys-lru`，`maxmemory` 建议 512 MB（腾讯云 Redis 最低配即可满足）。
- 盘中覆盖层：仅缓存"用户实际打开过"的股票，60 s TTL，峰值 < 5 MB。

### 8.2 迁移步骤（7 步，全程可回滚）

**M0 — 引入迁移框架（无业务变更）**
```sql
CREATE TABLE schema_migration (
  version     VARCHAR(32) NOT NULL,
  applied_at  DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  checksum    CHAR(64) CHARACTER SET ascii NOT NULL DEFAULT '',
  operator    VARCHAR(64) NOT NULL DEFAULT 'system',
  PRIMARY KEY (version)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```
- 所有 DDL 改为版本化脚本，执行记录写入此表；**移除 `except: pass`**，改为记录失败并中断启动。
- 回滚：本步无业务影响，回滚只需 `DROP TABLE schema_migration`。

**M1 — 建新表 + 历史日线回填（双写前）**
- 建 §④ 全部新表（均为空表，对现网零影响）。
- 回填 `daily_bar`：按 `trade_date` 逐日全市场拉取 3 年历史（约 750 次请求，分批 + 限流，建议 2–3 天窗口内完成）。
- 回填 `trade_calendar`、`suspension`。
- **校验门槛**：`daily_bar` 覆盖度 ≥ 99.5%，且与 `stock_calc_base` 现有向量反算的 30 日偏离值差异 ≤ 0.01 个百分点。不达标不得进入 M2。
- 回滚：`DROP` 新表即可，旧链路完全未动。

**M2 — 双写**
- 新写入路径同时写旧表（`stock_calc_base` / `prediction_dataset`）与新表（`daily_bar` / `metric_result` / `regulatory_fact` / ...）。
- 旧表继续作为**唯一读取源**。
- 每批次写完后运行对账查询（见 M3），差异写入 `quality_check_result`。
- 回滚：关闭双写开关，旧链路继续工作（新表数据可保留待下次重试）。

**M3 — 影子校验（≥5 个交易日）**

对账查询（新旧结果逐项比对）：
```sql
SELECT r.ts_code, r.rule_key, r.date_role, r.direction,
       r.value_num AS new_value, r.status AS new_status,
       r.availability, r.missing_reason_code
  FROM metric_result r
 WHERE r.dataset_version = %s
   AND r.status = 'unavailable';
```
- 门禁：`status='unavailable'` 占比 > 3% → 阻断；`missing_reason_code=''` 且 `availability='unavailable'` 的行数必须为 0。
- 同时比对旧 `prediction_dataset.items` 与新 `metric_result` 的 `ts_code/ruleKey/deviation/triggered` 四元组，差异股票数必须为 0（口径变更的需有显式 `rule_version` 变更记录）。
- 回滚：切回旧读路径。

**M4 — 切读**
- 三个接口改为：`dataset_pointer` → `metric_result`（按 `dataset_version`）。
- 保留旧 `prediction_dataset` 只读兼容，用于 M5 期间对照。
- 回滚：一个开关切回旧读路径（代码内保留双读分支一个版本周期）。

**M5 — 停止双写 / 下线旧表**
- 关闭对旧 `stock_calc_base` / `prediction_dataset` 的写入。
- 旧表保留 30 天后归档删除（`prediction_cache` 已有 `PREDICTION_CACHE_COMPAT_READ` 开关可直接复用，见 `market_calc_repository.py:24-27`）。
- 回滚：此步后不再支持在线回滚，只能从备份恢复——**因此 M5 必须在一个完整对账周期（≥10 个交易日）之后再执行**。

### 9.1 阻断式校验（severity = `block`）

任一不通过 → 阶段 2 事务回滚，不发布。

| check_code | 校验内容 | 数据支撑 | 阈值 |
| --- | --- | --- | --- |
| `DATASET_SINGLE_PUBLISHED` | 同一 `business_date` 只有一个 `status='published'` | `dataset_version` | 冲突数 = 0 |
| `CALENDAR_COMPLETE` | 日历覆盖 `business_date` 及未来 30 自然日 | `trade_calendar` | 缺失 = 0 |
| `QUOTE_FRESHNESS` | 全部活跃证券的 `quote_cutoff_date` == `business_date` | `daily_bar` | 未更新比例 ≤ 0.5% |
| `INDEX_ALIGNMENT` | 每只股票的基准指数 `as_of` == 股票 `as_of` | `daily_bar` + `index_daily_bar` | 不一致 = 0 |
| `MAPPING_COVERAGE` | 每只活跃证券在目标业务日有有效板块 + 指数映射 | `security_board_history` + `index_board_map_history` | 覆盖率 = 100% |
| `FACT_EVIDENCE_BOUND` | 每条 `confidence_state='confirmed'` 的事实至少有一条 `fact_evidence` | `regulatory_fact` + `fact_evidence` | 缺失 = 0 |
| `EVENT_FACT_ONE_TO_ONE` | 每个 `fact_id` 至多一个事件 | `same_direction_event.uk_event_fact` | 约束保证 |
| `CROSS_PAGE_CONSISTENCY` | 预测卡对应的四项结果在 `metric_result` 中存在且数值/方向/日期一致 | `metric_result` | 差异 = 0（PRD §11 #4） |
| `UNAVAILABLE_REASON_PRESENT` | `availability='unavailable'` 的行 `missing_reason_code` 非空 | `metric_result` | 违规 = 0 |
| `ANONYMOUS_FACT_COUNT` | 生产数据集中缺少稳定来源 ID / 内容哈希的事实数 | `regulatory_fact` | **必须为 0**（回执第 31 行） |
| `SOURCE_COVERAGE_COMPLETE` | 必需来源的采集批次均为 `complete` | `announcement_source_run` | 未完成来源数 = 0 |
| `PENDING_NOT_CONFIRMED` | 批次未完成时不得存在 `not_found` 结论 | `announcement.parse_status` + `announcement_source_run.coverage_state` | 违规 = 0 |

### 9.3 缺因枚举（DB 层落地）

**权威枚举以夏小笺《小程序前端契约与开发设计》§④-0.3 的 19 个 `reasonCode` 为准**（本节原稿的 12 个 snake_case 码作废，避免两套命名）。DB 侧落地方式：

```sql
CREATE TABLE missing_reason (
  reason_code   VARCHAR(48) NOT NULL COMMENT '与前端契约 reasonCode 同值，如 HISTORY_INSUFFICIENT',
  label_zh      VARCHAR(128) NOT NULL DEFAULT '' COMMENT '中文文案，供后端日志与降级展示',
  severity      ENUM('block','warn','info') NOT NULL DEFAULT 'warn',
  description   VARCHAR(512) NOT NULL DEFAULT '',
  PRIMARY KEY (reason_code)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

**19 个 code 与产出位置对照：**

| reasonCode | 由哪张表/哪项检查产出 | 阻断级别 |
| --- | --- | --- |
| `SOURCE_QUOTE_FETCH_FAILED` | `announcement_source_run` / `job_run`（采集失败） | block |
| `INDEX_NOT_ALIGNED` | `daily_bar` ↔ `index_daily_bar` 对齐检查 | block |
| `HISTORY_INSUFFICIENT` | `daily_bar` 窗口点数检查 | block（仅影响依赖该窗口的项） |
| `SUSPENSION_WINDOW_INCOMPLETE` | `suspension` + 复牌基线检查 | block（仅影响偏离类） |
| `CALENDAR_MISSING` | `trade_calendar` 覆盖检查 | block |
| `TRADING_STATE_UNKNOWN` | `security_trading_status_daily` | block |
| `SECURITY_IDENTITY_CONFLICT` | `security` / `security_board_history` 多源冲突 | block |
| `ANNOUNCEMENT_*`（一组） | `announcement` + `announcement_body`（源失败/未找到/正文不可读） | block |
| `FACT_UNMATCHED` | `same_direction_event.match_status='unmatched_pending'` | warn |
| `FACT_IDENTITY_MISSING` | `regulatory_fact.fact_key` 或 `evidence_hash` 缺失 | block（生产必须为 0） |
| `RESET_BOUNDARY_UNKNOWN` | `reset_boundary.confidence_state='pending_verification'` | warn |
| `DATASET_NOT_PUBLISHED` | `dataset_pointer` 空 | block |
| `DATASET_STALE` | `dataset_version.quote_cutoff_date` 落后业务日 | warn |
| `PREDICTION_NOT_OPEN` | 交易时段次日预测不开放（PRD §7） | info |
| `EXCLUDED_BY_POLICY` | 预测/监控排除规则命中 | info |
| `PENDING_VERIFICATION` | 批次未完成，结论未定 | warn |
| `UNKNOWN` | 兜底，禁止作为正常路径 | warn |

- **DB 层强制**：`metric_result` 上的 `chk_result_unavailable_reason` CHECK 约束（见 §4.9）保证「不可用必有缺因码」；`missing_reason` 枚举表用于约束取值范围与提供中文文案。
- **`UNKNOWN` 必须可告警不可静默**：出现 `UNKNOWN` 说明缺因分类器有盲区，计入 `quality_check_result` 并触发 `alert_event`。
- **前端契约**：前端只做「code → 中文文案」映射，不做语义判断；遇到未登记的 code 显示通用「数据不可用」并上报埋点，**禁止回退为 0 / 无异动 / 安全**（PRD §3.4 第 62 行、验收 #9/#10）。

**与 §4.9 的衔接：** `metric_result.missing_reason_code` 的取值即为本表 `reason_code`，由 `chk_result_unavailable_reason` CHECK 约束强制非空；`missing_reason` 表提供枚举封闭性与中文文案。

### 9.4 支撑表与产出物

| 表 | 门禁作用 |
| --- | --- |
| `quality_check_result` | 承载每次 `dataset_version` 的全部校验项、期望值、实际值、通过与否 |
| `dataset_version.validation_json` | 发布时快照门禁结论，便于事后追溯"当时为什么放行" |
| `announcement_source_run` | 支撑「批次覆盖未完成 → 未找到只能待核验」（PRD §6、验收 #11） |
| `regulatory_fact.confidence_state` + `fact_evidence` | 支撑「匿名事实计数必须为 0」（回执第 31 行） |
| `suspension.reason_code` | 支撑「停牌原因无法核实 → 待核验，不猜测」（PRD §4.4） |
| `alert_event` | 门禁失败的告警落库与闭环跟踪 |
| `replay_run` | 口径变更（如 P1-5 的入窗日/窗口合并策略）前后的影子对比结果留存 |

### 9.5 门禁执行位置

```
阶段 1 完成 → 运行 13 项 block 校验 → 落 quality_check_result
            → 任一 block 失败：dataset_version.status='validated'（不发布），告警
            → 全部通过：进入阶段 2 事务（重新核对 block 计数后切换指针）
```

- block 校验在**事务外**执行（耗时长、只读），事务内只做一次 `COUNT(*)` 复核——避免长事务持锁。
- 校验 SQL 全部走覆盖索引，单次全量门禁目标 < 60 s（见 §6.7）。
