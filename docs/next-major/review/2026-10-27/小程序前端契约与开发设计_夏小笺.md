## ① 总评结论

**总判：PRD/ARCH 对前端的约束是自洽的（"标签、颜色、日期、文案全部由接口字段驱动"），但现网 1.0.x 前端是这条约束的反例——它承担了大量正式状态判定；而 vNext 的文档里没有给出承载这条约束的「展示契约对象」，前端无法只靠字段驱动落地。契约缺口是本次唯一的硬阻塞，代码债务是最大的工作量。**

分四层判断：

### 1）契约层（阻塞）：PRD 定义了状态语义，没定义状态字段

PRD §3 给了四组状态的**语义与成立条件**，§9.1 要求前端"不得计算正式状态、标签颜色日期文案全部由接口字段驱动"，但通篇没有给出任何一个页面的字段清单、枚举值或状态组合规则。前端要落地 §5.1（次日结论四值）、§5.2（四卡当前/次日/数值/方向/阈值/区间/圆环/数据状态）、§7（预测排除原因、当日已触发卡保留到次日 09:00、交易时间内不开放次日列表）、§10（`dataset_version` 版本号展示），至少需要 **7 类文档里完全没定义的东西**：

1. 缺因（`unavailable_reason`）枚举与文案映射 —— 宋砚秋已确认后端是自由文本（P2-5），PRD 验收标准 #9 却要求"均能显示明确缺因"；
2. 次日结论（`nextDayConclusion`）枚举与触发规则清单 —— PRD §5.1 只有中文条件表；
3. 日期角色 `D/N` 与"09:00 切换 / 保留到次日 09:00"的机器可读字段 —— PRD §8.1 只写了业务规则；
4. 盘中覆盖层标记（盘中 vs 收盘、行情时刻、来源、是否持久化）—— PRD §5 描述了行为，没有字段；
5. `dataset_version` 的展示口径（版本号？更新时间？过期判定谁算？）；
6. 股票状态标签的组合规则（PRD §3.5-5 说"退市整理、停牌、终止上市可并列显示"，未给优先级与并列上限）；
7. 四卡圆环的数值口径（`progressPct` 谁算、`tone` 谁定、10 日同向是次数不是百分比、66.67% 黄预警是不是产品口径）。

这 7 项不定，前端要么继续自己算（违反 §9.1），要么无法渲染（违反验收 #5/#9）。**建议：在写实施文档前先冻结一份 `display-contract` 章节（本文 §④ 是草案），并由 `server/tools/api_contract_check.py` 加校验。**

### 2）代码层（高工作量）：现网前端是全项目最大的"正式状态计算"现场

抽查 `miniprogram/pages/stock/index.js`（718 行）发现，前端当前实际在做：

- **硬编码板块阈值**：`monitoringRuleLabel`（:100-120）用 `/^(4|8|9)/` 猜北交所，写出 150/60/300/75 的严重阈值 → 直接违反 PRD §4.2"阈值必须由证券属性与规则版本确定，不能由页面或接口硬编码"；
- **拼装监管文案**：`currentSevereRuleTexts`（:239-266）自行生成"连续10个交易日内收盘价涨幅偏离值累计达到 +100%"这类监管事实表述 → 违反 §9.1"文案由接口驱动"，且违反 §4.5"不得凭计算自动生成新的监管事实"的表述风险；
- **判定次日结论与状态横幅**：`assessNextDayRules`（:216-229）用前端硬编码的 `severeKeys/warningKeys` 集合分级；`buildNextDayForecast`（:268-329）用 `nextTradeDate > currentDate` 这类**日期比较**决定"当日已触发"还是"次日预测" → 违反 ARCH §6"时间由交易日历和目标数据集确定，不由页面本地时钟独立推断"；
- **计算四卡颜色与圆环进度**：`presentWarnings`（:452-531）从 `up/down/upThreshold` 反算 `progress`、`tone`、`toneColor`、`ringText`（含 `progress >= 66.6667 ? 'warning'` 这一产品口径阈值），颜色常量表写死在 :453；
- **用本地时钟算监管剩余天数**：`localTodayKey`（:136-139）+ `remainingMonitoringDays`（:141-152）用 `new Date()` 与 `Date.UTC` 相减；
- **伪造更新时间**：`formatUpdatedAt`（:84-89）遇到 8 位日期直接拼 ` 15:00` → 与 PRD §5"实时源失败时使用最近成功行情并明确时间"直接冲突，**用户会看到并不存在的数据时间**。

也就是说：**vNext 前端不是"加字段"，而是要把 `pages/stock/index.js` 里约 400 行的派生逻辑整体搬回后端，并换成字段驱动渲染。**这是工作量主体，应在里程碑里单列（见 §⑨ M1）。

### 3）时序层（可实施，但有硬约束）

PRD §5 的两段式刷新（先刷新已发布数据集，交易时段且可交易再刷实时行情）在小程序侧完全可实现，但有三个必须由后端给答案的前提：

- **"是否交易时段 / 是否可交易"不能由前端判定**。小程序本地时钟可被系统时间影响，且前端没有交易日历。必须返回 `session.intradayEligible` 之类的布尔值，前端本地时钟只用于节流；
- **盘中结果不落库**（README.md:94）意味着 S2 的结果只在本次响应里，前端必须能把"盘中临时值"与"收盘发布值"在 UI 上区分开，并在切页/切后台回来后**不把盘中值当持久化数据再用**；
- **三页可能读到不同版本**（宋砚秋 P1-4）意味着前端必须实现"版本一致性守卫"：跨页 `datasetVersion` 不一致时显式提示并刷新，禁止静默混用（否则直接违反验收 #4）。

### 4）体验与合规层（可控）

性能目标、包体积、rpx/安全区、tabBar、隐私入口、搜索历史本地化在现网基础上均可达成；但有三处需要立即处理：预测页 `nextDayReason` 用**中文字符串比较**控制交互（:63）、监控页 1.2s × 15 次轮询（:65-89）、`wx.downloadFile` 直接下载巨潮 PDF 的域名白名单问题（`utils/open-pdf.js:26`）。

**放行建议：** P1 共 10 项。其中 **P1-1～P1-4（契约类）必须先定稿**，它们决定接口形态，后改等于重写三页；**P1-5～P1-10** 可在实施并行推进，但必须在首个灰度数据集发布前完成。

## ② P1 阻塞问题清单

> P1 定义：不改则 vNext 前端无法做到"状态全部由接口字段驱动"，或上线后会把"数据不可用"渲染成"安全"、把"盘中临时值"渲染成"收盘事实"。

### P1-1 缺因无枚举、无文案，前端只能自己编说法，违反验收标准 #9

**证据：**
- `miniprogram/pages/stock/index.js:489-490`：`currentText: '数据不足'`、`remainingText: '暂不可判定'` —— 前端硬编码兜底文案；
- `miniprogram/pages/stock/index.js:520-530`：`forceUnknown` 分支用字符串拼接 ` ${item.target} · 待核验`、`ringText: '待核验'`；
- `miniprogram/pages/stock/index.js:278`：`['pending_verification','partial','unavailable','not_configured','unknown'].includes(...)` —— 前端硬编码后端状态枚举；
- 后端侧：宋砚秋 P2-5 已确认"缺因是自由文本"（`unavailableReason` 直接拼中文句子，如 `market_service.py:2231-2236`）。

**问题：** PRD §3.4 与验收 #9 要求"公告采集失败、正文待核验、证券无行情、指数未对齐均能显示**明确缺因**"。当前实现下，前端只能靠"数值缺失"反推"数据不足"，无法区分"公告没抓到"和"指数没对齐"，更无法给出"是否可恢复"。而"数据不足"这个说法本身在 PRD §3.4 里是被禁止的近似表达（不可用不得显示 0/无异动/安全，"数据不足"同样会误导）。

**建议改法：**
1. 后端定义 `reasonCode` 枚举（草案见 §④-0.3），每个结果对象固定携带 `unavailable?: { code, text, scope, retryable }`；
2. 前端维护唯一映射表 `utils/enum.js`：`code → { text, tone, retryable, hint }`，**文案与颜色 token 只在此处定义一次**；
3. 前端收到未知 `code` 时**降级为"数据不可用（原因：{code}）"，不得回退到安全色**；
4. `api_contract_check.py` 增加断言：任何 `status === 'unavailable'` 的结果必须带非空 `reasonCode`，且 `reasonCode` 必须在枚举表内。

### P1-2 次日结论由前端比较日期字符串 + 硬编码规则键集合判定

**证据：**
- `miniprogram/pages/stock/index.js:216-229` `assessNextDayRules`：本地 `new Set(['same_direction_10d','severe_10d','severe_30d'])` 与 `new Set(['ordinary_3d'])` 决定"严重/警告/安全"；
- `miniprogram/pages/stock/index.js:286-296`：`nextTradeDate <= tradeDate`、`nextTradeDate < currentDate` 等字符串比较决定"当日已触发"与"次日预测"的显示分支；
- `miniprogram/pages/stock/index.js:331-342` `resolveStatusBanner`：前端决定卡片是 `current-triggered` 还是 `monitoring`；
- `miniprogram/pages/stock/index.wxml:40`：`class="status-banner card status-{{detail.statusClass}}"` —— 卡片配色由前端派生值驱动。

**问题：**
1. PRD §9.1 明确"标签、颜色、日期和文案全部由接口字段驱动"，§8.1 明确"日期角色由 09:00 切换点决定"。前端用日期字符串大小比较实现日期角色判定，等于把 D/N 角色判定搬到了客户端，一旦后端改交易日历或遇到临时休市，前端判断就会与后端不一致；
2. PRD §5.1 说"次日结论是展示层派生值"，但**派生规则本身**（"仅 3 日可能触发且无严重可能触发 → 触发普通异动"）是规则口径，应由规则模块给出，前端只应做渲染；
3. PRD §5.1 的"当日已触发"与"严重异动监管中"两条分支（第 149-150 行）是不同证据来源（计算触发 vs 公告事实），前端无法可靠区分。

**建议改法：**
- 接口新增 `nextDayConclusion: { code, text, tone, triggeredRules: [{ ruleKey, ruleName, text, thresholdText }], evidenceDate, targetDate, line }`，`code ∈ {safe, may_trigger_ordinary, may_trigger_severe, unavailable}`；
- 接口新增 `regulatoryBanner: { code, text, tone, kind: 'current_triggered' | 'monitoring' | 'next_day' | 'unknown', evidence: {...} }`，把"当日已触发 / 监管中 / 次日风险提示"的分支判定完全后端化；
- 前端删除 `assessNextDayRules`、`buildNextDayForecast`、`resolveStatusBanner` 三个函数的产品判定部分，只保留日期/百分数的**格式化**。

### P1-3 四卡圆环数值、进度、颜色由前端从原始数值反算

**证据：**
- `miniprogram/pages/stock/index.js:453`：`const colors = { base:'#B9D6F2', warning:'#F5C542', severe:'#D94A45', unknown:'#DCEBFA' }` —— 颜色写死在页面；
- `miniprogram/pages/stock/index.js:477-483`：10 日同向 `progress = count/limit*100`、`tone` 由 `progress >= 66.6667` 决定；
- `miniprogram/pages/stock/index.js:495-518`：`upProgress/downProgress` 反算、`useUp = upProgress >= downProgress` 选方向、`remaining = threshold - |actual|`；
- `miniprogram/pages/stock/index.wxml:68`：`style="background: conic-gradient({{item.toneColor}} {{item.progress}}%, #E5E7EB 0);"`。

**问题：**
1. PRD §5.2 要求"展示当前/次日数值、方向、阈值、区间、圆环和数据状态"，但圆环的**口径**（百分比 vs 次数、取上涨还是下跌方向、多少算"接近阈值"）是产品/规则口径 —— 66.67% 这个数字没有任何文档依据，是前端自己发明的；
2. `useUp = upProgress >= downProgress` 意味着"哪一项更接近阈值就显示哪一项"，同一时刻单股页与预测页可能对同一只股票显示不同方向，直接违反验收 #4"单股与预测的共同规则结果在数值、方向、阈值、日期和触发状态上相同"；
3. 颜色硬编码导致主题/规则等级变更要改 JS，违反 §4.2"颜色等级由规则模块输出"。

**建议改法：**
- 每个四项结果固定携带 `ring: { mode: 'percent'|'count', displayValue, displayUnit, progressPct, progressText, tone, toneToken }`，**全部由后端算好**；
- 颜色改为 CSS 变量 token（如 `--tone-safe / --tone-warning / --tone-severe / --tone-unknown`），前端只映射 `toneToken → CSS var`，不再出现十六进制；
- 方向选择由后端给 `displayDirection`，前端禁止比较两侧进度。

### P1-4 股票状态标签组合、交易状态枚举、监管状态枚举未定义

**证据：**
- PRD §3.1 给了四种交易状态 + "退市整理/ST/*ST 单独显示"，§3.5-5 说"可并列显示"，但没给字段与优先级；
- 现网前端靠**正则匹配中文**判断退市整理：`miniprogram/pages/stock/index.js:166-169` `/退市整理|退市倒计时/.test(...)`；
- 现网前端靠**代码前缀**猜板块/过滤：`:133-135` `/^[15]/.test(code[0])`（基金/北交所？）、`/^\*?ST/.test(name)`、`name.includes('退')`（`pages/monitor/index.js:128-136`）；
- 监管状态在现网接口里是 `statusDisplay` + `statusClass` 两个**中文字段**（`market_service.py:2288-2292` 的 `marketStatusDisplay/statusClass`），不是枚举。

**问题：** 前端用股票名称里是否含"退"字来决定是否展示，是最脆弱的一类判定——改名、简称调整、新增板块都会失效；且"过滤掉 ST/退市"与 PRD §3.1"退市整理是证券属性/交易事实，在满足条件时单独显示"方向相反（PRD 要求**显示**，现网是**隐藏**）。

**建议改法：**
- 接口返回 `stateTags: Tag[]`，`Tag = { code: 'suspended'|'terminated'|'delisting_period'|'st'|'unknown_state', text, tone, priority, blocking }`，前端按 `priority` 排序取前 N 个渲染，不判断内容；
- 交易状态单独给 `tradeState: 'normal'|'suspended'|'terminated'|'unknown'`；
- **监管状态需要第五个"不可判定"占位**：PRD §3.2 只有 safe/ordinary/severe 三值，但 §3.2 第 49 行要求"3 日计算触发但公告未核验时不得显示安全"。前端没有第四枚举就只能显示空或安全。建议 `regulatoryState ∈ {safe, ordinary, severe, undetermined}`，`undetermined` 不是监管状态，是"当前不可判定"标记，文案与 tone 由 `reasonCode` 决定。**✅ 2026-10-27 已拍板接受**，四条约束（仅依赖不可用时出现 / 必须带 reasonCode / 中性灰"暂不可判定"禁与 safe 同色 / 追加空 reasons 断言）与在 `stateTags`、`regulatoryBanner` 两处的出现规则见 §④-0.6；
- 删除前端所有基于名称/代码前缀的分类逻辑。

### P1-5 监管剩余天数用本地时钟计算

**证据：**
- `miniprogram/pages/stock/index.js:136-139` `localTodayKey()` 用 `new Date()` 取本地年月日；
- `miniprogram/pages/stock/index.js:141-152` `remainingMonitoringDays` 用 `Date.UTC(...)` 相减，兜底再退回 `monitoring.remainingDays / days`；
- `miniprogram/pages/stock/index.wxml:58`："剩余 {{...}} 天"。

**问题：** ARCH §6 明确"时间由交易日历和目标数据集确定，不由页面本地时钟独立推断"。用户改系统时间、跨时区、跨日不刷新页面，都会得到错误剩余天数；更关键的是 PRD §2 要求"监管自然日倒数使用自然日，不用交易日替代"，这个口径只有后端有日历数据。

**建议改法：** 接口直接给 `remainingDays: { value: number|null, text: string, asOfDate: 'YYYYMMDD', basis: 'natural_day' }`，前端只渲染 `text`；`value` 为 `null` 时渲染 `--` 并显示 `reasonCode`。同时状态卡必须展示 `asOfDate`，让"剩余天数按哪天算"可追溯。

### P1-6 三页无 `dataset_version`，前端无法保证"同一数据集"也无法表达过期

**证据：**
- `miniprogram/utils/api.js` 全部 6 个接口无版本字段；
- `miniprogram/pages/prediction/index.js:83`：只有 `quoteUpdatedAt`；
- `miniprogram/pages/monitor/index.js:54`：只有 `result.updatedAt`；
- `miniprogram/pages/stock/index.js:668`：`dataUpdatedAt = quoteUpdatedAt || tradeDate`。

**问题：** PRD §10 要求"每个结果必须携带 `dataset_version`…"，验收 #4 要求"单股、重点监控、预测同一数据集、规则版本和结果"，ARCH §5 要求缓存键必须含 dataset_version。现网三页各自拿一个时间字符串，既无法对账也无法失效。叠加宋砚秋 P1-4（后端取数用 `ORDER BY updated_at DESC LIMIT 1`），三页读到不同版本是**必然会发生**的事故，而不是理论风险。

**建议改法：**
- 所有响应统一外层 `dataset: { version, ruleVersion, businessDate, nextBusinessDate, quoteAsOfDate, factAsOfDate, publishedAt, freshness: 'fresh'|'stale'|'expired', staleReason }`；
- 前端建 `store/datasetStore.js`：全局保存"当前已接受的 `version`"，任何响应 `version` 与之不同 → 不覆盖本地已渲染数据，改而显示顶部"数据版本已更新，点击刷新"提示条（对单股页）/ 下次 `onShow` 自动刷新（列表页）；
- 缓存键格式固定 `yidong:v4:{page}:{version}:{dateRole}:{param}`，旧版本 key 在写入新版本时清理（上限 10 个 key，防 storage 膨胀）。

### P1-7 预测页"排除原因"接口不返回，PRD §7 无法落地

**证据：**
- `server/services/market_service.py:267-271`：`if rule_key == "same_direction_10d": return False`，另有 monitored 去重分支 —— 一律静默丢弃，无任何 reason；
- `miniprogram/pages/prediction/index.js:11-27` `normalizeItems`：无排除原因字段处理；
- `miniprogram/pages/prediction/index.wxml:22`：空态只有"当前范围暂无候选股票"。

### P1-10 盘中结果标记缺失 + 前端伪造更新时间

**证据：**
- `README.md:94`："盘中刷新结果只在 POST 响应中返回，不写入数据库或缓存"；
- `miniprogram/pages/prediction/index.js:6-9`：`isIntradayRefreshResult` 靠 `refreshStatus === 'applied'` **且** `dataQuality.intraday === true || dataStage === 'realtime'` 双通道猜测，且这个结果只用于决定是否写 storage 标记（:49-53）；
- `miniprogram/pages/stock/index.js:84-89` `formatUpdatedAt`：8 位日期直接拼 ` 15:00`；:668 传入的是 `quoteUpdatedAt || tradeDate` —— **当 `quoteUpdatedAt` 为空时，把业务日当成"15:00 更新"展示给用户**；
- 单股页 UI 上没有任何"盘中/收盘"区分标记。

**问题：** PRD §5 要求"实时源失败时使用最近成功行情并明确时间/不可用状态，不以模板行情伪装实时"。现网恰好相反：拿不到行情时间时**编一个 15:00**。这是合规与信任层面的硬伤。

**建议改法：**
- 统一 `quoteLayer: { kind: 'close'|'intraday', asOf: '2026-10-27T14:32:11+08:00', source: 'tencent'|..., persisted: false, text: '盘中 14:32 临时数据' }`；
- `persisted === false` 时前端必须在页面可见处打"盘中临时数据，收盘后以发布数据为准"标记，切后台回前台后**不得**复用（需重新发起 S2）；
- `formatUpdatedAt` 删除日期补时间逻辑；时间为 `null` 时显示"数据更新时间未知"+ `reasonCode`，绝不臆造；
- **`publishedAt`（数据集发布时刻）与 `quoteLayer.asOf`（盘中快照时刻）必须分开展示，禁止合并成一个"更新时间"字段**（见 §④-0.8）。合并会把"收盘模板行情"伪装成"实时行情"，是 PRD §5 第 134 行与验收 #6 明令禁止的行为；
- 后端侧配套：数据层已承诺 `publishedAt` 非空且精确到毫秒（DB `chk_published_time` CHECK 约束，拿不到就不发布），前端因此**不再需要任何兜底**。

## ④ 页面级接口契约草案

> 这是本文重点。所有字段名为**草案**，需在实施文档冻结；命名沿用现网 camelCase 风格以减少迁移成本。
> 约定：`?` 表示可为空；枚举值一律小写下划线；所有日期用 `YYYYMMDD`，所有时刻用 ISO8601 带 `+08:00`。

### 0. 公共部分

#### 0.1 响应信封（三页 + 刷新接口统一）

```jsonc
{
  "code": 0,
  "message": "",
  "traceId": "c1f2...",            // 新增：排障与埋点串联
  "data": {
    "dataset": { /* 见 0.2 */ },
    "session": { /* 见 0.5，仅单股/预测页 */ },
    "dateRole": { /* 见 0.4，仅单股/预测页 */ },
    "...": "页面专属字段"
  }
}
```

#### 0.2 `dataset` —— 三页必须完全一致（PRD §10、验收 #4）

| 字段 | 类型 | 说明 | 前端用途 |
| --- | --- | --- | --- |
| `dataset.version` | string | `dataset_version`，格式 `YYYYMMDD-NN`（定长 11 位、零填充、字典序即时间序），如 `20261027-01`；`NN` 为**同一业务日内的发布序号**，从 `01` 起单调递增，事实更正/补采重算触发同日 +1（对应 PRD §6"事实更正会生成新数据集版本并重算"） | **缓存键组成部分、跨页一致性守卫的唯一判定键**（见 0.4 注） |
| `dataset.ruleVersion` | string | 规则版本，与规则说明页同源 | 模拟卡版本校验；规则页版本校验 |
| `dataset.businessDate` | string(8) | 当前业务日 `D` | 所有"当前"标签的日期来源 |
| `dataset.nextBusinessDate` | string(8) | `N` | 所有"次日"文案的日期来源 |
| `dataset.quoteAsOfDate` | string(8) | 行情截止日 | 展示"按 X 收盘数据计算" |
| `dataset.factAsOfDate` | string(8) | 公告事实截止日 | 监管事实摘要的日期来源 |
| `dataset.publishedAt` | ISO string（**非空、精确到毫秒、带 `+08:00`**） | 数据集发布时间 | "数据更新于 …" 的**收盘口径唯一来源**；与 `quoteLayer.asOf`（盘中口径）**不得合并展示**，见 0.7 |
| `dataset.freshness` | enum | `fresh` / `stale` / `expired` | `stale` → 显示"数据可能过期"；`expired` → 顶部黄条 |
| `dataset.staleReasonCode` | string? | 见 0.3 | 过期/不可用原因 |
| `dataset.state` | enum | `published` / `publishing` / `failed_keep_previous` | `publishing` → 列表页可等待；`failed_keep_previous` → 必须显示"仍为 X 日数据" |

#### 0.4 `dateRole` —— 日期角色与"保留到次日 09:00"

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `dateRole.code` | enum `current`\|`next` | 当前结果集所属日期角色；**与 DB 层 `metric_result.date_role` 同值，不做二次映射**（已与数据层对齐）。`current` = as of D，`next` = for N |
| `dateRole.businessDate` / `nextBusinessDate` | string(8) | 同 `dataset`，冗余便于卡片使用；`D`/`N` 的业务日语义只落在这两个字段上 |
| `dateRole.switchAt` | ISO string | 下一次角色切换时刻（次日 09:00） |
| `dateRole.serverTime` | ISO string | **服务端当前时间，前端判定期的唯一依据** |
| `card.retainUntil` | ISO string? | 单卡（如"当日已触发"）的保留截止时刻 |

**前端硬规则：**
1. 用 `dateRole.serverTime` 与 `retainUntil` 比较，不用 `new Date()`；`serverTime` 缺失时按"保留"处理并上报；
2. **版本守卫只比较 `datasetVersion` 字符串本身**，不得用 `businessDate + dateRole` 复合判断——一个 `dataset_version` 内同时存在 `current` 与 `next` 两组结果行（数据层确认：版本级唯一约束是 `(business_date, status='published')` 全局至多一行），用复合键会在每次正常发布时误判为"跨版本"；
3. 缓存键 `...:{datasetVersion}:{dateRole}:...` 中的 `dateRole` 仍保留（同一版本内确实有两套结果需要分开缓存），但**不参与版本变更判定**。

#### 0.5 `session` —— 两段式刷新的条件（**前端不得自行判定交易时段**）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `session.intradayEligible` | bool | 后端按交易日历 + 交易时段 + 证券可交易状态判定；`true` 才允许 S2 |
| `session.ineligibleReasonCode` | string? | `NON_TRADING_HOURS` / `NON_TRADING_DAY` / `SECURITY_NOT_TRADABLE` / `LUNCH_BREAK` / `AFTER_CLOSE` |

**监管状态 `undetermined`（PRD 缺口，2026-10-27 已拍板）：** PRD §3.2 只有 safe/ordinary/severe 三值，但 §3.2 第 49 行要求"3 日计算触发但公告未核验时不得显示安全"。没有第四枚举，前端只有两条路——显示"安全"（违规）或显示空白（体验崩）。

**总监裁决：`undetermined` 接受新增，但严格定义为「展示态」，不是第五种监管状态。**四条硬约束：

| # | 约束 | 落地方式 |
| --- | --- | --- |
| a | **仅当监管判断所需依赖中任一项为 `unavailable` / 待核验时出现** | 后端在 `regulatory.state` 写 `undetermined` 的前提：`reasons` 非空。前端不判断触发条件 |
| b | **必须同时携带至少一个 `reasonCode`，不允许裸 `undetermined`** | 契约层：`regulatory.unavailable.code` 非空；接口校验器拒绝 `state=undetermined && reasons=[]` |
| c | **视觉用中性灰 + 文案「暂不可判定」** | `tone='unknown'`，CSS token `--tone-unknown`；**禁止与 `safe` 同色同文案，禁止任何回退到「安全」的兜底** |
| d | 与 PRD §3.2「不得显示安全」条款**并列写入**，并追加验收断言 | 数据层断言：不存在 `state='undetermined' AND reasons 为空` 的行；前端断言：`enum.js` 中 `undetermined` 映射的 `tone !== 'safe'` |

**在 `stateTags` 与 `regulatoryBanner` 两处的出现规则：**

| 位置 | 规则 |
| --- | --- |
| `stateTags[]` | `undetermined` **不进** `stateTags`。`stateTags` 只承载交易/证券属性类标签（`suspended`/`terminated`/`delisting_period`/`st`/`unknown_state`）。`unknown_state` 属交易状态域（PRD §3.1"未知状态仅属于交易状态"），与监管域的 `undetermined` 严格分离，两者可同时出现 |
| `regulatoryBanner` | `undetermined` 经 `regulatoryBanner.code = 'undetermined'` 表达，形如 `{ code: 'undetermined', text: '暂不可判定', tone: 'unknown', cardClassToken: 'unknown', reasons: [{code, text}] }`。卡片边框/背景用中性灰（对应 PRD §5.1 的浅粉/红边之外的第四种"灰边灰底"），并**必须并列渲染 `reasons[]`**，不允许只显示"暂不可判定"四字 |

**组合示例（前端必须能表达）：**
- `tradeState=suspended` + `stateTags=[suspended]` + `regulatory.state=severe` + `regulatoryBanner.code='monitoring'` → 停牌 + 严重监管中，四项显示最后有效结果并标结果日期；
- `tradeState=unknown` + `stateTags=[unknown_state]` + `regulatory.state=undetermined` + `reasons=[TRADING_STATE_UNKNOWN]` → 灰卡"暂不可判定"+原因，四卡不可用；
- `tradeState=normal` + `stateTags=[]` + `regulatory.state=undetermined` + `reasons=[ANNOUNCEMENT_BATCH_INCOMPLETE]` → 正常交易但监管结论待核验，**不得显示"安全"**。

> 2026-10-27 与数据层评审对齐后的定稿项，前端侧按此实现；DB 侧落地见 `数据模型与性能设计_宋砚秋.md`。

| 项 | 定稿 | 前端侧约束 |
| --- | --- | --- |
| 缺因枚举 | 采用本文 0.3 的 19 个 `reasonCode`，DB 建 `missing_reason` 表同值，`metric_result.missing_reason_code` 引用，附 CHECK 约束 | 前端只做 `code → 中文` 映射，不做语义判断；**未登记 code 显示通用"数据不可用"并上报埋点** |

**`pdfCleanedReasonCode` 枚举（本文定稿）：**

| code | 前端文案 | 行为 |
| --- | --- | --- |
| `MONITOR_PERIOD_ENDED` | 监管期已结束，附件按保留策略清理 | 优先跳来源原文（`sourceUrl`） |
| `RETENTION_EXPIRED` | 附件保留期已满，已清理 | 优先跳来源原文 |

#### 0.8 两个"更新时间"必须分开（数据层提醒，前端采纳）

| 字段 | 含义 | 展示位置 | 前端规则 |
| --- | --- | --- | --- |
| `dataset.publishedAt` | 数据集发布时间（I 组 `dataset_version`） | 收盘口径"数据更新于 …" | 唯一来源，直接渲染 |
| `quoteLayer.asOf` | 盘中行情快照时刻（覆盖层自带） | 盘中口径"盘中 {HH:mm} 临时数据" | 仅在 `quoteLayer.kind === 'intraday'` 时展示 |

**前端硬规则：** 二者**不得合并成一个"更新时间"字段**。展示逻辑固定为：
1. `quoteLayer.kind === 'intraday' && quoteLayer.persisted === false` → 展示 `quoteLayer.asOf`（盘中临时），并在旁边保留一行小字"收盘结果更新于 {publishedAt}"；
2. 覆盖层不存在 / 失效 / 回落 → 展示 `publishedAt` 并标明"收盘结果"；
3. 任一时间缺失 → 展示 `reasonCode` 文案（如 `DATASET_NOT_PUBLISHED`），**绝不臆造时刻**。

这条直接对应 PRD §5 第 134 行"实时源失败时使用最近成功行情并明确时间/不可用状态，不以模板行情伪装实时"与验收 #6。

## ⑤ 刷新时序与降级方案

### 5.1 设计原则

1. **两段式、串行**：S1（已发布数据集）→ 渲染 → S2（盘中行情，仅当 `session.intradayEligible === true`）。S1 决定 `dataset.version`，必须先行；S2 依赖 S1 的 eligibility，必须串行。
2. **条件判定完全后端化**：前端**不判断**是否交易时段、是否可交易、是否集合竞价。只做节流与去重。
3. **本地时钟只用于节流**：`Date.now()` 仅用于"距上次成功刷新是否超过 `refreshThrottleSeconds`"和"切后台回前台是否超过 60s"，绝不用于日期角色判定。
4. **缓存先行渲染**：`onLoad` 先用 storage 快照出骨架/内容，再走网络；避免白屏。
5. **下拉刷新语义收敛（2026-10-27 已拍板）**：下拉 = 重跑 S1（已发布数据集刷新），**禁止触发 S2**；盘中实时仍只由首次进入编排触发。详见 §④-5 的 5.x 节。

### 5.2 时序

```text
onLoad
 ├─ [0ms]   读 storage(datasetVersion 键) → 立即渲染（骨架 or 上次内容 + "数据更新于 X"）
 ├─ [0ms]   S1: POST /api/session/refresh        (timeout 8s, retry 1)
 │            └─ 返回 dataset.version / session.intradayEligible
 ├─ [~800ms] GET  页面主查询（带 version）         (timeout 8s)
 │            └─ 版本守卫：version ≠ 当前接受版本 → 提示"数据版本已更新"
 ├─ [~1200ms] 渲染正式结果（首屏完成）
 └─ [条件]   if (session.intradayEligible) S2: POST /api/quotes/realtime (timeout 6s, retry 0)
              ├─ 成功 → 合并覆盖层（quoteLayer.kind='intraday'）+ 角标
              └─ 失败 → 保留收盘基线 + "实时行情暂不可用（{reasonCode}）"

onShow（切后台回前台）
 ├─ 距上次成功 > 60s 或 datasetVersion 已变 → 重跑 S1（不自动跑 S2）
 └─ 网络恢复事件（wx.onNetworkStatusChange）→ 同上
```

### 5.3 并发去重与防抖

全局单例 `store/refreshCoordinator.js`：

```js
const inflight = new Map()   // key -> Promise
const lastOk   = new Map()   // key -> { at, version }

function keyOf(page, param) { return `${page}:${param}` }

async function ensureFresh(page, param, { force = false } = {}) {
  const key = keyOf(page, param)
  const prev = lastOk.get(key)
  const throttle = getApp().globalData.refreshThrottleMs || 60000

  // 1) 节流：非强制且刚成功过 → 直接用 store 中已有数据
  if (!force && prev && Date.now() - prev.at < throttle) return readStore(key)

  // 2) 并发去重：同一 key 只存在一个 in-flight
  if (inflight.has(key)) return inflight.get(key)

  const task = runTwoPhase(key, page, param).finally(() => inflight.delete(key))
  inflight.set(key, task)
  return task
}

async function runTwoPhase(key, page, param) {
  // ---- S1：已发布数据集 ----
  let s1
  try {
    s1 = await api.refreshSession({ page, param, timeout: 8000 })
  } catch (e) {
    const cached = readStore(key)
    if (cached) { markStale(cached, 'S1_FAILED', e); return cached }   // 降级：缓存 + 过期标记
    throw renderableError('DATASET_NOT_PUBLISHED', e)                   // 无缓存：错误态，绝不显示 0/安全
  }

  // 版本守卫：只比较 datasetVersion 字符串本身（version 内 dateRole 不唯一，见 0.4 注 2）
  const accepted = getApp().globalData.datasetVersion
  if (accepted && s1.dataset.version !== accepted) {
    notifyVersionChanged(accepted, s1.dataset.version)   // 顶部提示条，不静默混用
  }
  getApp().globalData.datasetVersion = s1.dataset.version

  const data = await api.loadPage(page, param, { version: s1.dataset.version })
  writeStore(key, data)          // 键含 version + dateRole
  render(data)                   // 首屏完成

  // ---- S2：盘中覆盖层（条件由后端给）----
  if (s1.session && s1.session.intradayEligible) {
    try {
      const s2 = await api.realtimeQuotes(param, { timeout: 6000 })
      render(mergeIntradayLayer(data, s2))     // quoteLayer.kind='intraday', persisted=false
    } catch (e) {
      render(markIntradayFailed(data, e))      // "实时行情暂不可用，显示 X 收盘数据"
    }
  }

  lastOk.set(key, { at: Date.now(), version: s1.dataset.version })
  return data
}
```

要点：
- `inflight` 保证三页同时打开（tabBar 切换很快）不会打三次刷新；
- `force` 只在下拉刷新与用户点刷新按钮时为 `true`；
- S2 的 `retry: 0`（沿用现网 `utils/api.js:21,26` 的设定），实时源失败快速降级，不拖慢首屏；
- 单股页 S2 的 `tsCodes` 只含当前 1 只股票；预测页 S2 只含首屏可见的 ≤ 20 只，**不做全市场实时报价**。

### 5.4 降级矩阵

| 场景 | S1 | S2 | 前端展示 |
| --- | --- | --- | --- |
| 非交易时段（含午休/盘后/休市） | ok | **不发起** | 收盘数据集 + "数据更新于 {publishedAt}"（收盘口径）；`session.ineligibleReasonCode` 仅用于解释，不展示为错误 |
| 交易时段 · 证券可交易 | ok | ok | 覆盖层 + "盘中 {quoteLayer.asOf HH:mm} 临时数据，收盘后以发布数据为准"+ 小字"收盘结果更新于 {publishedAt}"（两时间并存，见 0.8） |
| 交易时段 · 实时源失败 | ok | fail | 回落收盘基线 + 黄条"实时行情暂不可用，当前显示 {quoteAsOfDate} 收盘数据（更新于 {publishedAt}）"（**禁止拼 15:00**） |
| 停牌 / 终止上市 | ok，`intradayEligible=false` | **不发起** | 状态标签 + 最后有效结果 + "结果日期 {asOfDate}" + 不生成新的收盘预测 |
| S1 失败 + 有缓存 | fail | 不发起 | 缓存内容 + 顶部"数据更新于 X，可能已过期" + 重试按钮（**不显示 0/安全**） |
| S1 失败 + 无缓存 | fail | — | 整页错误态 + 重试；空态文案由 `reasonCode` 给 |
| `dataset.state='publishing'` | ok | — | 列表页显示"数据集发布中"，可退避等待；不显示空态 |
| `dataset.state='failed_keep_previous'` | ok | — | 顶部黄条"今日数据集发布失败，当前显示 {quoteAsOfDate} 数据" |
| 跨页 version 不一致 | ok | — | 顶部提示"数据版本已更新" + 一键刷新；**不混用** |
| 弱网（RTT > 1s） | 超时 | 跳过 | 缓存优先渲染；超时阈值按 `navigator` 降为 5s |

## ⑥ 本地模拟方案（PRD §5.3）

### 6.1 可行性结论：**可行，且现网已跑通骨架**

- 现网已由后端提供向量：`simulationBase.stock/index` 与 `stockByWindow/indexByWindow`（`market_service.py:2310-2327`），前端 `bestDeviation`（`stock/index.js:359-381`）本地枚举窗口。说明链路可行。
- 数据量估算：窗口上限 30 → 向量长度 ≤ 31；加 `dates` 后每条约 `31 × (数字 + 8 字符日期)` ≈ **1.2～1.8 KB**（JSON，未压缩）。配合 gzip（云托管默认开启）实际传输 < 1 KB。**下载体积不是问题**，无需分页或拆分。
- 计算量：输入 10 天 × 2 列，每次重算 = 10 行 × (枚举 ≤ 30 窗口 × 30 元素) ≈ 9,000 次浮点乘加，**< 5ms**，可放在 `bindinput` 里（配 120ms 节流）。

| 风险 | 现状 | 对策 |

### 7.2 实施要点

1. **setData 拆分**：单股页首次渲染拆 4 段（基础信息 → 状态卡 → 四卡 → 模拟基础），避免一次性 100KB+；四卡用 `wx:key="ruleKey"` 复用。
2. **列表分页 + 复用**：monitor/prediction 首屏 20 条，滚动到底加载下一页（`nextCursor`）；行内容抽成组件（P2-5）；`rawItems` 移出 `data`。
3. **请求合并**：
   - 单股页去掉 `getMonitor({type:'all'})`（P2-2），减少一次全量请求；
   - 三页共享 `datasetStore`，`dataset` 只拉一次并广播；
   - 预测页 S2 只请求首屏可见标的。
4. **缓存策略**（ARCH §5 要求键含版本）：
   - 键：`yidong:v4:{page}:{datasetVersion}:{dateRole}:{param}`；
   - TTL：收盘数据集到 `dataset.publishedAt + 24h`；盘中结果**不落缓存**（`persisted:false`）；
   - 容量：最多保留 10 个 key，写入新版本时清理同名旧版本；storage 总量 ≤ 2MB（微信单小程序上限 10MB、单 key 1MB）；
   - 失效：`datasetVersion` 变化即失效；`freshness='expired'` 时展示但标黄。
5. **图片/圆环**：图标转 SVG（现网已部分 SVG）或 iconfont；圆环保留 `conic-gradient` 但四卡固定，避免长列表重绘；预测/监控列表**不用**图片，纯文本 + 色块。
6. **包体积**：主包 ≤ **1.5MB**（现网远低于此）；单页面 JS ≤ 100KB；`rules`/`privacy` 移入分包 `packageLegal`（非 tab 页，可分包）；开启 `minifyWXSS/minifyWXML`（已开，见 `project.config.json`）、上传时压缩、`uploadWithSourceMap` 生产改为 `false`。

### 7.3 弱网与错误态

- 三档：① **加载中**（骨架屏，monitor 已有 `skeletonRows`）；② **错误可重试**（网络/超时/5xx，统一文案 + 重试按钮）；③ **数据不可用**（业务 `unavailable` + `reasonCode`，**不用错误页样式**，用中性灰卡片 + 原因，避免用户误以为网络坏了）。
- 错误文案统一走 `utils/enum.js`（P2-10）；所有错误卡片展示 `traceId` 后 6 位便于客服排查。
- 网络状态监听：`wx.onNetworkStatusChange` 恢复时自动重试一次 S1（不重试 S2）。
