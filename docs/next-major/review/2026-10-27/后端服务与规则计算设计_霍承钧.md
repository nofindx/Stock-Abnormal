## ① 总评结论

**总判：PRD §9.2 的五层职责（数据 → 规则 → 计算 → 公告 → 业务服务）划分是对的、可落地的；但现网 `server/` 与这五层之间不是"补字段"的差距，而是"职责错位"的差距。若按现状顺序改造（先建表、再补字段、最后调口径），会把三处错误口径固化进新结构，届时改正要重放全部历史数据集。正确顺序是：先收敛唯一口径源 → 再统一计算入口 → 再原子化发布 → 最后做性能。**

分五层判断：

### 1）规则层：不是唯一口径源，而是四处硬编码 + 前端一份

同一份"板块阈值/基准指数/板块归属"规则，现网有五个互相不引用副本：

| # | 位置 | 内容 |
| --- | --- | --- |
| 1 | `server/rules/catalog.py:60-72` | `BOARD_RULES` 四个板块阈值 |
| 2 | `server/services/market_service.py:47-48` | `INDEX_BY_MARKET` / `INDEX_BY_BOARD` 指数映射 |
| 3 | `server/services/market_service.py:127-137` | `_board_label()` **用代码前缀猜板块**（`688`→科创板、`300`→创业板、`8/4`→北交所） |
| 4 | `server/services/monitor_service.py:35-40` | `MONITOR_PERIOD_TRADING_DAYS` 监管期长度 |
| 5 | `miniprogram/pages/stock/index.js:100-120` | 前端硬编码北交所 150/60/300/75 |

PRD §4.2 第 95 行要求「具体板块、基准指数和阈值必须由证券属性与规则版本确定，不能由页面或接口硬编码」，§10 第 228 行要求「规则说明页、后端计算、模拟基础和接口文案引用同一 `rule_version`」。现状两条都不成立。

### 2）计算层：同一业务问题有两条互不相同的实现路径

- **路径 A（PriceBar）**：`server/calculations/engine.py`，输入收盘价序列，`detect_severe_abnormal()` 里 `consolidate_same_direction_events()` 把重叠窗口合并成 episode（`:296-352`，docstring 明写 "A continuous run of overlapping windows in one direction is **one occurrence**"）。
- **路径 B（收益向量）**：`server/services/market_service.py`，`_vector_metrics()`（`:1723-2011`）用滚动 30 点收益率向量重算一切，10 日同向走 `confirmed_same_direction_event_ledger()`（engine 的 `confirmed_*` 版本）。

两条路径的入窗日**不一致**：A 用 `item.start_date`（`engine.py:490`），B 的确认事实分支用 `endDate`（`market_service.py:1986`）、纯计算分支用 `startDate`（`:1991`）。而 PRD §4.3 第 107 行与验收 #11 规定唯一入窗日是 `fact_end_date`。**同一只股票走两条路径会给出不同的 10 日同向次数**，直接决定"严重异动"红牌。

### 3）公告层：事实身份体系不成立，多源转载重复计次是必然事件

`monitor_service.py:1133/1189/1217` 三处 `source_id = sha256(url)[:24]`；`fact_ledger.py:105` 兜底材料也含 `sourceUrl`。巨潮、交易所官网、18.cn、中泰转载同一份公告时 URL 必然不同 → 多条事实 → 计数放大。`engine.py:355-405` 试图用 `(event_date, direction, content_hash)` 归并，但 content_hash 来自 `sha256(title\nbody)`（`monitor_service.py:1094`），不同来源 PDF 抽取正文不同 → hash 不同 → 不归并；更严重的是 `:393` 的判定**与注释意图相反**（`stable_hash` 为真才按日期方向归并，为假才退回 `source_id`，恰好是不稳定 hash 才会归并）。宋文 P1-1/P1-2 已给出 `fact_key`/`source_id` 两层身份的改法，本文在 §⑥ 补充**生成这两层身份的解析前置条件**（`fact_end_date` 与 direction 必须由正文结构化抽取得到，否则标 `identity_missing`）。

### 4）发布层：没有版本，三页同版本在结构上不可能

`market_calc_repository.py:150-170` 的 `prediction_dataset` 主键是 `(dataset_role, target_trade_date)`，读取走 `ORDER BY updated_at DESC LIMIT 1`（`:705-725`）；`market_service.py:2816-2921` 的 `today` 与 `next_day` 是两次独立事务。宋文 P1-4 已设计两阶段发布 + `dataset_pointer`，本文在 §⑦ 补充**编排时序、租约、幂等与门禁阈值**。

### 5）可观测性：缺因是自由文本，"不可用不得变安全"无法被机器校验

`server/data/stock_state.py:99` `data_error: str`；`market_service.py:2231-2236` 直接拼中文句子；`monitor_service.py:1063` `reason` 为自由串。PRD §3.4 与验收 #9 要求"均能显示明确缺因"。没有枚举就无法做发布门禁、无法聚合告警、无法在 CI 里断言。

**放行建议：** 后端侧 P1 共 14 项。**B-1～B-6 必须在写实施文档前定稿**——它们决定配置 schema、ID 体系与次日口径，后改等于重放全部历史；**B-7～B-14 可与实施并行**，但必须在首个灰度 `dataset_version` 发布前完成。另有 11 项产品口径需用户拍板（见 §⑪），其中「次日预测口径」与「10 日同向是否入预测池」会阻塞 M1。

## ② P1 阻塞问题清单

> P1 定义：不改则 vNext 后端无法落地，或上线后会产出错误的监管结论（把"不可用"变成"安全"、把"一次"计成"多次"、把"下周一"当成交易日）。

### B-1 规则口径硬编码在 5 处，规则模块不是唯一口径源
**证据：** `rules/catalog.py:60-72`；`market_service.py:47-48`、`:56`、`:127-137` `_board_label`；`monitor_service.py:35-40`；`miniprogram/pages/stock/index.js:100-120`。
**问题：** PRD §4.2 第 95 行、§10 第 228 行均不满足；板块/指数一旦变更（如北交所指数换锚、科创板阈值调整）需改 5 处代码且无法按生效日回溯。
**建议改法：**
1. 规则全面外部化（§④ 的 YAML + JSON Schema），`catalog.py` 降级为「加载器 + 冻结快照」，不再存字面量；
2. 板块归属、指数映射下沉为带生效区间的数据（宋文 §4.2 的 `security_board_history` / `index_board_map_history`），**删除 `_board_label` 的代码前缀猜测**；
3. 规则模块导出 `/api/rules/current` 供规则说明页与模拟卡消费，前端不再硬编码（对应夏文 P2-9）。

### B-2 三个互不相同的「规则版本」标识符共用一列
**证据：** `rules/catalog.py:14` `RULE_VERSION="RULE-2026-10-24.1"`；`market_service.py:62` `PREDICTION_RULE_VERSION="v67"`；`monitor_service.py:45` `MONITOR_RULE_VERSION="...-v28"`；落库列名统一为 `rule_version`（宋文 P1-8）。
**问题：** 无法判断某条结果是因哪个口径变化需要重算，PRD §4.5「规则版本变化 → 新增规则版本并重算数据集」无法实现；`v67` 这种版本号还被写进了 `calculationInput.sameDirectionWindowPolicy` 之外的展示字段（`market_service.py:2328`），暴露给前端。
**建议改法：**
- 按宋文 P1-8 拆成 `rule_version`（口径）/ `generator_version`（生成器）/ `announcement_parse_version`（解析）三列；
- 新增规则版本注册表 `rule_version_registry`（见 §④-6），含 `effective_from/effective_to/requires_replay/supersedes/config_hash`；
- **对外接口只暴露 `rule_version` 与 `dataset.version`**，`generator_version` 仅进日志与 `job_run`，`announcement_parse_version` 仅进事实证据。

### B-3 10 日同向：入窗日用 `start_date`，且重叠窗口被合并为一次
**证据：** `market_service.py:488-491`（`recent_start <= item.start_date <= recent_end`）；`market_service.py:1991`（纯计算分支用 `startDate`）；`engine.py:296-352`（episode 合并，docstring 明写 one occurrence）；`engine.py:490`。另 `market_service.py:1986`（确认事实分支用 `endDate`）与 `:1991` 不一致。
**问题：** 三处口径互不相同，均与 PRD §4.3 第 107 行「事件唯一归属日为……`fact_end_date`」和验收 #11 冲突；重叠窗口被合并违反验收 #1「重叠公告事实可分别计次」。
**建议改法：**
1. 计算模块内**唯一**入窗字段 `fact_end_date`，窗口过滤统一 `window_start <= fact_end_date <= as_of`；
2. **删除 `consolidate_same_direction_events` 的 episode 合并**；不同 `fact_id` 的事实一律分别计次；同一 `fact_id` 的重复由 `same_direction_event.fact_id UNIQUE` 兜底（宋文 §4.7）；
3. 若产品坚持保留"连续 episode 视为一次"，必须**另立一个 `rule_version`** 并在配置里标 `basis: product_inference`（PRD §4 第 74 行要求区分官方明文与产品推断），新旧口径各占一个版本以便对账（见 §⑨-2）；
4. 迁移期走影子计数：双口径各算一份落 `quality_check_result`，差异清单人工复核后再切。

### B-4 事实身份含来源 URL，单公告多事实靠字符串前缀造 ID
**证据：** `monitor_service.py:1133`、`:1189`、`:1217`；`:1088` `sha256("ordinary-reset:"+source_key)`；`:1051-1053` pending 同前缀；`fact_ledger.py:105`；`engine.py:386-396`（hash 稳定性判定反向）。
**问题：** 多源转载必然重复计次（违反 PRD §4.3 第 107 行与验收 #11）；单公告多事实靠调用方手工拼前缀，DB 无法校验（违反验收 #1）。
**建议改法：**
- `fact_key = sha1(ts_code | fact_type | fact_start_date | fact_end_date | direction)`，**不含任何来源字段**；
- `source_id = sha1(source_code | source_announcement_id)`，源级幂等；
- `regulatory_fact` 上建 `UNIQUE KEY uk_fact_key`，`INSERT ... ON DUPLICATE KEY UPDATE` 只更新证据/置信字段；
- **前置条件**：`fact_end_date` 与 `direction` 必须来自正文结构化抽取；缺失则 `confidence_state='identity_missing'` 且**不得形成 `fact_key`、不得计次**（回执第 31 行：生产数据集匿名计次数必须为 0）；
- 删除 `engine.py:355-405` 中基于正文 hash 的归并，改由 `uk_fact_key` 承担。

### B-5 交易日历源失败退化为「周一至周五」
**证据：** `monitor_service.py:665-689` `_trade_dates()`：`except Exception: pass` 后返回 `weekday() < 5` 的日期序列；方法 docstring 却写着「绝不把自然日冒充交易日」——注释与实现直接矛盾。另 `market_service.py:867-877` `_market_context` 在 `len(open_dates) < 2` 时才抛错， calendars 返回 2~30 个"开放日"时静默接受。
**问题：** 节假日被当成交易日 → 错误的偏离值、错误的 10 日同向窗口、错误的监管期起止。**这是"不可用变成安全"的最危险入口**——它不报错，直接算出一个看似合理的"安全"。
**建议改法：**
1. 交易日历是**硬依赖**，任何降级都是禁止的：源失败 → `availability='unavailable'` + `missing_reason_code='CALENDAR_MISSING'`，该股票全部依赖日历的项标 `unavailable`，绝不返回数值；
2. `trade_calendar` 落库（宋文 §4.3），运行期只读本地表；上游调用收敛到每日一次增量任务；
3. 启动时校验日历覆盖「最近 400 个自然日 + 未来 30 个自然日」，不足则拒绝启动（fail fast）；
4. 删除 `_trade_dates` 的 weekday 兜底分支，改为抛 `CalendarUnavailable`。

### B-6 预测页整体排除「10 日同向」且静默丢弃，无排除原因
**证据：** `market_service.py:266-271` `_prediction_item_allowed()`（`if rule_key == "same_direction_10d": return False`，无任何 reason）；`:3106-3109` `rules` 列表初始只含 `severe_10d`/`severe_30d`；`:282` 还有一个永不执行的重复分支。
**问题：** PRD §7 第 176 行明确要求预测筛选「**10 日同向**、10 日偏离、30 日偏离」；PRD §7 第 183 行要求「若因资格或数据状态不展示，接口返回排除原因」。现网两条都违反，且用户会把"不显示"理解为"没有风险"（PRD §3.4 禁止）。
**建议改法：**
- 产品先拍板（见 §⑪-2）。**无论哪种结论，都必须写进 `rules.prediction_policy` 并随 `rule_version` 下发**；
- 接口必须返回 `excluded[]`（夏文 P1-7）：`{tsCode, ruleKey, reasonCode, text}`；
- 若决定入池，需定义 `same_direction_10d` 的「可能触发」口径（见 §⑤-4 与 §⑪-1）；
- 单股四卡不受影响，始终展示四项（PRD §7 第 176 行）。

### B-7 缺因是自由文本，无法做门禁、告警与 CI 断言
**证据：** `data/stock_state.py:99` `data_error: str`；`market_service.py:2231-2236` 中文拼接；`monitor_service.py:1063` `reason` 自由串；`monitor_service.py:642` `:704` 直接拼中文档位。
**问题：** 验收 #9「均能显示明确缺因」无法机器校验；发布门禁无法按缺因聚合。
**建议改法：**
1. 缺因收敛为枚举 `missing_reason_code`（夏文 §0.3 的 19 个草案，本文 §⑦-5 给出后端生产逻辑与归属层）；
2. 枚举**由规则模块维护**（`rules.missing_reason_registry`），启动即校验；DB 侧 `missing_reason` 码表 + CHECK 约束（宋文 §4.9）；
3. `api_contract_check.py` 增加闭合断言（见 §⑨-5）；
4. 文案只留在前端 `enum.js` 与规则模块的 `label_zh`，**后端任何写路径不得拼中文原因句**。

### B-8 不保存原始日线 + 30 点收益向量硬截断，历史不可重放
**证据：** `market_calc_repository.py:3-4` docstring「不保存原始日线」；`:101-112` `stock_return_vector JSON`；`market_service.py:1124` `ordered_stock[-30:]`；`:2600` `vector[-30:]`；`:2648` `vector[-30:]`。
**问题：** 30 个收益点无法重算 30 日窗口（需 31 个收盘点）；停复牌基线、重置生效日一旦变化，旧窗口无法重建；PRD §10「历史版本可重放」结构上不可能。
**建议改法：**
- 新建 `daily_bar` 原始日线表（宋文 P1-3），保存 ≥3 年；主存「未复权收盘价 + `adj_factor`」，前复权序列读取时按当日最新因子换算、不落库；
- **计算模块的正式输入改为收盘价序列 + 日历 + 事实 + 重置边界**，不再以收益向量为输入；
- `security_return_vector` 保留为查询加速派生表，**不作为重放依据**，且长度放宽到 31+（30 日窗口需 31 点）。

### B-9 单股/监控/预测不是同一 `dataset_version`，发布非原子
**证据：** `market_calc_repository.py:150-170`、`:705-725`；`market_service.py:2816-2921`；`market_service.py:618` 原地 upsert。
**问题：** PRD §9.3 第 224 行「三页只能读取同一发布版本」与验收 #4 在结构上不可能满足。
**建议改法：** 采用宋文 §5 的两阶段发布 + 单行 `dataset_pointer`；本文 §⑦-2 给出编排时序、租约与门禁阈值。补充一条：**请求上下文必须固化 `V`**，单股 → 预测 → 监控的同一次会话内跨接口沿用同一个 `V`；`V` 对应的 `quote_cutoff_date` 早于当前业务日 → 返回 `DATASET_STALE`，不返回上一版本数值。

### B-10 公告与事实账本跑在容器临时盘，PDF 落 `/tmp`
**证据：** `monitor_service.py:62` `MONITOR_DB_PATH=/tmp/stock-abnormal/monitor.db`；`:195` `MONITOR_PDF_DIR=/tmp/stock-abnormal/monitor-pdf`；`data/fact_ledger.py:14` `import sqlite3`；`:50-54`。
**问题：** 云托管多实例 + 滚动发布时临时盘不共享、不持久，PRD §6「事实先入账」随容器重启丢失；PRD §6/验收 #13 的对象存储地址/哈希/清理记录不存在。
**建议改法：** 全量迁 MySQL（宋文 P1-7）；PDF 迁对象存储，MySQL 只存 `pdf_object_key`/`pdf_sha256`/`pdf_size_bytes`/`pdf_url`；清理走 `pdf_cleanup_log`。本文 §⑥-7 给出 PDF 生命周期状态机。

### B-11 无任务租约、无幂等、DDL 失败静默
**证据：** `market_calc_repository.py:126-133` `market_calc_job` 无 `lease_until`/`owner`（对比 `:171-185` `prediction_job` 有）；`:194-217` `ALTER TABLE` 包在 `try/except Exception: pass`；`monitor_service.py:99-107` 同模式。
**问题：** 多实例并发重算、重复打上游；某次 ALTER 失败被吞掉后计算结果静默缺列；PRD §9.3 第 224 行「失败继续提供上一成功版本」无法保证。
**建议改法：** 统一 `task_lease`（宋文 §5.2）；引入 `schema_migration` 表 + 两阶段 DDL（加列 → 双写 → 切读 → 删旧列）；所有明细写 `INSERT ... ON DUPLICATE KEY UPDATE`；旧任务写入前比对 `generation`，落后则中止。

### B-12 逐股循环调 Tushare，配额与耗时不可控
**证据：** `market_service.py:900-904` `_daily()` 逐股请求（仅靠进程内 `_daily_cache` 兜底）；`:2605-2608` 新上市股票**逐股**调 `daily(ts_code=...)` 补历史；`:600-607` 历史覆盖审计按 10 天分块循环调 `suspend_d`（每次全市场）；`tushare_client.py:169-177` `trade_cal` 仅进程内缓存 43200s、`:193-201` `suspend_d` 3600s，多实例各缓存一份。
**问题：** 全市场约 5500 只股票，逐股补历史最坏 5500 次请求；Tushare 有频率限制，触发限流后整批失败；进程内缓存在 2+ 实例下放大 N 倍上游调用。
**建议改法：**
1. **日线一律按交易日批量拉取**：`daily(trade_date=YYYYMMDD)` 一次拿全市场，禁止在批处理路径出现 `daily(ts_code=...)`；新上市股票的历史同样用批量日线按日补齐；
2. `suspend_d` 每日一次增量落 `suspension` 表，覆盖审计改为只读本地表（宋文 P1-9）；
3. 上游调用统一走**源级令牌桶**（Redis `INCR+EXPIRE`，不可用时退化为进程内令牌桶）+ 指数退避 + 熔断；
4. 进程内缓存仅保留 5s LRU 且键含 `dataset_version`，跨实例一致性由 MySQL/Redis 承担。

### B-13 次日「可能触发」口径有两套实现，且与 PRD 定义不明
**证据：** 单股页走 `market_service.py:1608-1720` `_next_day_rule_candidates()`（反解所需涨跌幅 ≤ 涨跌停板 → 可能触发）；预测列表走 `:3126-3156`（`_required_up_percent` + `distance > limit` 排除 + `severe_10d` 已触发则次日不重复）；两者对 `reset_window`、`scope`、方向的处理不同参不同。
**问题：** PRD §7 第 181 行只说「次日『可能触发』是计算候选」，未定义"可能"的数学含义；两套实现对同一只股票可能给出不同结论，直接违反验收 #4「单股与预测的共同规则结果在数值、方向、阈值、日期和触发状态上相同」。
**建议改法：**
1. 次日判定**只能有一个实现**（计算模块 `next_day_assessment()`），单股与预测页都消费它的输出；
2. 口径写进 `rules.next_day_definition` 并随 `rule_version` 下发（推荐方案见 §⑤-4，需产品拍板 §⑪-1）；
3. 输出必须包含 `assumption`（指数次日涨跌幅假设）、`triggerPrice`、`tolerancePct`、`limitRatio`，否则不可解释（现网 `TriggerPrice` 有 `trigger_price`/`remaining_percent` 但**不输出指数假设**，见 `engine.py:167-192`）。

### B-14 停牌原因无分类来源，重置边界靠运行时推导
**证据：** `market_service.py:1088-1127` `_trim_vectors_after_suspension()` 只识别"缺口"，不区分「严重异动相关停牌」与「普通事项停牌」；`:1264-1273` `_monitor_rule_reset_date()` 在**运行期**从公告快照重新推导重置日；重置生效日散落在 `ruleResetDate` 字段（`monitor_service.py:1108`、`:1145`）。
**问题：** PRD §4.4 第 120 行要求区分两类停牌（同向事件一"延续"一"清零"），第 120 行还要求「不能只凭停牌时间与异动日期相邻来推断因果」；现网无停牌原因分类来源，只有时间缺口推断。重置日在运行期推导 → 无法审计、无法重放（宋文 §4.8）。
**建议改法：**
1. `suspension` 表增加 `suspension_reason_class ∈ {severe_related, ordinary, unconfirmed}`，**只能由交易所/上市公司正式公告或交易状态来源分类**；
2. 重置边界落成 `reset_boundary` 行（宋文 §4.8），每行可追溯到 `trigger_fact_id` + 生效日 + 影响/保留指标；
3. `reason_class='unconfirmed'` 时：保留事件账本，受影响的重置判断标 `RESET_BOUNDARY_UNKNOWN` 待核验，**不猜测清零也不猜测延续**（PRD §4.4、验收 #12）。

## ④ 规则模块设计

### 4.1 定位与硬约束

```
server/rules/
├── schema/rule_set.schema.json     # JSON Schema（Draft 2020-12）
├── configs/
│   ├── RULE-2026-10-24.1.yaml      # 已生效（由 catalog.py 现有常量迁移而来）
│   └── RULE-2026-11-xx.1.yaml      # 待发布
├── loader.py        # 加载 + 校验 + 冻结
├── registry.py      # 版本注册表与生效区间解析
├── selectors.py     # 无副作用查询 API
└── tests/
```

**五条硬约束（违反任一即启动失败）：**

1. **无副作用**：不联网、不连 DB、不读系统时钟（所有日期由调用方注入）、不写文件（配置在构建期冻结为不可变对象）。
2. **不可变**：加载后产出 `FrozenRuleSet`，字段全 `frozen=True`，任何写操作抛异常。
3. **可哈希**：整份配置计算 `config_hash = sha256(canonical_json)`，写入 `rule_version_registry.config_hash` 与每个 `dataset_version`，用于重放对账。
4. **Fail fast**：schema 校验失败或语义校验失败 → 进程拒绝启动，**不做任何降级**（规则降级 = 悄悄换口径，比不可用危险得多）。
5. **单一出口**：计算层、公告层、业务服务、规则说明页、模拟卡全部通过 `selectors.py` 取口径；`grep` 验收：`server/` 下除 `rules/configs/` 外不得出现裸阈值数字。

```python
    # 语义校验（schema 表达不了的交叉约束）

    _assert(all board 的 severe_30d.up >= severe_10d.up)            # 30 日阈值不应低于 10 日

    _assert(board_index_map 对 (board, exchange) 在任意业务日上至多一条有效)   # 无重叠区间
    _assert(missing_reason_registry 的 code 无重复且含 'UNKNOWN')
    _assert(next_day_definition.mode in KNOWN_MODES)
    ...
```

**回滚**：配置即代码（Git 管理 + CI 校验）。回滚 = 把上一版 YAML 重新发布 → `registry` 检测到 `config_hash` 变化且 `supersedes` 链回退 → 触发 `requires_replay=true` 的全量重放 → 生成新 `dataset_version`（**不改写已发布的版本**，PRD §10 第 228 行）。

### 4.5 官方明文 vs 产品推断的标注与下发

- 每个可配置叶子节点带 `basis` 字段（`official` / `product_inference`）；
- `meta.basis_summary` 聚合两份清单，随 `/api/rules/current` 下发；
- 规则说明页按 `basis` 分两栏渲染，推断项必须带「产品口径，非交易所原文」标注（PRD §4 第 74 行）；
- 接口里任何由推断口径产生的结论，其 `evidence` 必须带 `basis: product_inference`，便于前端加脚注。

### 4.6 规则版本升级 → 重算 → 灰度（对应 PRD §4.5）

**升级六步：**

1. **新增版本** `rollout_phase='shadow'`，`supersedes` 指向旧版；
2. **影子重放**：用新版本对最近 30 个业务日全量重算，结果写入 `replay_run`，**不发布**；
3. **对账**：`diff_summary_json` 输出逐股票逐规则的差异清单（新增触发/消失触发/数值变化），人工复核；差异率超阈值（建议 `>0.5%` 股票数）则打回；
4. **灰度**：`rollout_phase='canary'`，按 `ts_code` 哈希取 `canary_ratio` 的股票用新版本，其余用旧版本；**同一 `dataset_version` 内允许两个 `rule_version` 共存**，但每条 `metric_result` 必须带自己的 `rule_version`，且灰度开关写进 `dataset_version.validation_json`；
5. **全量**：`rollout_phase='full'`，全部股票切新版本，生成新 `dataset_version`；
6. **归档**：旧版本 `rollout_phase='retired'`，`effective_to` 填切换日；保留配置与 `config_hash` 供重放。

### 5.2 算法 ①：共同有效交易日对齐 + 区间偏离

```
function align_common_sessions(stock_closes, index_closes, trading_days, resets):
    # 1. 基准：只保留「股票有收盘价」且「指数同日有点位」的日期
    common = [d for d in trading_days if d in stock_close_map and d in index_close_map]
    # 2. 重置切段：从最近一次生效的 severe reset 起（severity 覆盖全部指标）
    #    ordinary reset 只切 3 日窗口，10/30 日不受影响（PRD §4.4 表）
    seg_start = max(effective_severe_reset_date, default = common[0])
    common = [d for d in common if d >= seg_start]
    # 3. 停牌不补日：不加任何虚拟点，不把停牌日当 0 收益（PRD §4.1 第 78 行）
    return common

function deviation(closes_stock, closes_index, common, window_n):
    # N 日窗口需要 N+1 个收盘点（engine.calculate_deviation 的既有口径，保留）
    if len(common) < window_n + 1:
        return UNAVAILABLE(HISTORY_INSUFFICIENT, actual=len(common), required=window_n+1)
    dates = common[-(window_n + 1):]                 # 以最新共同交易日为终点
    r_stock = compound(close_ratio(dates))           # 复合，非算术和
    r_index = compound(index_ratio(dates))
    return DeviationResult(deviation = r_stock - r_index, start=dates[0], end=dates[-1])
```

**复权取舍（需拍板 §⑪-5，默认建议）：** 主存未复权收盘价 + `adj_factor`，计算时对**窗口内部**的除权日做因子归一化（即窗口内收益用 `close_t * adj_t / close_{t-1} / adj_{t-1}`），保证区间收益连续；对外展示的 `triggerPrice` 用**未复权**价格，避免给用户一个"理论价"但实际盘面对不上。理由：监管口径以实际收盘价为准（`core/models.py:54` 注释同），且宋文 P1-3 已论证前复权落库会破坏可重放。

**停牌：** 停牌日不产生收益点（不补 0、不插值）。复牌首个有效收益日的比较基点是**停牌前最后一个有效收盘价**与**同日指数点位**（PRD §4.4 第 120 行）；复牌日跳空收益进入新窗口。复牌后 3/10/30 个有效共同交易日未凑齐 → 对应窗口 `HISTORY_INSUFFICIENT`，**不显示 0%**。

### 5.3 算法 ②：次日「可能触发」判定（★ 核心决策点）

**问题陈述：** N 日的股票收益未知，指数收益也未知。"可能触发"必须有确定定义，否则同一天两人算出两个结论。

**推荐方案 A：反解容忍涨幅（reverse-solve tolerance）** —— 与现网 `TriggerPrice`（`engine.py:167-192`）同源，可复用，且语义最贴合 PRD §7「计算候选」。

```
function next_day_assessment(common, window_n, target_up, target_down, rule, direction):
    # 0. 前置：日历可用 + N 存在 + 交易状态非 unknown
    if not calendar_available or next_date == "":
        return UNAVAILABLE(CALENDAR_MISSING)
    if trading_state == 'unknown':
        return UNAVAILABLE(TRADING_STATE_UNKNOWN)

    # 1. 构造 N 日窗口：把 D 收盘序列向后推一个虚拟交易日 N
    #    N 的指数涨跌幅按配置假设（默认 neutral_zero）
    idx_assumption = rule.next_day_definition.index_return_assumption   # 默认 0.0
    # 2. 反解：求使「N 日窗口偏离首次达到阈值」所需的股票 N 日涨跌幅 r*
    #    deviation(N) = (R_stock_D * (1+r*) - 1) - (R_index_D * (1+idx) - 1)  [复合口径]
    #    令 deviation(N) = target_up  →  解出 r*_up
    r_star_up   = solve_required_stock_return(common, window_n, target_up,   idx_assumption)
    r_star_down = solve_required_stock_return(common, window_n, target_down, idx_assumption)
    # 3. 可达性：单日涨跌幅受涨跌停板约束（ST/新股/退市整理另有比例，见 §⑪-6/7）
    limit = rule.boards[board].limit_price_ratio
    if 0 <= r_star_up <= limit:
        status_up = 'possible'
    elif r_star_up < 0:
        status_up = 'triggered'        # 当前已超阈值（理论上 D 已触发，不应出现在 N）
    else:
        status_up = 'safe'             # 一日之内到不了
    # 4. 输出
    return NextDayResult(
        status = status_up,
        triggerPrice = base_price * (1 + (idx_assumption + target_up)/100),
        tolerancePct = r_star_up,
        limitRatio   = limit,
        assumption   = { indexReturn: idx_assumption, basis: 'neutral_zero' },
    )
```

**与现网的关系：**
- `engine.TriggerPrice`（`:86-95`）已经算了 `trigger_price` 与 `remaining_percent`，但**不输出指数假设**，导致不可解释，且 `remaining_percent` 是"距触发价的百分比"而非"所需单日涨跌幅"——两者在复合口径下不等价。vNext 保留 `TriggerPrice` 结构体，补 `assumption` 字段并把主判定量换成 `tolerancePct`。
- `engine.PredictionPoint`（`:98-106`）是 T+1..T+N 序列，vNext 只需要 `offset=1`；保留 `predict_trigger_prices` 供模拟卡复用，但**次日判定只取第一点**。
- 现网 `_next_day_rule_candidates`（`market_service.py:1608-1720`）本质就是方案 A（反解 + `0 <= distance <= limit`），但缺 `assumption` 输出、且 10 日同向分支（`:1681-1719`）用的是"假设涨跌停 + 检查是否产生新候选事件"的另一套逻辑。vNext 统一走 `next_day.py`，**删除 `_next_day_rule_candidates` 与预测列表里的重复实现**（B-13）。

**备选方案（不推荐，列出供拍板）：**

| 方案 | 定义 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **A 反解容忍涨幅**（推荐） | 解出所需单日涨跌幅，与涨跌停比较 | 有明确阈值、可解释、可给出触发价、与现网同源 | 依赖指数假设；"可能"其实是"一日之内可达" |
| B 区间扫描 | 枚举 r ∈ [-limit, +limit]，任一 r 使偏离达阈值即 possible | 不依赖点估计 | 几乎等价 A（单调性下必然等价），实现更复杂 |
| C 历史波动分位 | 用近 60 日波动分布估计 P(触发) > x% | 更"概率化" | 引入统计模型，不可重放（依赖模型版本）、易被理解为荐股，**违反 PRD §1 不提供收益承诺** |

**10 日同向的次日判定（推荐）：** `count(direction) + 1 >= threshold` **且** 存在一个未匹配的 3 日计算候选，其窗口 `end_date == N` 且方向相同 → `possible`。理由：PRD §7 第 181 行「次日『可能触发』是计算候选，不增加正式 10 日同向次数或生成监管事实」——次日能否 +1 取决于是否会产生新的"计算候选"，而正式计次仍需公告确认。

### 5.4 算法 ③：10 日同向计次与窗口滚动

```
function count_same_direction(facts, unresolved, market_candidates, common, as_of, rule):
    window_n   = rule.boards[board].thresholds.same_direction_10d.count_window  # 10
    win_start  = trading_day_at_index(index_of(as_of) - window_n + 1)  # 最近 10 个交易日
    events = []
    for fact in facts:
        # ★ 唯一入窗日：fact.fact_end_date（PRD §4.3 第 107 行）
        if not (win_start <= fact.fact_end_date <= as_of):
            continue
        # 方向分离：up / down 各自计数，不相抵（PRD §4.2 第 95 行）
        if fact.direction not in ('up','down'):
            # 公告未明确方向时，用对齐的 3 日行情复算判定；算不出 → 待核验
            d = resolve_direction_by_market(fact.fact_end_date, common, rule)
            if d is None:
                mark_unresolved(fact, FACT_UNMATCHED); continue
            fact = fact.with_direction(d, source='market-calculation')
        # 收盘复算必须达到该板块 3 日普通阈值且方向一致（PRD §4.3 第 102 行）
        if not market_match(fact, market_candidates, rule):
            mark_unresolved(fact, FACT_UNMATCHED); continue
        # ★ 一事实一事件：fact_id 唯一（重叠事实分别计次，验收 #1）
        # ★ 跨源幂等：fact_key 相同的事实只算一次，多一条证据不多一次（验收 #11）
        events.append(SameDirectionEvent(fact_id=fact.fact_id,
                                         fact_key=fact.fact_key,
                                         fact_end_date=fact.fact_end_date,
                                         direction=fact.direction,
                                         counted=True))
    # 滑出：fact_end_date 落到窗口之前的事件自然不计入；历史行保留不删
    up   = count(events, 'up')
    down = count(events, 'down')
    # ★ 待核验事实不计数，但必须把状态抬成 unavailable（PRD §4.3 第 105 行：不能当 0 次）
    if unresolved:
        availability = 'unavailable'; reason = worst_reason(unresolved)
    return SameDirectionResult(up=up, down=down, availability=..., missing_reason_code=reason,
                              counted_events=events)
```

**关键不变量（进属性测试，见 §⑨-4）：**
- `I1 幂等`：同一 `fact_key` 写入 N 次，`up`/`down` 不变；
- `I2 单调（非负）`：随 `as_of` 前进，事件只因滑出而减少，不会因重复采集而增加；
- `I3 重叠独立`：两条 `fact_key` 不同但区间重叠的确认事实 → 计数 +2；
- `I4 方向分离`：`up + down` 可以大于任一方向阈值，但各自独立判触发；
- `I5 不可降级为 0`：`unresolved` 非空 → `availability='unavailable'`，**绝不返回 0 次**。

### 5.5 算法 ④：重置边界

```
function resolve_reset_boundaries(facts, suspensions, trading_days, rule):
    boundaries = []
    for f in facts where f.fact_type in RESET_FACT_TYPES:
        policy = rule.reset[f.reset_kind]                 # ordinary/severe/risk_warning
        if policy.scope == 'none': continue               # 一般风险提示不重置（PRD §4.4）
        eff = next_trading_day(f.disclosure_date)         # 公告次一交易日
        boundaries.append(ResetBoundary(scope=policy.scope, effective_date=eff,
                                        reset_metrics=policy.reset_metrics,
                                        preserve_metrics=policy.preserve_metrics,
                                        trigger_fact_id=f.fact_id,
                                        confidence_state='confirmed'))
    for s in suspensions:
        # ★ 停牌原因必须由正式来源分类，不得按时间相邻推断（PRD §4.4 第 120 行）
        if s.reason_class == 'severe_related':
            kind = 'suspension_severe'
        elif s.reason_class == 'ordinary':
            kind = 'suspension_ordinary'
        else:  # unconfirmed
            # ★ 保留事件账本，标待核验，不猜测清零也不猜测延续（验收 #12）
            boundaries.append(ResetBoundary(scope='unknown', effective_date=s.resume_date,
                                            confidence_state='pending_verification',
                                            missing_reason_code='RESET_BOUNDARY_UNKNOWN'))
            continue
        eff = s.resume_date                               # 复牌交易日建立新窗口
        boundaries.append(ResetBoundary(scope=kind, effective_date=eff, ...))
    # 冲突：同一 effective_date 同时存在 severe 与 ordinary → severe 覆盖（PRD §3.2 严重优先）
    return merge_with_precedence(boundaries, order=['severe','suspension_severe','ordinary','suspension_ordinary'])
```

**两类停牌的差异（PRD §4.4 第 117-118 行）：**
- 普通事项停牌复牌：`reset_metrics=[3/10/30 偏离]`，`preserve_metrics=[same_direction_10d]` → **同向事件延续，按 `fact_end_date` 滚动**；
- 严重异动相关停牌复牌：`reset_metrics=[四项全量]`，`preserve_metrics=[]` → **同向事件一并清零**。

### 5.6 算法 ⑤：缺因的产生与传播（保证不降级为安全）

**产生点（唯一）：** 计算链上任何一步拿不到必需输入 → 构造 `Unavailable(code, scope, detail)`，**不再继续用默认值计算**。禁止 `except: return 0 / None / False` 后继续（B-P2-5）。

**传播规则：**

1. **逐项独立**：`metric_result` 一行 = (股票 × 规则 × 日期角色 × 方向)。单项缺依赖只让该行 `unavailable`，**其他行照常算出**（PRD §3.5 第 69 行「一个严重项不得屏蔽其他项」、验收 #10）。
2. **聚合取最严重**：`nextDayConclusion` / `regulatoryBanner` / `regulatory.state` 聚合四项时，若任一项 `unavailable` → 聚合结果 `unavailable`（`undetermined`），**不回退 `safe`**（PRD §3.2 第 49 行、夏文 §0.6 的 `undetermined`）。
3. **优先级**：同一行多个缺因时按 `severity`（block > warn > info）取最高，其次按固定顺序（下表）。
4. **门禁**：`severity='block'` 的缺因在发布门禁里计数，超阈值阻断发布（§⑦-3）。

**缺因 → 产生位置映射表：**

| `EXCLUDED_BY_POLICY` | 业务服务（预测筛选） | 预测页 | info |
| `UNKNOWN` | 兜底 | 通用 | block |

## ⑥ 公告模块设计

### 6.1 职责边界（ARCH §4.4）

公告模块**只输出**：原始材料引用（URL/来源/披露日）、正文证据（文本/哈希/读取方法与置信度）、结构化事实（类型/区间/方向/监管期限/停复牌分类）、匹配所需字段（`fact_key`/`fact_end_date`/`direction`/`fact_type`）。
公告模块**不做**：写最终次数、写监管标签、写预测名单、直接执行重置。

### 6.2 采集

```
server/announcements/
├── sources/
│   ├── cninfo.py      # 巨潮：主源，按栏目(sse/szse/bse) × 关键词
│   ├── exchange.py    # 交易所官网：补充/校验
│   ├── issuer.py      # 发行人官方页面：补充/校验
│   └── broker.py      # 18.cn / 中泰：风险提示类，仅作监管事实展示，不触发重置
├── runner.py          # 批次编排：run_id、分页、覆盖边界、速率、重试
├── parse/
│   ├── body_reader.py # PDF 文本层 → OCR 回退
│   ├── extract.py     # 正文 → 结构化事实
│   └── classify.py    # 事实类型 / 停牌原因分类
├── identity.py        # fact_key / source_id 生成
├── dedup.py           # 跨源幂等
├── correction.py      # 更正 / 撤回
├── storage.py         # COS PDF 生命周期
└── tests/
```

**采集批次契约：** 每次采集生成一个 `announcement_source_run`：

```jsonc
{
  "run_id": "ANN-20261027-01",
  "window": { "start": "20261020", "end": "20261027" },
  "sources": [
    { "code": "cninfo", "role": "primary", "coverage": ["ordinary","severe","risk_warning","suspension","delisting"],
      "status": "completed", "requests": 96, "items": 55, "failed_keywords": [] },
    { "code": "exchange", "role": "supplement", "status": "partial", "failed": ["szse"] }
  ],
  "batch_complete": false,          // ★ 任一首源未完成 → false
  "coverage_boundary_note": "巨潮按栏目+关键词采集，不宣称全量覆盖"
}
```

**★ 硬规则（PRD §6 第 170 行、验收 #11）：** `batch_complete == false` 时，窗口内"未找到匹配公告"**只能**记为 `ANNOUNCEMENT_BATCH_INCOMPLETE` 待核验；只有 `batch_complete == true` 且覆盖校验通过，才能确认"当日没有已确认普通事件"并保持次数不增加。

**速率与重试：**

| 项 | 策略 |
| --- | --- |
| 列表请求 | 源级令牌桶（巨潮 ≤ 2 QPS、18.cn ≤ 1 QPS、中泰 ≤ 1 QPS），超限排队不丢弃 |
| 正文下载 | 独立线程池 8 并发，单 URL 超时 12s，失败进重试队列（指数退避 1s/4s/16s，最多 3 次） |
| OCR | 独立队列（CPU 密集），与下载解耦；OCR 命中率目标 < 5%（多数 PDF 有文本层） |
| 失败分类 | `fetch_failed`（源不可用）/ `not_found`（查无此公告）/ `body_unreadable`（正文不可读）/ `no_fact`（无匹配事实）——**四者绝不等价** |
| 死信 | 3 次重试仍失败 → `announcement_dead_letter`，告警 + 每日补采 |

### 6.3 解析：正文字段契约

### 6.4 去重与多源幂等

```
function ingest(announcement):
    ev   = build_evidence(announcement)          # 源级身份
    src_id = sha1(f"{ev.source_code}|{ev.source_ann_id}")
    for raw_fact in extract_facts(announcement.body, parse_version):
        if not raw_fact.has_identity():
            unresolved.append({..., confidence_state='identity_missing'}); continue
        fact_key = sha1(f"{ts_code}|{fact_type}|{start}|{end}|{direction}")
        # ★ 单公告多事实：不同 fact_key 各自成行（验收 #1）
        # ★ 多源转载：同一 fact_key 只 upsert 证据，不新增事实行（验收 #11）
        upsert(regulatory_fact, key=fact_key, on_duplicate=merge_evidence)
        upsert(fact_evidence,   key=src_id,    on_duplicate=update)
```

**跨源冲突处理：** 同一 `fact_key` 下不同来源给出的 `direction` 或区间不一致 → `confidence_state='source_conflict'`，保留双方证据，该事实**不计次**，并抬 `PENDING_VERIFICATION`。优先级：交易所官网 > 巨潮 > 发行人 > 券商转载（仅展示）。

### 6.5 更正与撤回

```sql
CREATE TABLE fact_correction (
  correction_id     BIGINT NOT NULL AUTO_INCREMENT,
  fact_key          CHAR(64) CHARACTER SET ascii NOT NULL,
  supersedes_fact_id BIGINT NOT NULL,
  correction_type   ENUM('amend','withdraw') NOT NULL,
  corrected_fact_id BIGINT NULL,
  effective_at      DATETIME(3) NOT NULL,
  source_id         CHAR(64) NOT NULL,
  reason            VARCHAR(255) NOT NULL DEFAULT '',
  PRIMARY KEY (correction_id),
  UNIQUE KEY uk_correction (supersedes_fact_id, correction_type, source_id),
  KEY idx_corr_fact (fact_key)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

- **amend（更正）**：生成新 `fact_id`（新 `fact_key`，若区间/方向变了），原事实 `counted=0` 并保留证据；**不覆盖原始证据**（PRD §6 第 172 行）。
- **withdraw（撤回）**：`same_direction_event.counted=0`，`is_active=0`；若该撤回使某股票跌破严重阈值 → **触发该股票重算 + 新 `dataset_version`**。
- 更正/撤回都必须触发受影响股票的重算，且新数据集保留"因更正而降级"的审计记录（`audit_log.action='fact_correction_rebuild'`）。

### 6.6 覆盖边界声明

`source_coverage_boundary` 表显式声明每个源覆盖哪些公告类型/板块/交易所，以及是否宣称全量：

| source_code | 覆盖类型 | 板块 | 全量声明 |
| --- | --- | --- | --- |
| `cninfo` | ordinary / severe / risk_warning / suspension / delisting | SSE/SZSE/BSE | **否**（按栏目 + 关键词） |
| `exchange` | severe / suspension / delisting | 对应本所 | 否（官网栏目） |
| `issuer` | 本发行人全部 | — | 否 |
| `broker` | risk_warning | — | 否（滚动列表） |

PRD §6 第 170 行「不能宣称全量覆盖」——接口必须在 `regulatory.evidence` 与 `dataset` 层带回 `coverageNote`，前端不得显示"已核查全部公告"。

### 6.7 PDF 生命周期

```
[下载成功] → 校验 %PDF 魔数 → 计算 sha256 → 上传 COS → 写 announcement_pdf_object
                                                            (object_key, sha256, size, fetched_at, url)
     ↓
[解析] 文本层 → OCR 回退 → 写 announcement_body(text, method, confidence, pages, error)
     ↓
[有效期内] 监管事实有效期未结束 → pdfAvailable=true → 页面可打开（后端代理 /api/announcements/{id}/file）
     ↓
[期满] 监管期结束 + 无审计保全要求 → 清理 COS 二进制 → 写 pdf_cleanup_log
     ↓
[清理后] pdfAvailable=false, pdfCleanedNote="附件已按保留策略清理，请查看来源原文"
        → 页面优先跳来源 URL；来源不可用 → 明确提示，不显示损坏链接（PRD §6 第 168 行、验收 #13）
```

清理任务每日一次，只清理 `regulatory_end < today - retention_days(默认 30)` 且 `preservation_required=false` 的对象；每次清理写 `pdf_cleanup_log(object_key, sha256, cleaned_at, reason)`。

### 6.8 解析质量度量（进 `quality_check_result`）

| 指标 | 定义 | 目标 | 门禁 |
| --- | --- | --- | --- |
| `body_readable_rate` | 正文可读公告数 / 命中公告数 | ≥ 95% | < 90% → block |
| `fact_extraction_rate` | 抽到结构化事实数 / 正文可读数 | ≥ 90% | < 80% → warn |
| `identity_complete_rate` | 能生成 `fact_key` 的事实 / 全部事实 | ≥ 98% | < 95% → warn |
| `match_rate` | 与计算候选匹配成功的事实 / 可匹配事实 | ≥ 85% | < 70% → warn |
| `pending_rate` | `unresolved` 事实 / 全部事实 | ≤ 5% | > 15% → block |
| `identity_missing_count` | 生产数据集里 `identity_missing` 且计入计数的事实数 | **必须 = 0** | ≠ 0 → block（回执第 31 行） |
| `batch_complete` | 首源采集批次是否完成 | true | false → 该窗口"未找到"只能待核验 |

## ⑦ 业务服务编排与 API 设计

### 7.1 后台更新/发布：详细时序

```
阶段 0  领取租约（防止多实例并发重算）
  UPDATE task_lease SET owner=?, generation=generation+1,
         lease_until=NOW(3)+900s WHERE job_name='daily_rebuild' AND lease_until < NOW(3);
  affected_rows == 0 → 放弃本次执行（已有实例在做）
  心跳：每 60s 续租；租约过期未续 → 其他实例可抢占

阶段 1  冻结输入 & 建候选版本（不可见）
  1.1 确定 business_date D：日历可用 ? D : 中止（★ 绝不退化工作日，B-5）
  1.2 INSERT dataset_version(..., status='building')  ← 对外完全不可见
  1.3 增量拉取并落库（每条按 1000 行/事务，单行事务目标 < 300ms）：
      trade_calendar → suspension → security/stock_basic
      → daily_bar（★ 按交易日批量，禁止逐股）→ index_daily_bar
  1.4 数据对齐校验：股票 as_of == 指数 as_of == D；否则记 quality_check_result

阶段 2  公告采集与解析（可独立失败、可重试、可补采）
  2.1 起 announcement_source_run（run_id 固定，幂等）
  2.2 按源采集列表 → 下载正文 → 解析事实 → 生成 fact_key/source_id
  2.3 upsert regulatory_fact / fact_evidence / fact_correction
  2.4 写 source_coverage：batch_complete / 各源状态 / 覆盖边界
  ★ 源失败不视为"无事实"：抬 ANNOUNCEMENT_FETCH_FAILED，批次标 incomplete

阶段 3  规则解析
  3.1 按 business_date 从 rule_version_registry 选生效 rule_version（含灰度分流）
  3.2 加载 FrozenRuleSet（进程内缓存，key=config_hash）

阶段 4  计算（★ 业务服务只编排，不实现算法）
  4.1 逐股票构造 CalcInput（分片并行，见 §⑧）
  4.2 调 calculations.engine.compute(CalcInput, RuleSet) → 行情候选 + 缺因
  4.3 把候选与公告事实交给 engine 做确定性匹配 → 正式计次
  4.4 应用重置边界 → 四项 current / next 结果

阶段 5  落库（幂等）
  5.1 reset_boundary（uk: ts_code+scope+effective_date+trigger_fact_id）
  5.2 same_direction_event（uk: fact_id）
  5.3 metric_result（uk: dataset_version+ts_code+rule_key+date_role+direction）
  全程 ON DUPLICATE KEY UPDATE；不触碰 dataset_pointer

阶段 6  质量门禁 → 原子发布（单事务，目标 < 50ms）
  START TRANSACTION;
    INSERT quality_check_result ... ;
    SELECT COUNT(*) FROM quality_check_result
      WHERE dataset_version=? AND severity='block' AND passed=0;   -- 必须 = 0
    SELECT published_version FROM dataset_pointer WHERE id=1 FOR UPDATE;
    UPDATE dataset_version SET status='archived' WHERE status='published' AND dataset_version<>?;
    UPDATE dataset_pointer SET published_version=?, published_at=NOW(3) WHERE id=1;
    UPDATE dataset_version SET status='published', published_at=NOW(3) WHERE dataset_version=?;
  COMMIT;
```

**失败与回退：**

| 失败点 | 处理 |
| --- | --- |
| 阶段 0 抢不到租约 | 直接返回，不写任何东西 |
| 阶段 1 日历不可用 | `status='failed'`，`dataset_pointer` 不变；告警 `CALENDAR_MISSING`；**不发布** |
| 阶段 2 公告源全失败 | 继续构建（监管事实可来自上一版已确认事实），但 `batch_complete=false` → 同向项抬 `ANNOUNCEMENT_BATCH_INCOMPLETE`；若门禁判定影响面过大则阻断 |
| 阶段 4 计算异常 | 该股票标 `unavailable`，**不中断整批**；失败数超阈值 → 阻断 |
| 阶段 5 写库失败 | 重试 3 次；仍失败 → `status='failed'`，指针不变，下次重跑靠唯一键收敛 |
| 阶段 6 门禁不通过 | `status='validated'` 不发布；保留明细供排障与补采后重投 |
| 任何时刻 | 对外始终提供上一 `published` 版本 + `dataset.state='failed_keep_previous'` + `staleReasonCode`（PRD §9.3 第 224 行） |

**回滚：** 发布后若发现错误 → 把 `dataset_pointer.published_version` 改回 `previous_version`（单事务，< 50ms），新版本置 `rolled_back`；**明细不删**，供复盘。

### 7.2 查询流程（三页同版本）

```
请求进入
  → 生成/透传 traceId
  → 读 dataset_pointer（本地 5s 缓存 / Redis 30s）→ V
  → 校验 V：quote_cutoff_date < 当前业务日 → freshness='stale' + DATASET_STALE（不返回数值伪装安全）
  → 本次请求内所有查询强制 WHERE dataset_version = V
  → 单股：读 metric_result(16 行) + regulatory_fact + reset_boundary
     监控：读 regulatory_fact（按 target_date 过滤有效期；未来事实不提前、已失效不进入）
     预测：读 metric_result WHERE date_role=? AND status IN (triggered, possible)  ← 纯筛选，不改底层结果
  → 若 session.intradayEligible：叠加盘中覆盖层（quoteLayer.persisted=false，不落库）
  → 组装 dataset/dateRole/session 三段公共头，返回
```

**★ 三页同版本的机器保证：**
1. 请求上下文对象 `RequestContext(dataset_version=V, rule_version=R, business_date=D)`，单股 → 预测 → 监控跨接口透传同一个 `V`；
2. 所有响应外层强制带 `dataset`，由统一响应中间件注入，业务代码不可覆盖；
3. CI 断言：三页在同一时刻的响应 `dataset.version` 必须相等（§⑨-5）。

## ⑧ 性能方案与量化目标

### 8.1 全市场重算（目标 P95 < 8 分钟）

**现网瓶颈：** 逐股循环调 Tushare（B-12）、30 点收益向量反复 JSON 序列化、单线程。

**改造方案：**

| 步骤 | 现网 | vNext | 收益 |
| --- | --- | --- | --- |
| 日线拉取 | 混合 `daily(ts_code=)` 逐股 + `daily(trade_date=)` 批量 | **一律 `daily(trade_date=)` 批量**，增量日每日 1 次；新上市股票用批量日线补齐 | 5500 次 → 1~3 次/日 |
| 指数日线 | 逐指数 `index_daily`（5 个） | 保持 5 次/日（可接受） | — |
| 内存布局 | dict of dict，反复 `float()` | 一次性转 `numpy` 数组（或纯 Python 双数组 + 预计算前缀积） | 30~50× |
| 并行 | 单线程 + 2 线程池 | 按 `ts_code` 哈希分 8 片，`ProcessPoolExecutor(8)`（CPU 密集：复合收益 + 窗口扫描） | ~6× |
| 窗口计算 | 每股票独立算 3/10/30 | 前缀积一次算出，窗口偏离 O(1) 查询 | O(N·W) → O(N) |
| 写库 | 逐条 upsert | 1000 行/批，`ON DUPLICATE KEY UPDATE`，按 `ts_code` 排序避免跨分区随机 IO | ~10× |

**耗时预算（P95）：**

| 阶段 | 预算 | 说明 |
| --- | --- | --- |
| 抢租约 + 建版本 | 5 s | 单 SQL |
| 日历/停复牌增量 | 20 s | 2~3 次上游调用 |
| 日线批量拉取 + 落库 | 90 s | 1~3 次请求 + 5500 行 upsert（1 MB） |
| 指数日线 | 20 s | 5 次请求 |
| 公告采集与解析（并行，非阻塞主链） | 180 s | 列表 ~96 次 + 正文 ~55 篇；超时降级为待核验，不阻断 |
| 计算（8 进程 × 5500 股） | 180 s | 每股 < 5 ms（窗口扫描 30 次 O(1) 查询） |
| 事实匹配 + 重置 | 40 s | 按股票分组，事实量小 |
| 落库（metric_result ~88K 行） | 60 s | 88 批 × 1000 行 |
| 质量门禁 | 30 s | ~18 条聚合 SQL |
| 原子发布 | < 1 s | 单事务 |
| **合计 P95** | **≈ 625 s ≈ 10.4 min** | ⚠ 略超 8 分钟目标 |

**为达到 < 8 分钟，追加两项优化：**
1. **增量计算**：非重置日只重算「当日有新收益点」的股票（全部 5500 只都有新点，但 3/10/30 窗口只需滑动一步）→ 用增量窗口（去掉最旧一日收益、加最新一日）替代全量重算，计算阶段 180 s → 40 s；
2. **公告采集与主链解耦**：公告采集独立任务（提前 30 分钟启动），主链只读取已入库事实 → 主链去掉 180 s。

优化后 P95 ≈ **625 - 140 - 180 ≈ 305 s ≈ 5.1 min**，留 60% 余量。

### 9.4 属性测试（Property-based，用 Hypothesis）

| 不变量 | 性质 |
| --- | --- |
| **I1 幂等** | 同一 `fact_key` 写入 N 次 → `up`/`down` 计数不变 |
| **I2 单调** | `as_of` 单步前进，事件数只因滑出而减少或不变；重复采集不增加 |
| **I3 重叠独立** | 两条 `fact_key` 不同、区间重叠的确认事实 → 计数 +2 |
| **I4 方向分离** | `up` 与 `down` 独立计数、独立判触发，互不相抵 |
| **I5 不可降级** | 输入含 `unresolved` → 结果 `availability='unavailable'` 且 `status != 'safe'`（**永不出现 safe**） |
| **I6 对齐对称** | 交换股票/指数输入顺序不改变偏离绝对值符号约定 |
| **I7 窗口边界** | 恰好等于阈值 → `triggered`（`>=` 比较，容差 1e-9）；阈值 ±0.005% 的样本必须覆盖 |
| **I8 日历不降级** | 日历不可用时**任何**路径都不得返回数值 |
| **I9 日期角色单调** | `retainUntil` 单调不回退；`switchAt` 严格递增 |
| **I10 三页一致** | 同一 `dataset_version` 下，单股与预测的共同规则结果（数值/方向/阈值/日期/触发态）必须相等 |

### 9.5 与 `server/tools/api_contract_check.py` 的衔接

```python
    sim = detail["data"]["simulation"]
    assert sim["ruleVersion"] == detail["data"]["dataset"]["ruleVersion"]

    # 8) 盘中不落库：GET 不得返回 intraday
    assert stable_get["data"]["quoteLayer"]["kind"] == "close"

    # 9) 交易时间内不开放次日（结构化字段，非字符串比较）
    if predictions["data"]["nextDay"]["open"] is False:
        assert predictions["data"]["nextDay"]["display"]["style"] == "center_two_line"
```

## ⑪ 待拍板口径（PRD 未定义，工程必须决策）

> 每项给「建议决策 + 理由 + 需拍板标记」。**标记 🔴 的项阻塞 M1，必须最先定。**

### 🔴 11-1 次日「可能触发」的数学口径
- **建议：** 方案 A「反解容忍涨幅」——假设指数次日涨跌幅为 0，解出使窗口偏离首次达到阈值所需的股票单日涨跌幅 `r*`；`0 ≤ r* ≤ 涨跌停比例` → `possible`；输出 `tolerancePct`、`triggerPrice`、`assumption.indexReturn`。
- **理由：** 与现网 `TriggerPrice` 同源、可解释、可给出触发价、不引入统计模型（避免"收益承诺"合规风险）、可重放。
- **需拍板：** ① 是否接受"可能 = 一日之内可达"这一语义（而非概率）；② 指数次日假设固定 0，还是用近 20 日均值/昨值（建议固定 0，理由：可重放、不预测市场）；③ `same_direction_10d` 的次日口径是否采用「count+1 ≥ 阈值 且 存在 `end_date == N` 的未匹配计算候选」。

### 🔴 11-2 10 日同向是否进入异动预测池
- **现状冲突：** PRD §7 第 176 行要求入池；`market_service.py:266-271` 整体排除。
- **建议：** **入池**，但卡片形态改为「次数式」而非「距离式」：显示 `已确认 N 次 / 阈值 M 次` + `次日可能 +1 的条件`，不显示"距阈值还有 X%"。排除政策写进 `rules.prediction_policy.include_same_direction_10d`。
- **理由：** PRD §7 明确列出三项严重规则；排除会让预测页缺失一个严重维度，且与验收 #4 的可对账性相悖。次数式卡片规避了"距离式预测卡没有连续阈值距离"的实现难题。
- **备选：** 若产品坚持排除，必须在 PRD §7 删除「10 日同向」并写明原因，同步更新验收标准，并在接口 `excluded[]` 返回 `EXCLUDED_BY_POLICY`。

### 🔴 11-3 重叠窗口计次：per_fact 还是 episode
- **建议：** `per_fact`（不同 `fact_id` 的事实分别计次）。
- **理由：** PRD §11 验收 #1 明文「重叠公告事实可分别计次」；`engine.py:296-352` 的 episode 合并与之冲突。
- **需拍板：** 确认 PRD 优先于现网实现；若产品确实要 episode 口径，须另立 `rule_version` 并标 `basis: product_inference`，新旧各占一版本对账。

### 11-4 板块/基准指数变更的生效日
- **建议：** 以**公告/交易所正式变更生效日**为界；变更前用旧板块旧指数，变更后用新板块新指数，历史数据集不追溯改写。若变更导致阈值变严，不追溯历史触发；若变松，也不撤销已确认事实。
- **理由：** PRD §10「历史版本可重放」与「不允许页面自行推断」；追溯改写会破坏已发布数据集的可审计性。
- **需拍板：** 确认"不追溯"；以及板块归属存在冲突来源时的优先级（建议：交易所公告 > Tushare `stock_basic` > 代码前缀，**代码前缀仅作兜底且必须标记 `SECURITY_IDENTITY_CONFLICT`**）。

### 11-5 除权除息（复权）取舍
- **建议：** 主存未复权收盘价 + `adj_factor`；**窗口内部**对除权日做因子归一化（保证区间收益连续）；对外 `triggerPrice` 用**未复权价**。
- **理由：** 监管口径以实际收盘价为准（`core/models.py:54`）；前复权序列落库会随每起除权事件整体变化，破坏可重放（宋文 P1-3）。
- **需拍板：** 确认"窗口内归一化 + 对外未复权"；以及除权当日是否计入收益（建议计入，用因子还原后的等价收益）。

### 11-6 新股首日
- **建议：** 上市首日**不设涨跌幅限制**（主板/双创/北交所规则不同），`limit_price_ratio` 在首日应取 `null` → 次日可达性判定无法给出 → 该股当日次日结论标 `unavailable`（`TRADING_STATE_UNKNOWN` 或新增 `NEW_LISTING_NO_LIMIT`）；有涨跌幅限制后正常计算。历史不足 31 点时对应窗口标 `HISTORY_INSUFFICIENT`。
- **理由：** 无涨跌停时"一日之内可达"恒成立，判定失去意义；且首日收益分布异常，不应进入异动池。
- **需拍板：** 是否完全排除新股（建议：上市未满 31 个交易日的股票不进预测池，但单股页照常展示并标 `HISTORY_INSUFFICIENT`）。

### 11-7 退市整理期涨跌幅
- **建议：** 退市整理期涨跌幅限制与板块不同（通常 10%），`limit_price_ratio` 由**证券属性 + 交易状态**共同决定，规则模块配置 `boards[x].limit_price_ratio_overrides.delisting_period: 10.0`。
- **理由：** PRD §3.1 第 39 行「退市整理是证券属性/交易事实……在满足条件时单独显示」，不是第五种交易状态，因此用属性覆盖而非新增状态。
- **需拍板：** 各板块退市整理期的具体涨跌幅比例取值（需法务/交易所口径确认）；ST/*ST 的涨跌幅是否同样按覆盖处理（建议：是）。

### 11-8 公告撤回后的计数与重算
- **建议：** 撤回 → `same_direction_event.counted=0, is_active=0`；触发该股票重算并生成**新** `dataset_version`；若因此跌破严重阈值，监管状态降级但保留审计记录；原事实证据**不删除**，保留 `fact_correction` 关联。
- **理由：** PRD §6 第 172 行「事实更正会生成新数据集版本并重算，不覆盖原始证据」。
- **需拍板：** 撤回后是否需要在页面展示"曾被计入后撤回"的历史痕迹（建议：单股页历史可追溯区展示，监控页不展示）。

### 11-9 停牌原因无法确认时的默认
- **建议：** `suspension_reason_class='unconfirmed'` → 保留事件账本、重置判断标 `RESET_BOUNDARY_UNKNOWN` 待核验、受影响项 `unavailable`，**不猜测清零也不猜测延续**。
- **理由：** PRD §4.4 第 120 行与验收 #12 明文要求。
- **需拍板：** 待核验状态的最长保留期限（建议：直到正式来源可确认或该股终止上市；超过 60 个自然日仍未确认则升级告警）。

### 11-10 次日指数涨跌幅假设
- **建议：** 固定 `0.0`（`neutral_zero`），并在接口 `assumption` 字段显式回传。
- **理由：** 可重放；任何非中性假设都是"预测市场"，与 PRD §1「不提供收益承诺」冲突。
- **需拍板：** 确认固定 0；若希望提供"乐观/中性/悲观"三档，需另立口径且每档都要可重放（建议 vNext 不做）。

### 11-11 多源事实冲突（方向/区间不一致）
- **建议：** 优先序 交易所官网 > 巨潮 > 发行人 > 券商转载；仍冲突 → `confidence_state='source_conflict'`，该事实**不计次**，抬 `PENDING_VERIFICATION`，进告警待人工确认。
- **理由：** 冲突时任何一方都可能是错的，猜测计数会直接产出错误监管结论。
- **需拍板：** 确认优先序；以及人工确认的 SLA（建议 T+1 内处理，超时升级）。
