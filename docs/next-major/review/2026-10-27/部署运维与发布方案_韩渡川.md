## ① 总评结论

**总判：vNext 的产品目标（原子发布 `dataset_version`、日终全市场重算 P95 < 8 min、盘中实时覆盖层、09:00/15:00 硬时间切换）本身可达，但现网「单服务 + 进程内调度 + 容器临时盘 + 无迁移 + 零日志」这五件事叠加在一起，会在扩到第二个实例的瞬间自我破坏。部署形态改造不是优化项，而是 vNext 能否成立的前置条件。**

四条第一性原理判断：

**1）定时任务是全局单点，HTTP 服务是无状态可伸缩——把两者塞进同一进程，等于把「可扩展性」和「单点性」绑死。**
现网 `server/app.py:25-30` 是模块级单例，`app.py:402-403` 启动两个后台调度线程（`market-calc` / `official-monitor`）。云托管按负载扩容后，**每个实例都跑一份日终任务**：重复写 `stock_calc_base`、重复打 Tushare、各自维护一份 `/tmp` 上的 SQLite 事实库。1 实例时侥幸正确，2 实例时必然分裂。`market_service.py:208` 的 `_market_update_lock` 只是**进程内**锁，跨实例无效。

**2）「没有回滚就不上线」——现网没有任何一层可回滚。**
DB 无迁移版本（`market_calc_repository.py:194-227` 一串 `ALTER TABLE` 包在 `except Exception: pass`）；镜像无 commit 标识（`/health` 不含构建信息）；发布即全量无灰度；小程序只能回退到上一线上版。而 vNext 把「发布」从"每周一次代码发布"变成"每天一次数据发布 + 每周一次代码发布"，两者的回滚语义完全不同，现网只支持后者。

**3）可观测性为零 → 静默失败是默认行为，而不是异常。**
`server/` 全量 Python 文件对 `logging` / `getLogger` 的引用数为 **0**（仅 15 处 `print`）；`app.py:393-395` 的 `log_message` 直接 `return`，关闭了全部 HTTP 访问日志。叠加调度循环里的 `except Exception: ... 继续`（`market_service.py:2399-2400`、`monitor_service.py:287-288`）与 schema 迁移的静默吞异常，**「任务没跑」「跑了一半」「发布未切换」——vNext 最危险的三种失败模式，现网没有任何一种能被自动发现**。现网唯一的外部信号 `/health.lastErrorActive` 还要求「失败发生在今天」（`app.py:208`），跨天即失效。

**4）成本与配额的真正风险不在存储，而在「耦合放大」。**
存储侧最贵的 PDF 只有 ~6 GB/年（宋砚秋 6.2），清理后 30% 留存 ≈ 1.8 GB/年，完全可控。真正的风险是 `market_service.py:2608` 在逐股循环里调 `client.daily(ts_code=...)`——**5,500 次/日**，而 `tushare_client.py:80-92` 无超时、无重试、无限流。一次失败重试就可能撞穿 Tushare 配额 → 数据集不发布 → P1。改成批量 `daily(trade_date=)` 后请求数从 5,500 降到 ≈7，**下降 99.9%**，这是本方案里投入产出比最高的一项。

**放行建议：** P1 共 8 项。
- **OPS-1（进程/任务拆分 + MySQL 租约）、OPS-2（版本化迁移）、OPS-3（结构化日志 + 健康字段）、OPS-4（CI 门禁）必须在第一个 vNext 数据集发布前完成**——它们决定"发布出去的东西是不是可信的"；
- OPS-5（事实库/PDF 出临时盘）、OPS-6（灰度回滚）、OPS-7（连接池与上游治理）、OPS-8（密钥配置边界）需在灰度放量（G2）前完成。

## ② P1 阻塞问题清单

> P1 定义：不改则 vNext 在生产上不可信——要么发布出去的结果不可回滚，要么失败无法被发现，要么多实例下必然产出错误结论。

### OPS-1 单服务 + 进程内调度，多实例必然分裂

**证据：**
- `server/app.py:25-30` 模块级单例 `SERVICE` / `ANNOUNCEMENTS` / `OFFICIAL_MONITOR`
- `server/app.py:402-403` `SERVICE.start_scheduler()`、`OFFICIAL_MONITOR.start_scheduler()`
- `server/services/market_service.py:286-303` 启动 `market-calc` / `stock-basic-sync` / `prediction-rebuild` 三个 daemon 线程
- `server/services/monitor_service.py:206-213` 启动 `official-monitor` 线程；`:263-289` 循环体内自行判断"今天是否采集过"
- `server/services/market_service.py:208` `self._market_update_lock = Lock()`（`:2534`、`:2737` 使用）——**仅进程内有效**
- `server/services/market_calc_repository.py:126-133` `market_calc_job` 无 `lease_until` / `owner`；仅 `prediction_job` 有（`:177`）

**问题：**
1. 云托管盘中 09:30-15:00 必然扩容到 >1 实例（PRD §5 要求首次打开即刷新实时行情，开盘集中进入）。每实例一份调度器 → 日终任务重复执行、Tushare 调用翻倍、两份不同的 `/tmp` 事实库（OPS-5）。
2. 即使只靠 `prediction_job.lease_until`，它也是**单库行锁**语义，只在"两个实例恰好同时 claim"时串行；而 `market_calc_job` 完全没有这层保护。
3. **云托管定时触发器不是银弹**：触发器是 HTTP 回调，会 LB 到服务下的任一实例。对多实例 API 服务配触发器 = 随机打到一台，仍然要靠租约去重；且触发器只保证"到点叫一次"，不保证成功、不保证串行、**没有补偿记录**。

**建议改法：**
- **API 与 worker 按进程角色拆成两个云托管服务**（同一镜像、不同 `APP_ROLE`）。API 服务完全不启动调度线程；worker 固定 `min=max=1`，跑全部定时任务。这符合 ARCH §7「API 和重任务可按进程角色分开部署，不形成独立微服务」，不拆微服务、不改代码库结构。
- 若短期内不拆服务，也必须引入 `APP_ROLE` 开关 + MySQL 租约（见 §4.3），**API 进程永不执行写任务**。
- 定时触发器只配在 **worker 服务**（单实例）上；同时保留 `job_run` 表 + `catchup_scan()` 做"叫醒失败/漏跑"的兜底与告警。
- 幂等不能只靠租约：租约解决"不并发"，唯一键解决"重复执行结果一致"。所有写必须靠 `uk_fact_key` / `uk_result` / `dataset_version` 唯一键幂等。

### OPS-2 无版本化迁移，schema 变更不可回滚，且滚动发布期 schema 分裂

**证据：**
- `server/services/market_calc_repository.py:75` `ensure_schema()`，`:194-227` 一串 `ALTER TABLE ... ADD COLUMN`，失败由 `:216` / `:227` 的 `except Exception: pass` 静默吞掉
- `server/services/monitor_service.py:99-107` 同类 `PRAGMA table_info` + `ALTER TABLE ADD COLUMN` 模式
- 现网无任何迁移版本号、无历史表、无 `down` 脚本

**问题：**
1. **失败被吞**：某次 `ALTER` 在生产失败 → 后续计算静默缺列 → 结果错误且无人知晓。
2. **启动即迁移**：vNext 要新建 20+ 张表（宋砚秋 §④），靠 `ensure_schema()` 等于把一次性大爆炸 DDL 放在容器启动路径上；失败要么启动失败、要么半套 schema。
3. **滚动发布期 schema 分裂**：新旧实例并存期间，旧代码 + 新 schema（或反之）同时在线，是最容易产生"静默缺列"的窗口。
4. 无版本 → 无法回答"生产现在跑的是哪套 schema"，也无法回滚。

**建议改法：**
- 引入 `schema_migration` 表（见 §6.1），每个迁移一个编号 SQL 文件，带 `up` / `down`、checksum、执行记录。
- **迁移从容器启动路径剥离**：改为独立的 `migrate` 角色（或 worker 启动前置步骤），抢 MySQL 全局命名锁 `SELECT GET_LOCK('sa_schema_migration', 10)` 保证同一时刻只有一个容器跑 DDL；**失败即 fail-fast 退出容器让发布失败，绝不吞异常**。
- 应用代码删除 `ensure_schema()`：应用只读 schema，不建表。
- vNext 期间所有 DDL 必须**向前兼容两阶段**（加列 → 双写 → 切读 → 删旧列），保证旧实例在新 schema 上仍可读可写，这是"回滚不需要回滚 DDL"的前提。
- CI 增加两条硬门禁（见 §5.2）：空库一键重建 + `--down 1 --up 1` 可执行。

### OPS-3 可观测性为零：无日志、无 traceId、健康检查不可信

**证据：**
- `server/` 全量 Python：`grep -rn "logging\|getLogger"` = **0 处**；`print(` 15 处
- `server/app.py:393-395` `log_message()` 直接 `return`，HTTP 访问日志全部关闭
- `server/services/market_service.py:2399-2400` 调度循环 `try/except Exception: 继续`
- `server/services/monitor_service.py:287-288` 同上
- `server/app.py:208` `lastErrorActive = bool(last_error) and (last_failure_date == today or ...)`——跨天失效
- `server/app.py:190-221` `/health` 不含任何构建/版本标识
- `server/tools/health_alert_check.py:74-80` 只 `print` JSON 到 stdout + 退出码，**不发送任何通知**

**问题：**
1. 三种静默失败（任务没跑 / 跑了一半 / 发布未切换）**全部不可自动发现**。这是本方案认为最严重的一条：不是"观测不好"，而是"观测不存在"。
2. 无 traceId → 一次请求跨 API/计算/公告/DB 的路径无法串联；无 `dataset_version` 维度 → 无法回答"这个结果是哪个版本算出来的"。
3. 健康检查不含构建信息 → 回滚时无法确认线上跑的是哪个 commit（致命）。
4. `health_alert_check.py` 需要人工执行才产出告警（README:55），等于没有告警。

**建议改法：** 见 §7——结构化 JSON 日志（必带 `trace_id`/`job_run_id`/`dataset_version`/`rule_version`/`business_date`）、`job_run` 记账 + `catchup_scan`、`/health` 新字段（含 `build.commit`）、告警规则 YAML + 推送通道 + 值班手册。

### OPS-4 无 CI/CD：全靠人工命令，且 GitHub 分支直接绑定生产构建

**证据：**
- 仓库**无 `.github/` 目录**（已确认）
- `README.md:82-94` 云托管代码源 = GitHub `nofindx/Stock-Abnormal` 分支 `Stock-Abnormal`，根目录 `Dockerfile` 构建
- `README.md:51-58` 全部测试命令靠人工手敲（`unittest` / `api_contract_check.py` / `prediction_migration_check.py` / `health_alert_check.py` / `node --check` / `json.tool` / `git diff --check`）
- `docs/正式上线清单.md:15、21-23` 多项验收仍为未勾选 `[ ]`

**问题：**
1. 开发分支 = 生产构建源。云托管虽需手动点"发布"，但**从"构建成功"到"发布到生产"之间没有任何质量闸门**。
2. 现成的门禁脚本（`api_contract_check.py` 等）没有被执行的位置，无法阻止一次坏发布。
3. 小程序包（上线清单:20 记 208,857 字节）无体积门禁、无"包内不含 127.0.0.1"门禁——而 `README.md:44-46` 要求上传前**手工**改 `devApiBaseUrl`、"上传前恢复云托管地址"，这是最容易漏的一步，漏了就是把 `127.0.0.1` 发到生产。

**建议改法：** 见 §5。核心是三件事：分支策略（生产构建源改为 `release/*` 或 tag）、CI 全量门禁（含迁移双向可执行）、CD 自动验收 + 自动回滚。

### OPS-5 事实库与 PDF 在容器临时盘，多实例必然丢失且不可审计

**证据：**
- `server/services/monitor_service.py:62` `MONITOR_DB_PATH` 默认 `/tmp/stock-abnormal/monitor.db`；`:15` `import sqlite3`
- `server/data/fact_ledger.py` 全模块 SQLite，`server/services/monitor_service.py:71` `sqlite3.connect`
- `server/services/monitor_service.py:195` `MONITOR_PDF_DIR` 默认 `/tmp/stock-abnormal/monitor-pdf`
- `server/app.py:283-294` `/api/monitor/announcement` 直接 `file_path.read_bytes()` 从**本地盘**读 PDF
- `server/app.py:317` `MONITOR_PUBLIC_BASE_URL` 硬编码默认生产域名

**问题：**
1. 实例重启/扩缩/发布 → 事实账本与 PDF 全丢（宋砚秋 P1-7 同结论）。PRD §6「监管事实先入账，再由规则和计算使用」在运维层面不成立。
2. **多实例下 PDF 只存在于采集它的那台**，`/api/monitor/announcement` 在其他实例上必然 404——PRD §6「监管事实有效期内通过页面点击查看」与验收 #13 直接失败。
3. 回执要求的「生产数据集匿名事实计数必须为 0」**无法审计**：数据在 `/tmp`，且没有任何对外指标。
4. 硬编码默认域名：换环境会生成指向错误域名的公告链接（对外可见，属于可感知事故）。

**建议改法：**
- 事实库迁 MySQL（与 `prediction_dataset` 同库），PDF 迁 COS 对象存储；MySQL 只存 `pdf_object_key` / `pdf_sha256` / `pdf_size_bytes` / `pdf_url`。
- PDF 打开改为 **COS 签名直链**（带有效期）或后端代理（代理时后端从 COS 取，**不再依赖本地盘**）。
- `/health` 暴露 `gates.anonymousFactCount`，**> 0 即 P1 告警**（回执硬要求）。
- `MONITOR_PUBLIC_BASE_URL` 移入集中配置，**不再给默认值**，`production` 环境缺失即 fail-fast。

### OPS-6 发布无灰度、无原子切换载体、无回滚矩阵

**证据：**
- `server/services/market_calc_repository.py:150-170` `prediction_dataset` 主键 `(dataset_role, target_trade_date)`，**无版本列**
- `README.md:94-95`「发布后先检查 `/health`，再按测试文档执行 API 和小程序验收」= 发布即全量
- `docs/正式上线清单.md:96`「按云托管控制台回滚上一稳定版本」= 只能整体回滚镜像，无法只回滚数据

**问题：** vNext 每天发布一个新 `dataset_version`。"发布"从"每周一次代码发布"变成"每天一次数据发布 + 每周一次代码发布"，两者失败模式与回滚动作完全不同（前者回退指针，后者回退镜像），现网只有后者。

**建议改法：** 见 §6.3 / §6.4——`dataset_pointer` 单行原子切换（< 50 ms，宋砚秋 §5.2 同）、四阶段灰度（G0 影子 → G3 下线）、七类故障的回滚矩阵、以及"没有回滚就不上线"发布前五项检查表。

### OPS-7 MySQL 无连接池，上游调用无超时/无重试/无限流

**证据：**
- `server/services/market_calc_repository.py:63-70` `connection()` 每次 `driver.connect(...)` 新建，`finally: connection.close()`——**全库无连接池**
- `server/services/tushare_client.py:80-92` `call()` 无 timeout 参数、无重试、无限流
- `server/services/market_service.py:2608` 逐股循环内 `self.client.daily(ts_code=stock["ts_code"], ...)`
- `server/app.py:401` `ThreadingHTTPServer`——无界线程池，无请求超时
- `server/services/market_service.py:200` `ThreadPoolExecutor(max_workers=2)`

**问题：**
1. **连接风暴**：每个请求 1~N 次 TCP 握手 + 鉴权。盘中峰值下 CloudBase MySQL 连接数被打满 → "Too many connections"，全站失败。
2. **上游挂起**：Tushare 无超时 → 占满 `prediction` 线程池（仅 2 worker）→ 级联到 HTTP 线程 → 雪崩。且 `ThreadingHTTPServer` 无界线程池没有熔断闸门。
3. **配额击穿**：5,500 次逐股调用，重试场景下极易超限 → 整体失败 → 数据集不发布 → P1。

**建议改法：**
- 连接池（`DBUtils.PooledDB` 或自建），按角色设上限：api 每实例 8、worker 4、migrate 1；`wait_timeout` 小于 MySQL 侧；暴露 `poolInUse` / `pool_wait_seconds` 指标。
- Tushare 客户端：全站令牌桶（`TUSHARE_QPM`，默认 60）+ 单次超时 10 s + 指数退避重试 2 次；**全改批量 `daily(trade_date=)`**（宋砚秋 6.6 同结论）。
- HTTP 层：请求级超时（读 8 s / 写 15 s）+ 每路由信号量；实时行情源熔断（连续 3 次失败熔断 60 s，半开探测）+ 指数行情 30 s 进程内共享缓存（顾图南 5.5 同）。

### OPS-8 密钥与配置管理无边界，且存在本地密钥文件兜底路径

**证据：**
- `server/services/tushare_client.py:25-51` `_read_local_token()` 从 `key/key.txt`、`key/tushareMcp.txt` 读 token
- `server/services/market_calc_repository.py:31-49` MySQL 凭证纯 env，但**无集中定义、无启动校验**
- `server/app.py:317` 硬编码默认生产域名
- 环境变量散落在 10 处 `os.getenv`（`TUSHARE_TOKEN` / `MYSQL_*` / `MONITOR_DB_PATH` / `MONITOR_PDF_DIR` / `MONITOR_PUBLIC_BASE_URL` / `PREDICTION_CACHE_COMPAT_READ` / `FORCE_MARKET_HISTORY_REBUILD` / `BROKER_HISTORY_SCAN` / `HOST` / `PORT`）
- `README.md:42` 只有一句原则性声明「不进入小程序包、接口响应或日志」

**问题：**
1. **半可用启动**：缺变量时服务照样起来（`/health` 只显示 `configured.host=true`，密码为空也能启动），故障定位成本极高。
2. 本地密钥文件兜底是开发便利，一旦将来有挂载或误打入镜像层，密钥即泄漏（当前 `.dockerignore` 已排除 `key`，这是对的，但机制上依赖人的记忆）。
3. 云托管环境变量明文存储、对服务内所有进程可见，**无轮换机制、无审计、无最小权限约束**（MySQL 账号很可能拥有 DDL 权限）。
4. 无集中清单 → 新增环境（staging）时必然漏配。

**建议改法：**
- 配置集中到 `server/config.py`（dataclass + `from_env()` + `validate()`），**启动即校验必填项，缺失直接 fail-fast 退出并打印缺失清单**，不做"半可用"。
- `APP_ENV=production` 时**禁用本地密钥文件兜底**路径。
- 环境变量按最小权限拆分：**应用账号只给 DML**（`stock_abnormal` 库），**DDL 只在 `migrate` job 注入独立迁移账号**；Tushare token、COS 密钥分环境隔离。
- 输出层加 redact 过滤器（键名匹配 `token|password|secret|key` 一律 `***`），作用于日志、`/health`、错误响应。
- 密钥轮换流程写入运维手册（现网无任何轮换记录）。

## ③ P2 问题清单

> P2 定义：不阻塞首个数据集发布，但会显著影响可维护性、成本、安全或响应速度。

### OPS-P2-1 Dockerfile 单阶段、root 运行、无构建元数据
**证据：** `Dockerfile:1-21`：`python:3.11-slim` + `apt-get install tesseract-ocr tesseract-ocr-chi-sim tesseract-ocr-eng` + `pip install`（PyMuPDF / Pillow / pypdf / pytesseract），单阶段，**无 `USER`**（以 root 运行）、无 `HEALTHCHECK`、无 `ARG GIT_COMMIT`。
**影响：** 镜像量级 700 MB~1 GB，冷启动与**盘中 09:30 扩容**变慢（扩容正是峰值关键路径）；root 运行放大漏洞影响面；线上无法自证版本（回滚时致命）。
**建议：** 多阶段构建；`USER 10001`；`ARG GIT_COMMIT` → `ENV BUILD_COMMIT` 并由 `/health` 暴露；**按角色裁剪镜像**——API 不需要 OCR，用 `api` target 去掉 tesseract/PyMuPDF，镜像可降到 ~200-350 MB。

### OPS-P2-2 健康检查把外部依赖纳入存活判定，且太重
**证据：** `container.config.json:7-12` `/health` 每 30 s；`app.py:163-227` 每次 `/health` 都要查 `market_calc_job`、`stock_basic_coverage()`、`prediction_migration_status()`、`monitor_health()`（读 SQLite）、`_is_trade_day()`（可能回源 Tushare）。
**影响：** 每实例每 30 s 一次"半个业务请求"的 DB 负载；上游抖动 → `/health` 超时 → 云托管判定不健康 → 重启 → 更多实例重启，**雪崩**；且 `monitor_health` 读 `/tmp` SQLite，不同实例返回不同结果。
**建议：** 拆 `/health/live`（纯进程存活，< 5 ms，不查任何外部依赖，容器健康检查用）、`/health/ready`（发布验收）、`/health`（业务健康，运维/CI 用，内部依赖查询加 3 s 超时保护）。

### OPS-P2-3 无 graceful shutdown，滚动发布会硬中断长任务
**证据：** `app.py:398-409` 只 `serve_forever()` + `finally close()`，无 `SIGTERM` 处理；调度线程 `daemon=True`（`market_service.py:292`），进程退出即被杀。
**影响：** 云托管滚动发布发 SIGTERM → 正在跑的日终重算（目标 8 min）被硬中断 → 半套数据落库。**这是「跑了一半」静默失败的主要来源。**
**建议：** 注册 SIGTERM handler → 置 `stop_event` → 停止接新请求 → 等待在途任务完成或最多 `GRACEFUL_TIMEOUT`（默认 300 s）→ 退出；`job_run` 记录 stage，重启后从失败 stage 续跑。

### OPS-P2-4 无请求级超时、无并发上限、无熔断
**证据：** `app.py:401` `ThreadingHTTPServer` 无界线程；`market_service.py:200` 预测线程池仅 2 worker；实时行情三源串行回退（顾图南 5.5）。
**影响：** 单股详情最坏 12 s（顾图南 5.4）；开盘集中进入时线程池打满 → 全站排队。
**建议：** HTTP 层请求超时 + 每路由信号量；实时源熔断（3 次失败熔断 60 s，半开）；指数行情 30 s 共享缓存。

### OPS-P2-5 小程序发布与后端发布未解耦，且无体积/域名门禁
**证据：** `README.md:44-46` 手工改 `devApiBaseUrl`；`docs/正式上线清单.md:22` 该项仍为未勾选；`miniprogram/project.config.json` `urlCheck:false`、`uploadWithSourceMap:true`。
**影响：** 漏改即把 `127.0.0.1` 发到生产；`urlCheck:false` 让开发者工具不校验域名，生产才暴露（PDF `downloadFile` 域名未配白名单 → 线上打不开公告）；sourcemap 打进包。
**建议：** `devApiBaseUrl` 按 `wx.getAccountInfoSync().miniProgram.envVersion` 自动切换，**禁止手改**；CI 断言包内不含 `127.0.0.1`/`localhost`/`http://`；提审版本 `uploadWithSourceMap:false`。

### OPS-P2-6 无数据保留与清理作业
**证据：** PRD §6 / 验收 #13 要求清理 PDF 二进制；`docs/生产操作手册.md` 全文无任何清理作业；`monitor_service.py:195` PDF 只落盘不清理。
**影响：** 宋砚秋 6.2 估算 PDF 6 GB/年；无清理 → 3 年 18 GB+ 且线性增长，且"监管期结束"无判定作业 → PRD §6 合规目标无法达成。
**建议：** `announcement_pdf_cleanup`（J9）日任务 + `pdf_cleanup_log` 留痕；`/health` 暴露 `pdfObjectBytes` / `pdfCleanedLast24h`。

### OPS-P2-7 无库级备份与恢复演练
**证据：** `docs/生产操作手册.md:29-31`、`:105-107` 只有表级 `CREATE TABLE ... AS SELECT` 的手工备份；**无库级备份、无恢复演练、无 RPO/RTO 定义**。
**影响：** 事实库迁 MySQL 后，一次误删 = 监管事实永久丢失（公告原文可能已下线，**不可重放**）。
**建议：** 见 §9.1。这是迁库后必须立刻补的一条。

### OPS-P2-8 无容量基线与压测，扩缩容策略未定义
**证据：** README 与运维手册均无 QPS/并发/实例数基线；`container.config.json` 只有 `service`/`containerPort`/`build`/`healthCheck`，**无 `minNum`/`maxNum`/`cpu`/`mem`**。
**建议：** 见 §8.1-8.3（20 QPS 设计基线 + api min2/max6 + worker 1×2C4G）。

### OPS-P2-9 告警无推送通道与值班机制
**证据：** `server/tools/health_alert_check.py:74-80` 只 print + 退出码，不发送通知；README:55 需人工执行。
**建议：** 外部巡检（云函数/定时触发器 + 企业微信机器人 Webhook）每 15 min 打 `/health`，按 `alerts[]` 分级推送；脚本保留为本地排障工具。

### OPS-P2-10 环境隔离缺失：开发版直连云托管生产
**证据：** `README.md:46`「开发者工具 develop 环境默认请求云托管地址，上传的开发版本可直接访问真实数据」。
**影响：** 开发版/体验版直接读写生产 MySQL，一次误操作即生产事故；无 staging，所有验证都在生产做。
**建议：** 拆出 staging 云托管服务 + staging MySQL（生产脱敏子集），开发版默认指 staging。

## ④ 部署形态与进程/任务拆分设计

### 4.1 结论：拆成 2 个常驻服务 + 1 个一次性 job（同一镜像、不同 `APP_ROLE`）

| 服务 | 角色 | 实例数 | 对外 | 职责 |
|---|---|---|---|---|
| `stock-api` | `APP_ROLE=api` | min 2 / max 6（CPU 60% 扩容） | 公网（小程序 `callContainer`） | 只处理 HTTP，**不启动任何调度线程、不执行写任务** |
| `stock-worker` | `APP_ROLE=worker` | **min=max=1** | 不公网暴露 | 跑 J0-J10 全部定时任务 + `catchup_scan` |
| `stock-migrate` | `APP_ROLE=migrate` | 按需，跑完即停 | — | 版本化 DDL，抢全局锁 |

**为什么必须拆（第一性原理）：** 定时任务的本质是全局单点，HTTP 服务的本质是无状态可水平扩展。同进程部署 = 想扩容 API 就必然复制出 N 个调度器。拆开后 API 可自由扩容，worker 固定单实例，语义清晰，且**不违反 ARCH §7「模块化单体、不拆微服务」**——代码库、镜像、模块边界全部不变，只是进程角色分离。

**为什么不能完全依赖云托管定时触发器：** 触发器只保证"到点发起一次 HTTP"，不保证成功、不保证串行、**无补偿**。worker 恰好在重启时，这次触发就丢了，且没有任何记录说它丢了（正是 OPS-3 的"任务没跑"）。因此：**触发器负责"到点叫醒"，`job_run` 表负责"记账与补跑"**。

### 4.2 关键简化：把「09:00 D/N 切换」从任务降级为函数

PRD §8.1 的 09:00 切换、15:00 后等收盘、周末/休市不刷新，是产品硬约束。若把它实现成"定时任务"，就引入了"切换任务失败 → 全站日期错乱"的新失败模式（且多实例下还要保证所有实例同时切换成功）。

**改法：** `date_role = resolve(trade_calendar, now, dataset.target_trade_date)` 是一个**纯函数**，由 API 在每个请求的读取路径上计算，不落库、不调度、不缓存跨实例状态。多实例天然一致，也不存在"切换失败"。交易日历来自 MySQL `trade_calendar` 表（宋砚秋 §4.3），进程内缓存 5 min。

这是本方案里最重要的一处"用函数替代状态"的设计——**能用纯函数解决的时间语义，绝不引入定时任务**。

### 4.3 任务租约（无 Redis 方案：MySQL advisory lock + 租约表）

**选型判断：不引入 Redis。**
- 现网无 Redis 客户端（`server/requirements.txt` 全文无 `redis`），PRD §9.3 第 220 行与 ARCH §7 第 139-140 行声称的「腾讯云 Redis 当前集成」与事实不符（宋砚秋 P2-2 同结论，`docs/生产操作手册.md:7-8` 明确写着"当前后端没有 Redis 客户端"）。
- 本系统任务量极小（每日 ~10 个任务、分钟级粒度），MySQL `GET_LOCK` 完全够用。引入 Redis = 多一个有状态组件、一份成本、一套故障模式，而毫秒级租约的性能优势用不上。
- **给文档的改法**：PRD §9.3 / ARCH §7 的「腾讯云 Redis（当前已有）」改为「Redis：可选组件，**当前未启用**；租约、限流、刷新协调由 MySQL 实现」。重新评估条件见 §7.6。

```sql
CREATE TABLE task_lease (
  task_name      VARCHAR(64) NOT NULL PRIMARY KEY,
  business_date  CHAR(8)     NOT NULL,
  owner          VARCHAR(64) NOT NULL,          -- instance/pod id
  generation     BIGINT      NOT NULL DEFAULT 0,
  lease_until    DATETIME(3) NOT NULL,
  heartbeat_at   DATETIME(3) NOT NULL,
  created_at     DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  KEY idx_lease_until (lease_until)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

```sql
-- 1) 抢会话级命名锁（连接断开自动释放，无需 TTL 兜底）
SELECT GET_LOCK(CONCAT('sa_lease_', :task_name), 0) AS got;
-- 2) 锁内 upsert：无记录 / 已过期 / 自己持有 → 续约；否则放弃
INSERT INTO task_lease (task_name, business_date, owner, generation, lease_until, heartbeat_at)
VALUES (:name, :bd, :owner, 1, DATE_ADD(NOW(3), INTERVAL :ttl SECOND), NOW(3))
ON DUPLICATE KEY UPDATE
  owner        = IF(lease_until < NOW(3) OR owner = VALUES(owner), VALUES(owner), owner),
  generation   = IF(lease_until < NOW(3), generation + 1, generation),
  lease_until  = IF(lease_until < NOW(3) OR owner = VALUES(owner),
                    DATE_ADD(NOW(3), INTERVAL :ttl SECOND), lease_until),
  heartbeat_at = IF(owner = VALUES(owner), NOW(3), heartbeat_at);
-- 3) 回读确认 owner = 自己 且 lease_until > NOW(3)；否则随机退避后放弃
-- 4) 释放：UPDATE ... SET lease_until = NOW(3);  SELECT RELEASE_LOCK(...)
```

- **心跳**：长任务每 30 s 续约；心跳写失败即自杀（避免僵尸持有）。
- **TTL = 900 s** > 单次任务 P99（宋砚秋 6.7 全量重放 P99 < 12 min = 720 s）。
- 幂等兜底：租约解决"不并发"，唯一键（`uk_fact_key` / `uk_result` / `dataset_version`）解决"重复执行结果一致"。

### 4.4 每日任务编排（worker，Asia/Shanghai）

| # | 任务 | 触发 | 依赖 | SLA | 失败处置 |
|---|---|---|---|---|---|
| J0 | `migrate` | worker 启动前置（抢 `sa_schema_migration` 锁） | — | < 60 s | fail-fast，容器退出，发布失败 |
| J1 | `calendar_sync`（交易日历） | 每日 06:00 + 启动补跑 | — | < 30 s | 失败 → 当日全线 `unavailable` + P1 |
| J2 | `security_sync`（`stock_basic` / 板块 / 指数映射） | 06:10 | J1 | < 60 s | 同上 |
| J3 | `daily_bar_ingest`（批量 `daily(trade_date)` + `index_daily` + `suspend_d`） | 15:30 / 16:00 / 16:30 / 17:00 / 18:00 重试 | J1,J2 | < 3 min | 重试 5 次；全失败保留上一版本 + P1 |
| J4 | `announcement_collect`（列表 + 正文 + PDF→COS） | 15:20 起，**独立于 J3 并行** | J1 | < 15 min | 部分失败 = 相关证券 `pending_verification`，不阻断发布 |
| J5 | `announcement_parse`（正文/PDF 解析、OCR） | J4 产出即刻（内部队列 4-8 worker） | J4 | < 10 min | 单篇超时 20 s，失败进重试队列 |
| J6 | `recompute`（5,500 × 4 项 × 2 角色） | J3 成功 且 J5 达覆盖阈值 | J3,J5 | **P95 < 8 min** | 超时 → **不发布**，保留上一版本 + P1 |
| J7 | `quality_gate`（阻断式校验） | J6 后 | J6 | < 60 s | 任一 block → **不发布** + P1 |
| J8 | `publish`（切 `dataset_pointer`） | J7 通过 | J7 | **< 50 ms** | 事务失败自动回滚，指针不动 |
| J9 | `pdf_cleanup`（清理过期 PDF 二进制） | 每日 03:00 | J1 | < 5 min | P3，次日补跑 |

**关键设计点：**
1. **J4/J5 与 J3/J6 解耦并行**（顾图南 O-4）：公告侧含 OCR 最坏 15 min，不阻塞行情主线；正文未完成的证券其"公告相关结论"标 `pending_verification`，其余三项照常发布——符合「不可用不得变安全」。
2. **15:00 硬约束**：J3 不得早于 15:00；用 `trade_calendar` 判定交易日才跑，周末/休市跳过（沿用现网 `_market_scheduler_loop` 的判断逻辑，迁到 worker 后保留）。
3. **09:00 切换不是任务**（见 §4.2）。
4. **J10 是静默失败的总闸门**：它比对"今日应跑任务清单（由 `trade_calendar` 推出）"与 `job_run` 的实际 success 记录，缺一个即补跑 + 告警。

## ⑤ CI/CD 流水线

### 5.1 分支策略（现网只有一个生产分支 `Stock-Abnormal`，必须改）

| 分支 | 用途 | 保护 |
|---|---|---|
| `main` | 默认分支，集成 | 保护分支，只接受 PR |
| `feat/*` `fix/*` | 开发 | PR → `main` |
| `release/*` 或 tag `v*.*.*` | **生产构建源** | 需 CI 全绿 + 人工 approval |
| `Stock-Abnormal` | 1.0.x 归档 | 冻结 |

**为什么：** 把"开发分支"和"生产构建源"分开，是"没有回滚就不上线"的第一道闸门——生产构建源必须是被 PR 门禁验证过的、可被打 tag 的不可变引用。云托管构建源从 GitHub 分支改为 **TCR 镜像 tag**（构建与发布分离，见 §5.3）。

### 5.3 CD（`release.yml`，tag `v*` / `release/*` push 触发）

1. CI 全绿（required checks 全通过）。
2. 构建镜像 → 打 `sha-<commit>` 与 `v<x.y.z>` **双 tag**（**禁止 `latest`**）。
3. 推到腾讯云容器镜像服务 TCR；**云托管生产服务代码源改为 TCR 镜像 tag**（替代当前的 GitHub 分支源），实现构建与发布分离。
4. **DB 迁移（阻断 + 人工 approval）**：运行一次性 `stock-migrate` job（抢全局锁），失败即中止发布。
5. 先发布 **worker**（单实例，避免新任务被旧代码处理）。
6. 再滚动发布 **api**（保留 1 个旧实例观察 5 min）。
7. **自动验收**：`/health` 断言（`build.commit` == 期望、`dataset.version` 存在、`gates.anonymousFactCount == 0`、`alerts == []`）→ `api_contract_check.py --require-data` → `health_alert_check.py`。
8. 任一步失败 → **自动切回上一镜像 tag** + P1 告警。

**构建失败处置：** 不产生新版本，生产保持旧镜像；通知值班群；**禁止"手工改环境变量绕过"**。
**发布失败处置：** 见 §6.4 回滚矩阵。若 DB 迁移已执行，先确认新 schema 对旧代码向前兼容（两阶段 DDL 保证），再决定是否执行 `down`。

## ⑥ 迁移与灰度回滚

### 6.1 版本化迁移框架：自建 migration 表 + 编号 SQL（不用 Alembic）

**选型理由：** ① 现网 schema 由 `ensure_schema()` 手写 SQL 生成，没有 SQLAlchemy 模型可供 Alembic autogenerate（宋砚秋 §④ 的新模型是设计稿，不是代码）；② 本项目 DDL 全是手写 SQL，Alembic 只能当"文件执行器"，引入 SQLAlchemy 依赖 + 一层抽象的收益低于成本；③ 自建 30 行即可满足：编号 + checksum + 锁 + 记录。

```sql
CREATE TABLE schema_migration (
  version     VARCHAR(32)  NOT NULL PRIMARY KEY,   -- '0007'
  name        VARCHAR(128) NOT NULL,
  checksum    CHAR(64)     NOT NULL,               -- sha256(up.sql)
  applied_at  DATETIME(3)  NOT NULL,
  duration_ms INT          NOT NULL,
  applied_by  VARCHAR(64)  NOT NULL                -- 'ci' / 'worker-<instance>'
);
```

**执行器规则：**
1. 全局锁 `SELECT GET_LOCK('sa_schema_migration', 10)`——同一时刻只有一个容器跑 DDL。
2. 每个迁移单文件、单事务。**DDL 与 DML 不得混在同一迁移**（MySQL DDL 不能回滚）。
3. 已应用迁移的 checksum 变化 → **直接报错中止**（禁止改动已上线的迁移文件）。
4. `--dry-run` 输出待执行清单；`--check` 用于 CI 空库重建验证。
5. 每个 `up` 必须配 `down`（`down` 允许是"人工步骤说明"，但必须存在）。

### 6.2 SQLite 临时盘 → MySQL 的数据搬运（含「匿名事实计数必须为 0」审计）

**核心难点：** 事实库在 `/tmp`，**容器重启即消失**，搬运窗口只有"当前存活的那个实例"。因此第一步不是迁移，是**抢救**。

| 步 | 动作 | 阻断条件 |
|---|---|---|
| 0 | **抢救导出**：在存活的 worker 容器内跑一次性脚本，把 `announcement_fact` / `announcement_pending` / `monitor_snapshot` / `monitor_state` / `ingest_run` 导出为 JSONL（量级几 MB），**立即上传 COS**（绝不停留在容器盘） | 导出失败 → 停止，先人工介入 |
| 1 | **冻结写入**：worker 成为唯一写入者，API 不再写事实库 | — |
| 2 | **`identity_audit`（阻断）**：`fact_key` 五要素（`ts_code`/`fact_type`/`fact_start_date`/`fact_end_date`/`direction`，宋砚秋 P1-1）任一为空 → `identity_missing`；无法从正文确定 `fact_end_date` → `identity_missing`；统计 `anonymous_fact_count`（无稳定身份却已正式计数的事实数） | **`anonymous_fact_count > 0` → 禁止迁入生产**，必须先在 staging 人工补齐或降级为 `pending_verification` |
| 3 | **影子入库**：写入新表时 `confirmation_status='pending_verification'`，**不参与正式计次**；保留旧 JSONL 快照 | — |
| 4 | **对账**：`SELECT COUNT(*) FROM regulatory_fact WHERE confirmation_status='confirmed' AND fact_key=''` 必须为 0；与导出行数对账（允许因 `ON DUPLICATE KEY` 归并而减少，但**归并必须有日志**） | 不一致 → 停止 |
| 5 | **放行**：人工确认 + 门禁通过后，批量置 `confirmed`，触发一次全量重算与发布 | — |
| 6 | **回滚**：JSONL 快照在 COS 保留 90 天；MySQL 新表在灰度期不是唯一真值，可整表 `TRUNCATE` 重来 | — |

> 注意：回执明确要求「生产 10 日同向事实若缺少稳定来源 ID/内容哈希，必须标记 `identity_missing` 并待核验，不允许匿名 fallback 事实正式计数；**生产数据集匿名计次数必须为 0**」。第 2 步是这个要求在运维流程上的唯一落点，也是 §7.4 中唯一 `for: 0m` 的 P1 告警。

### 6.3 四阶段灰度（每阶段有明确 Exit 条件）

| 阶段 | 内容 | Exit 条件（**全部**满足才进下一阶段） |
|---|---|---|
| **G0 影子** | 新旧并行计算，只写新表，三页仍读旧路径；每次发布产出差异报告 | 连续 **5 个交易日**：`dataset_version` 均生成成功、新旧四项结果差异率 < 0.5% 且**所有差异可解释** |
| **G1 只读灰度** | 内部账号/体验版小程序读新 `dataset_version` | 连续 **3 个交易日**：接口 P95 达标（宋砚秋 6.7）、`anonymousFactCount == 0`、无 P1 告警 |
| **G2 生产切换** | 切 `dataset_pointer` 到新版本，正式版小程序生效 | 连续 **5 个交易日**：门禁全绿、事实匹配率 ≥ 基线、公告正文可读率 ≥ 基线、无数据类 P1 |
| **G3 下线旧路径** | 删 `prediction_cache` 兼容读、删 SQLite 依赖、关 `PREDICTION_CACHE_COMPAT_READ` | 备份完成 + **14 天**观察期（沿用 `docs/生产操作手册.md:111` 的 14 天约定） |

- **发布原子性**：`dataset_pointer` 单行 `UPDATE`（宋砚秋 §5.2），< 50 ms。三页读取统一先 `SELECT ... FROM dataset_pointer` 拿 version，再按 version 查明细，**禁止任何"读最新"的路径**。
- **影子校验**：G0 期间同时按新旧口径计算（宋砚秋 P1-5 的 10 日同向 `fact_end_date`/窗口合并口径切换必须走这一步），差异写 `quality_check_result`，超阈值即阻断。

### 6.4 回滚矩阵

| 故障层 | 检测 | 回滚动作 | RTO | 数据损失 |
|---|---|---|---|---|
| 代码发布（api） | 自动验收失败 / 5xx 突增 | 云托管切上一镜像 tag | < 5 min | 无 |
| 代码发布（worker） | 任务失败告警 | 同上；在途任务可重跑 | < 5 min | 无 |
| DB 迁移 | 执行失败 / `--check` 失败 | 执行 `down`；若 DDL 已应用且无 `down`，靠两阶段兼容让旧代码在新 schema 运行 | < 15 min | 无 |
| **数据集发布（每日）** | 门禁 block / 发布后校验失败 | **指针不切换（默认行为）**；已切换则 `UPDATE dataset_pointer` 指回上一 version | **< 1 min** | 无（明细按 version 保留 ≥ 30 天） |
| 数据污染（错误事实入账） | 匿名事实告警 / 人工发现 | 该 `fact_key` 置 `revoked` + 触发重算发布（事实只增不改） | < 30 min | 无 |
| 误删数据 | 备份校验失败 | 从备份恢复到临时库，按表导回 | < 2 h | ≤ 24 h（日备） |
| 小程序版本 | 线上崩溃 | 微信公众平台回退上一版本 | 10-30 min | 无（前端无状态） |

**「没有回滚就不上线」发布前五项检查表**（每次发布逐条勾选）：
1. 镜像有上一 tag 且验证可用；
2. 本次迁移有 `down`，或已确认两阶段兼容；
3. 数据集有上一 version 且明细保留 ≥ 30 天；
4. 小程序有上一线上版本可回退；
5. 值班人已确认并知悉回滚路径。

groups:
- name: 数据集与门禁
  rules:
  - alert: DatasetNotPublished
    expr: (time() - dataset_published_at_seconds) > 26*3600 and is_trade_day == 1

    expr: dataset_age_seconds > 36*3600 and is_trade_day == 1
    for: 30m
    labels: {severity: P1}
  - alert: AnonymousFactCountNonZero          # 回执硬要求：生产必须为 0
    expr: anonymous_fact_count > 0
    for: 0m
    labels: {severity: P1, runbook: "runbooks/anonymous-fact.md"}

- name: 静默失败巡检                            # 对应 OPS-3 的三种失败模式
  rules:
  - alert: JobMissed                            # ① 任务没跑

    labels: {severity: P1, runbook: "runbooks/job-missed.md"}

    expr: job_status{job="J6"} == 2 and job_stage != "finished"
    for: 5m
    labels: {severity: P1}
  - alert: PublishNotSwitched                   # ③ 门禁过了但指针没切

    labels: {severity: P1}
  - alert: WorkerNoHeartbeat                    # worker 死 → 所有任务静默停摆

    for: 0m
    labels: {severity: P1}

- name: 质量与上游
  rules:
  - alert: AnnouncementBodyReadableBelowBaseline
    expr: announcement_body_readable_ratio < 0.95
    for: 1h
    labels: {severity: P2}
  - alert: FactMatchRatioDrop
    expr: fact_match_ratio < 0.9 * fact_match_ratio offset 7d
    for: 1h
    labels: {severity: P2}

- name: 接口与容量
  rules:
  - alert: ApiP95LatencyHigh
    expr: histogram_quantile(0.95, rate(http_request_duration_seconds_bucket[5m])) > 0.8
    for: 15m
    labels: {severity: P2}
  - alert: ApiErrorRateHigh
    expr: rate(http_requests_total{status=~"5.."}[5m]) / rate(http_requests_total[5m]) > 0.01
    for: 10m
    labels: {severity: P1}
  - alert: MysqlPoolExhausted
    expr: mysql_pool_wait_seconds{quantile="0.95"} > 0.05
    for: 10m
    labels: {severity: P2}

- name: 成本与合规
  rules:
  - alert: PdfRetentionOverBudget
    expr: pdf_object_bytes > 30 * 1024^3
    for: 1h
    labels: {severity: P3}
  - alert: BackupMissing
    expr: time() - mysql_last_backup_at_seconds > 26*3600
    for: 0m
    labels: {severity: P1, runbook: "runbooks/backup-missing.md"}

### 7.5 告警分级与值班响应

| 级别 | 定义 | 通知 | 响应 |

| **P1** | 影响监管结论正确性或数据不可用：未发布数据集、匿名事实 > 0、接口 5xx > 1%、备份缺失、worker 失联 | 电话 + IM，7×24 | **15 min 内响应，2 h 内处置或回滚** |
| **P2** | 质量下降/延迟/成本：正文可读率 < 95%、P95 超标、配额逼近、任务漏跑已补跑 | IM，工作时间 | 当个交易日处置 |

**落地前提**：现网 `health_alert_check.py` **只 print 不发送**（`server/tools/health_alert_check.py:74-80`）。改造为：外部巡检（云函数/定时触发器 + 企业微信机器人 Webhook）**每 15 min** 打 `/health`，按 `alerts[]` 分级推送；脚本本身保留为本地排障工具。每条 P1 必须有 runbook（`ops/runbooks/`）且**至少演练过一次**。

### 7.6 Redis 取舍（明确写进文档）

- **当前不启用 Redis**：租约、限流、刷新协调、共享缓存全部用 MySQL / 进程内实现（现网本就如此）。
- **重新评估的触发条件**（任一）：① 盘中 QPS 持续 > 200 且 DB 读 P95 超标；② 需要跨实例共享"刷新协调"（当前单实例 worker 已覆盖）；③ 引入 MQ 替代 `job_run` 队列。
- **若引入**：只缓存可重建数据，键含 `dataset_version`，降级路径 = 直连 DB（**不得用空值/默认值兜底**），遵循宋砚秋 §7.4 的五条硬规则。
- **文档改法**：PRD §9.3 第 220 行、ARCH §7 第 139-140 行的「腾讯云 Redis（当前已有）」→「Redis：可选组件，当前未启用；租约与限流由 MySQL 实现」。

## ⑧ 容量与成本估算

### 8.1 前提（沿用宋砚秋 6.1，补充运维侧参数）

| 参数 | 取值 | 依据 |
|---|---|---|
| 活跃证券 N | 5,500 | 宋砚秋 6.1 |
| 交易日/年 | 243 | 宋砚秋 6.1 |
| DAU（上线首年保守） | 3,000 | 假设，需在 G1 用真实数据校正 |
| 单次会话请求数 | 8-12 | 搜索 3 + 详情 1 + 预测 2 + 监控 2 + 刷新 1-2 |
| **日请求量** | **≈ 30,000** | 3,000 × 10 |
| 峰值集中度 | 开盘 30 min 占全天 35% | A 股工具类小程序经验值 |
| **峰值 QPS** | 30,000 × 35% / 1800 ≈ **5.8** | **设计取 20 QPS（3.4× 冗余）** |

### 8.2 MySQL

- **存储**：宋砚秋 6.2 估算 3 年热数据 **≈ 1.82 GB**，日增 ≈ 24 MB（≈ 8.8 GB/年）；含 binlog 7 天与索引碎片 → **建议 50 GB**（与其一致）。
- **连接数（现网关键缺陷修正）**：现网**每请求新建连接**（`market_calc_repository.py:63-70`）。
  - api：池 8 × 实例数（min2 / max6）= **16~48**
  - worker：4；migrate：1
  - 只读副本（查询走从库）：8 × 实例数 = **16~48**
  - **峰值 ≈ 48 + 4 + 48 + 余量 ≈ 110** → 建议 `max_connections ≥ 200`
- **内存**：`innodb_buffer_pool_size ≥ 8 GB`（可全放下 1.82 GB 热数据 + 索引）。
- **成本量级**：主 8 GB + 50 GB + 1 只读实例 ≈ **¥600-1,200/月**（需以控制台实际报价核对）。

### 8.3 云托管实例

| 服务 | 规格 | 实例数 | 依据 |
|---|---|---|---|
| api | 1 vCPU / 2 GB | **min 2 / max 6**，CPU 60% 扩容 | 20 QPS × 单请求 ~120 ms ≈ 2.4 vCPU·s/s，2 实例足够；开盘峰值 6 实例兜底 |
| worker | **2 vCPU / 4 GB** | **1** | 全市场重算需并行（8 min SLA）+ OCR 线程池 4-8 |
| migrate | 0.5 vCPU / 1 GB | 按需，跑完即停 | — |

**为什么 worker 要 2 vCPU**：顾图南 5.2 估算现网日终 8-20 min，优化后主线 ≤ 5 min；公告侧 OCR 单篇 12-40 s × 30% × 30 篇 ≈ 108-360 s，需 4-8 并发才能压进 15 min。单 vCPU 无法达成 SLA。
**成本量级**：api 2 实例常驻 + 峰值 6 实例约 4 h/日 + worker 1×2C4G 常驻 ≈ **¥400-800/月**。
**优化**：非交易时段（15:00-次日 09:00 且非补跑窗口）把 api 缩到 1 实例，可省约 **30%** 计算成本。

### 8.4 对象存储（PDF）

- **产出**：宋砚秋 6.2 ≈ **6 GB/年（16 MB/日）**；顾图南 5.6 给 0.75-15 GB/年（按 100 KB-2 MB/篇）。取交叉区间：**55 篇/日 × 300 KB = 16 MB/日 ≈ 4-6 GB/年**。
- **清理后**：PRD §6 保留策略（有效期内常驻 + 审计保留）→ 长期留存 **30%** → 稳态 **1.2-1.8 GB/年**；10 年累计 **12-18 GB**。
- **预算**：标准存储 **30 GB**（含清理前堆积、版本冗余、日志）+ 生命周期规则（90 天转低频，365 天归档/删除，取决于保全要求）。
- **成本**：COS 标准存储 ≈ ¥0.118/GB/月 → 30 GB ≈ **¥3.5/月**。**真正成本在请求次数与外网下行**：建议**签名直链 + 短有效期** + 小程序侧 `downloadFile` 后本地缓存，避免后端代理（代理会额外消耗云托管 CPU 与流量）。合计 **¥20-40/月**。

### 8.5 Tushare 配额（现存最大外部风险）

| 项 | 现状 | 目标 |
|---|---|---|
| 日频请求数 | **5,500 次**（`market_service.py:2608` 逐股 `daily(ts_code=)`） | **≈ 7 次**（`daily(trade_date)` ×1 + `index_daily` ×5 + 日历 + `stock_basic` + `suspend_d`） |
| 超时 | **无**（`tushare_client.py:80-92`） | 10 s |
| 重试 | **无** | 指数退避 2 次 |

**收益：请求数下降 99.9%，从根本上消除配额击穿风险。** 这是本方案投入产出比最高的一项改动（约 1 人日）。`/health` 暴露 `tushare.qpsUsed/qpsLimit`，> 80% 告警。

## ⑨ 灾备与合规

### 9.1 备份策略（现网缺口最大的一项）

| 对象 | 频率 | 保留 | 恢复演练 |
|---|---|---|---|
| MySQL | 自动日备 + 周全备 | 日备 7 天 / 周备 8 周 / 月备 12 月 | **每季度一次**：恢复到临时库并跑 `api_contract_check` |
| `dataset_version` 明细 | 随库备份 + 每次发布导出 JSONL 到 COS | 30 天（回滚矩阵依赖） | 每半年一次 |
| 事实 JSONL 快照（迁移期） | 一次性 | 90 天 | — |
| COS PDF | 版本控制（+ 可选跨地域复制） | 版本保留 90 天 | 半年一次抽样下载校验 sha256 |
| 代码/配置 | Git + tag | 永久 | — |

- **RPO ≤ 24 h**（日备），**RTO ≤ 2 h**（恢复到临时库 + 按表导回，见 §6.4）。
- **必须做的第一件事**：现网只有表级 `CREATE TABLE ... AS SELECT` 的手工备份（`docs/生产操作手册.md:29-31`、`:105-107`），**无库级备份、无恢复演练**。事实库迁 MySQL 后，一次误删 = 监管事实永久丢失（公告原文可能已下线，**不可重放**）。这条在迁库当天就必须补齐，不能等到 M4。

### 9.2 高可用与多实例

- **api ≥ 2 实例跨可用区**（云托管默认多 AZ）；健康检查改用 `/health/live` 避免上游抖动导致误杀（OPS-P2-2）。
- **worker 单实例是刻意取舍**（任务天然单点）。可用性由"可发现 + 自动恢复"保证：`WorkerNoHeartbeat` 告警（900 s 无心跳即 P1）+ 云托管实例自动拉起 + `catchup_scan` 补跑。
- **数据库**：主 + 只读副本（查询走从库，可接受主从延迟 ≤ 1 s，宋砚秋 6.8）；**`dataset_pointer` 切换必须在主库事务内完成**——从库读到旧指针是安全的，因为旧版本也是一个完整、通过门禁的版本。

### 9.3 数据保留与清理

| 数据 | 保留 | 作业 |

| 公告 PDF 二进制 | 监管事实有效期内常驻；期满且无保全要求即清理，保留源 URL / sha256 / 正文证据 / 清理记录（PRD §6、验收 #13） | J9 日任务 |

### 9.4 隐私合规

- **无账户体系、搜索历史仅本地**（`docs/正式上线清单.md:42-47`）：服务端**不得引入任何用户标识**。因此：① 日志/埋点禁止记录 `openid`、设备信息；② `wx.cloud.callContainer` 自带用户态但我们不消费，代码注释与隐私指引保持"不调用微信用户身份接口"（上线清单:47）；③ 限流若需"按用户"，只能用**请求级**令牌桶（IP + 参数），**不得落地用户标识**。
- **日志脱敏**：搜索词不落日志。现网 `log_message` 直接关闭访问日志正是为此（理由正确），改造后继续保留该约束——**恢复访问日志但不恢复 query 记录**。
